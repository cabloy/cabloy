# A-Commerce Presentation Contracts

## Purpose and Authority

This document is the living resource/scene matrix for A-Commerce semantic presentation. It applies [PRD-UI-01](./prd.md) and [SRS-UI-05](./srs.md) under [ADR 0003](./decisions/0003-semantic-presentation-contracts.md).

It does not redefine product scope, DTO/API membership, validation, persistence, authorization, Model ownership, page ownership, or SSR privacy. Those remain authoritative in the PRD and SRS. Vona DTO render metadata translates an already-authorized scene contract into placement and renderer choice; Zova implements that metadata at runtime.

## Matrix conventions

| Column                       | Meaning                                                                                        |
| ---------------------------- | ---------------------------------------------------------------------------------------------- |
| Resource and scene           | The domain projection, audience, and task being described.                                     |
| Information areas and fields | Business facts needed by the scene, in intended reading or input order.                        |
| Boundary                     | Whether data is editable, readonly, derived, hidden, live, or immutable snapshot data.         |
| Presentation strategy        | Default, shared renderer, or a later Commerce-specific renderer decision.                      |
| Constraint and evidence      | Authority/privacy boundary that must survive the presentation work and its verification owner. |

## Product Admin renderer decision

Product Category identity reuses the Category-established shared resource renderers, not a Commerce-specific renderer: `basic-resource:formFieldResourcePicker` serves editable `categoryId` with resource `commerce-catalog:category` and relation name `category`; the same field handles readonly View state, and `basic-resource:resourcePicker` serves the List cell. Their default identity mapping displays `category.name`, so Product View/List must first expose exactly `category: { id, name }`; `categoryId` alone cannot resolve a readonly or table label. This approved response-only projection implies neither a Category summary/hierarchy/publication projection nor a new Category API.

Product publication reuses `basic-select:formFieldSelect` and `basic-select:select` with the existing localized `Unpublished` / `Published` items and boolean values `false` / `true`. Shared readonly select handling already normalizes SQLite `0` / `1` values, so Product requires neither custom coercion nor a custom renderer. Default text preserves title/description semantics, while the existing shared date and date-range renderers preserve business-date semantics. Gate B therefore requires no reverse-chain prerequisite; no Zova renderer, paired reverse build, or dependency synchronization changes belong to this documentation slice.

## SKU Admin renderer decision

SKU `priceCents` retains its persisted USD minor-unit meaning. The shared currency renderer is approved for reuse only with the Coupon Template minor-unit configuration `{ fixed: 2, exp: 2, zero: 2 }`, which displays and edits USD cents as two-decimal currency values while serializing back to integer minor units. The SKU source gate must confirm this emitted option behavior before referencing `basic-currency:formFieldCurrency` and `basic-currency:currency`; no Commerce-specific currency renderer or persistence conversion is authorized.

SKU lifecycle reuses `basic-select:formFieldSelect` and `basic-select:select` with the existing localized `draft`, `active`, `inactive`, and `archived` items. The renderer translates the current server-authorized state; it does not define or bypass the allowed transition graph, serializable update transaction, or `systemAdmin` permission boundary. Existing shared date and date-range renderers preserve the business-date fields and compact `code`/`createdAt` filter.

`productId` remains an ID-valued Admin field for this gate. A readable Product label would require a deliberate response-only `product: { id, title }` projection, a column-limited relation, explicit service includes, and generated-contract/runtime proof; that is an API-contract decision and is deferred rather than silently added. The projection must not include Category, publication, SKU, price, stock, or sellability facts.

`attributes` is structured `DtoSkuAttribute` data but is absent from the current generic Admin Create/Update/View/List DTO boundary. This gate preserves that omission. No attribute editor, summary, or response projection may be introduced until a separate DTO-contract decision approves its membership and chooses a renderer that preserves the name/value structure. The existing `basic-details` family is not treated as approval by itself. Default identity/text treatment remains the fallback for fields whose approved contract has no semantic renderer.

Gate B therefore approves only existing shared renderer identities and preserves all current SKU API, persistence, validation, lifecycle, stock, sellability, authorization, Model/page, customer catalogue, and order-snapshot boundaries; no reverse-chain prerequisite is required for this documentation-only decision.

## Order Admin renderer decision

Order state reuses `basic-select:formFieldSelect` and `basic-select:select` with localized labels for the existing nine persisted states. This translates state for the Admin workbench only; the Order service transition graph, transaction boundaries, and `systemAdmin` authorization remain authoritative. `payableTotalCents`, `eligibleSubtotalCents`, `discountCents`, and immutable line monetary facts reuse `basic-currency:formFieldCurrency` / `basic-currency:currency` with `{ fixed: 2, exp: 2, zero: 2 }`, preserving integer USD minor-unit persistence. Reservation deadlines and business dates reuse the shared date field/cell renderers; `createdAt` retains the existing date-range filter.

The readonly View uses the established grouped form layout. Its approved lines relation uses the existing `basic-details:formFieldDetails` convention: the visible `lines` relation supplies immutable data, a hidden `_lines` auxiliary schema supplies table columns, and the associated details schema supplies readonly row forms. The details row metadata has no Create, Update, or Delete actions; it may expose a view-only row action when needed. This reuses the existing Zova renderer behavior, so no reverse-chain renderer prerequisite is required. Address and coupon snapshots remain object-valued immutable facts; no live Address, Coupon, Product, or SKU relation is introduced for display convenience.

## Stock Admin renderer decision

Stock Balance and Stock Audit use the existing generic Resource List/filter and Back-only readonly View scenes. The approved compact field split keeps raw `skuId`: a readable SKU label would require a separately approved response-only relation projection, model relation, explicit service include, and emitted/runtime proof. No such projection is approved. Existing shared `basic-date` form/cell and date-range controls preserve `createdAt`/`updatedAt` and the exact `skuId` / `createdAt` filters.

On-hand, reserved, available, audit delta, and immutable before/after counters are scalar integers. Default numeric rendering preserves their units without implying editability. `available` remains a server-derived `onHand - reserved` fact. Audit operation remains default scalar rendering because no approved localized operation item contract exists; actor, reservation, balance, and correlation identifiers and reason retain default ID/text treatment. No custom quantity/delta/operation renderer, details projection, or reverse-chain prerequisite is approved.

The Balance `adjustStock` command remains separate from generic Resource mutation: it is server-authorized and not activated as an Admin UI action in this gate. Stock Audit remains immutable and GET-only. Dormant generated Create/Update DTOs do not authorize or surface generic CRUD. Gate C must prove the exact List/View membership and Back/View-only boundary, including the absence of Create/Update/Delete and of any adjustment action. Before contracting Audit View fields that are absent from the current generated schema, verify emitted metadata/OpenAPI behavior rather than hand-editing generated artifacts.

## Address Admin renderer decision

Address Admin uses the existing generic Resource List/filter and Back-only readonly View scenes. The approved compact List keeps scalar recipient/contact/location facts only: `recipientName`, `phone`, `countryCode`, and `city`, with `id` as the View link. It does not construct a formatted address summary, add a relation, or introduce a computed response field. The complete persisted address remains a readonly View concern.

Default text rendering preserves recipient, contact, country/region/city, postal-code, and address-line meaning without treating individual components as client-authoritative. Existing `basic-date` field/cell and date-range controls preserve `createdAt`/`updatedAt` and the exact `recipientName` / `phone` / `createdAt` filter. No custom Address renderer or reverse-chain prerequisite is approved.

The decision preserves the existing Admin `select`/`view` API and its independent `systemAdmin` authorization. It does not authorize the dormant generic frontend mutation helpers, change their ownership, or affect the separate customer `mine`/`viewMine`/`createMine`/`updateMine`/`deleteMine` DTO, Model, page, route-admission, query, mutation, or SSR boundaries. Gate C must prove the exact Admin List/View membership, filter layout, View-only/Back-only boundary, and absence of generic CRUD metadata before source work begins after Stock CI closure.

## Renderer selection rule

Use the default renderer for ordinary text and simple values when it preserves business meaning. Use a shared renderer for dates, enum labels/selects, cents, resource identities, and reusable details. Introduce a Commerce-specific renderer only when those shared resources cannot preserve the documented meaning or interaction, and then follow the reverse contract loop before backend metadata references it.

## Form Layout Authority

This matrix defines the A-Commerce resource/scene information areas and presentation decisions; it does not define a separate form-layout grammar. Author `tabs`, `groups`, `sections`, `fields`, and renderable `blocks` with the repository [Form Layout Guide](../../../cabloy-docs/frontend/form-layout-guide.md). Apply the semantic authority boundary in [ADR 0003](./decisions/0003-semantic-presentation-contracts.md): groups express business information areas, sections provide local Grid/flow placement, and tabs are reserved for genuinely independent areas. Layout metadata remains a presentation translation and must not become product, DTO/API, authorization, state/page, or SSR authority.
