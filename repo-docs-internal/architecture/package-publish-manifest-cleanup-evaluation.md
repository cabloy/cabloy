# Package Publish Manifest Cleanup: `clean-package` vs `publishConfig`

Status: Evaluation and recommended migration gates; no packaging or release behavior changed. Recheck tool versions and pack behavior before implementation.

## Question and conclusion

The [Vona module boilerplate](../../vona/packages-cli/cli-set-api/cli/templates/create/module/boilerplate/_package.json) currently uses `clean-package` at pack time to remove `exports["."].import` so a published package resolves to `./dist/index.js`, while the checkout still resolves local imports to `./src/index.ts`. Can `publishConfig.exports` replace this mechanism?

**With `pnpm pack` / `pnpm publish` 11.5.2, yes for the `exports` rewrite, but not for the entire cleanup policy. With the repository's current `lerna publish` pipeline, no.** Lerna 10 packs the package without applying pnpm's `publishConfig` manifest overrides. Removing `clean-package` while retaining Lerna would leave the source `.ts` import condition in the published tarball. Adding `publishConfig.exports` alone would be inert for this purpose.

This is an assessment, **not** a decision to migrate publication to pnpm or a claim that any package has already been migrated.

## Current release and resolution boundaries

- The root [release script](../../scripts/release.ts) calls `lerna publish <bump> --yes` for leaf packages, then separately calls `npm publish` for the root package. The root [package manifest](../../package.json) declares pnpm `11.5.2` and Lerna `^10.0.0`; the inspected installed Lerna version was `10.0.0`.
- The [Lerna package list](../../lerna.json) selects vendor modules/suites and CLI, framework, and utility packages. It is not the same as the [Vona](../../vona/pnpm-workspace.yaml) or [Zova](../../zova/pnpm-workspace.yaml) pnpm workspace membership. The root package is a separate source-distribution product with different inclusion rules ([root `.npmignore`](../../.npmignore)); changing local exports permanently to `dist` would break the local-source and root-source-distribution assumptions.
- The Vona boilerplate exports `types: ["./src/index.ts", "./dist/index.d.ts"]`, `import: "./src/index.ts"`, and `default: "./dist/index.js"`. Its `prepublishOnly` builds JS and declarations; `prepack` runs `clean-package`, and `postpack` restores the working manifest. The cleanup removes its own configuration, `devDependencies`, and `exports["."].import`, but **does not replace the backend `types` array**. Existing generated manifests, such as [demo-basic](../../vona/src/suite/a-demo/modules/demo-basic/package.json), contain their own copy of this policy; updating the generator does not update them.
- The [Zova module boilerplate](../../zova/packages-cli/cli-set-front/cli/templates/create/module/boilerplate/_package.json) also replaces `exports["."].types` with `./dist/index.d.ts`. Other packages can remove `require`, rewrite export subpaths, or rewrite CLI `bin` paths; see [Vona CLI](../../vona/packages-cli/cli/package.json) and [CLI Set API](../../vona/packages-cli/cli-set-api/package.json). Do not assume one universal publication manifest.
- Some packages deliberately retain `devDependencies`: [a-core](../../vona/src/suite-vendor/a-vona/modules/a-core/package.json) supplies `globalDependenciesDev` metadata that needs the dependency versions. Never apply blanket deletion across packages.

## Tool behavior verified for the pinned versions

| Pack/publish path | `publishConfig.exports` in tarball | Lifecycle / other relevant behavior |
| --- | --- | --- |
| `pnpm pack` / `pnpm publish` 11.5.2 | Supported: replaces the **whole** `exports` value, not a subpath or nested key. | Uses an exportable manifest; does not automatically remove `devDependencies`. `pnpm pack` runs `prepack`, `prepare`, `postpack`, but not `prepublishOnly`. Its default manifest processing omits publish lifecycle scripts and rewrites `workspace:` ranges. |
| `npm pack` / `npm publish` 11.6.1 | Not a general tarball-manifest override for `exports`; npm's `publishConfig` supplies publish settings. | `npm pack` runs `prepack`, `prepare`, `postpack`, not `prepublishOnly`. Do not use an npm tarball to validate pnpm's rewrite. |
| `lerna publish` 10.0.0 (current leaf path) | **Not applied**: Lerna packs the on-disk manifest with npm-packlist/tar after lifecycle hooks, then publishes that tarball via npm tooling. | In an isolated invocation of Lerna's publish pack helper, the order was `prepare`, `prepublishOnly`, `prepack`, `postpack`. Lerna's `npmClient` setting does not switch this pack engine to pnpm. |

The pnpm field-level replacement is visible in [pnpm 11.5.2's `overridePublishConfig` implementation](https://github.com/pnpm/pnpm/blob/v11.5.2/releasing/exportable-manifest/src/overridePublishConfig.ts#L5-L44); its [exportable-manifest implementation](https://github.com/pnpm/pnpm/blob/v11.5.2/releasing/exportable-manifest/src/index.ts#L35-L84) shows other publication transformations. Consult the [pnpm `publishConfig` reference](https://pnpm.io/package_json#publishconfig), but note that current online documentation can describe fields added *after* 11.5.2. Lerna [documents its npm-based publishing path](https://lerna.js.org/docs/features/version-and-publish#publishing-to-npm); the inspected [Lerna 10 pack implementation](https://github.com/lerna/lerna/blob/v10.0.0/libs/core/src/lib/pack-directory.ts) and [publish implementation](https://github.com/lerna/lerna/blob/v10.0.0/libs/core/src/lib/npm-publish.ts) distinguish it from pnpm's exportable-manifest path. See also [npm's lifecycle order](https://docs.npmjs.com/cli/v11/using-npm/scripts/#life-cycle-operation-order).

Isolated **local tarball tests**, with no registry publish, confirmed that pnpm 11.5.2 replaces the entire `exports` object but retains `devDependencies`, whereas Lerna 10 retains the original `exports` and `publishConfig` in the tarball when no cleanup hook is present. This does **not** constitute a successful end-to-end registry release test. Export maps govern entry resolution, not file inclusion: replacing an export does not itself remove files from the tarball.

## Refactor choices and recommended sequence

1. **Capture today's artifact contract before changing behavior.** Add isolated pack tests for a generated Vona module, a Zova module, a CLI package (including `bin` and subpaths), and a package that must retain `devDependencies`. Check the tarball's `package.json`, actual `dist` and declaration files, exported subpaths, local-source resolution before packing, and working-manifest restoration afterward. Exercise the *Lerna* pack path used by the release, not only `pnpm pack`; do not publish to a registry as part of an ordinary test. Test failure and interrupted-build recovery explicitly: Lerna invokes `postpack` after creating the tarball but does not wrap its pack operation in `finally`.
2. **For a small, safe cleanup, keep pack-time manifest transformation while Lerna is the publisher.** Consolidate repeated rules only if the artifact tests preserve each package's behavior. `publishConfig.exports` by itself is not a substitute in this path. Evaluate restoration on failure separately rather than assuming `postpack` always runs. Do not permanently replace checkout exports with `dist` imports.
3. **Only if eliminating `clean-package` is the goal, plan a separate pnpm publication migration.** Produce complete publish-time `exports` maps, including all existing subpaths (`"./package.json"`, wildcard exports, and special cases), and model publication-only `bin`, `types`, and other overrides per package. Preserve each package's intended `devDependencies` policy. A pnpm [`beforePacking` hook](https://pnpm.io/pnpmfile#hooksbeforepackingpkg-pkg--promisepkg) could implement the remaining manifest changes without editing checkout manifests, but runs only for pnpm's pack/publish path, not Lerna's.
4. **Retain release orchestration equivalence before switching commands.** `pnpm -r publish` is not a drop-in replacement for `lerna publish`: explicitly match Lerna's package allowlist, independent versioning, workspace dependency conversion, build lifecycle, tags/registry settings, ordering, and recovery behavior. Keep root `npm publish` separate unless deliberately redesigning the root source distribution. Compare old and new tarballs and perform a controlled publication rehearsal before removing the old hooks from templates and existing manifests.

The immediate recommendation is **artifact-contract tests first, no direct replacement of `clean-package` by `publishConfig` under Lerna**. Revisit the migration only with a concrete requirement to change the publication engine and a separately reviewed release plan.

## Validation boundary for this record

This evaluation inspected repository and installed-tool source and exercised disposable local pack fixtures using pnpm 11.5.2, npm 11.6.1, and Lerna 10.0.0. It did not generate modules, edit published manifests, run a full release, contact the registry, or validate every existing package's tarball. The tests and rollout gates above remain **proposed work**, not completed verification.
