## System Context

Language providers are ordinary suite modules whose static resources are interpreted by core registration. Vona owns backend text and localized backend metadata; Zova owns frontend text and runtime presentation. Neither stack sends an automatic authoritative language list to the other in current source. Configure each root explicitly and align the supported sets/default for a deployed paired application; do not invent a synchronization endpoint.

## Capability and Persistence Ownership

- **SRS-LOC-01**: Create paired `cabloy-locale` suites with `locale-jajp` and `locale-zhtw`, package names `vona-suite-cabloy-locale`, `zova-suite-cabloy-locale`, and matching `vona-module-locale-*` / `zova-module-locale-*` names. Backend providers declare `vonaModule.capabilities.locale: true`; frontend providers declare `zovaModule.capabilities.locale: true`. Regenerated module metadata must preserve the flag through existing discovery. Recheck name collisions before source creation. Add neither blanket target dependencies nor a new capability store. Traceability: `PRD-LOC-01`, `PRD-LOC-06`, `WBS-LOC-20-01`, `WBS-LOC-30-01`.
- **SRS-LOC-02**: Capability-marked providers author `src/locales/<locale>.ts` with `{ modules: { '<target-module>': flatDictionary } }` and, when needed, top-level global string entries. `src/locales/index.ts` exports a locale-code map named `localesProvider`, re-exported by the module's `src/index.ts`; core consumes `resource.localesProvider` only for locale-capability modules. Ordinary modules retain `resource.locales`. This separate static resource export, accepted by [ADR 0002](./decisions/0002-locale-provider-resource-export.md), is not a parallel registry or a public dynamic registration API. Central registration separates global strings from the `modules` envelope, registers module dictionaries under their target names, and never registers the envelope as a text key. Reuse existing registry helpers without parallel override stores or pack Monkey/Main mutation. Only provider resources get this interpretation; ordinary module semantics and project override behavior remain unchanged. Skip provider targets absent from the active metadata map, register present lazy targets without importing/installing them, and preserve stable module order for provider collisions. Scoped precedence is project target override > provider > ordinary target dictionary. Global collisions retain stable first-registration-wins behavior; scoped lookup still precedes global lookup. Traceability: `PRD-LOC-01`, `PRD-LOC-04`, `WBS-LOC-20-01`.

## Startup Contracts

- **SRS-LOC-03**: Zova must include locale-capability modules in startup resource import selection and complete provider installation/registration before the first preload installation. Retain monkey/sync and ordinary lazy-loading behavior; avoid classifying providers again as SSR remainder modules. System-level dictionaries are initialized once per Sys, not repeated in each SSR request/AppModule. Provider resources are data-only; do not add app-level provider lifecycle requirements. A preload consumer's supported module initialization sees provider translations, and a lazy target later merging its own dictionary cannot replace earlier provider values. Traceability: `PRD-LOC-03`, `WBS-LOC-20-01`.
- **SRS-LOC-04**: Vona registers project global/module overrides, then provider resources, then ordinary module resources inside its existing locale-loading phase. It remains eagerly loaded and retains the existing moduleLoading/config/locales/moduleLoaded lifecycle. Complete dictionaries are available at moduleLoaded and later supported consumers; do not promise dictionary availability in the earlier moduleLoading hook. Initialize application-owned maps without request-specific writes or cross-application mutation of imported provider source objects. Traceability: `PRD-LOC-03`, `WBS-LOC-20-01`.

## Language Policy Contracts

- **SRS-LOC-05**: Both roots expose `config.locale.items` as a locale-code-to-label-key subset map and `config.locale.default` as the sole configured default. Zova keeps storeKey and existing ancillary frontend fields. Add the Vona root type/default/config surface and migrate a-locale negotiation and existing default consumers away from dictionary-derived availability and module defaultLocale; keep protocol, cookie, and alias options in their existing owner. Do not retain competing defaults or silently consult an obsolete defaultLocale. Items use a subset-capable type such as `Partial<Record<keyof ILocaleRecord, string>>`; nonempty items and an included default are validated before active locale use. Provider installation must not mutate either setting. Resource absence is not a reason to reject an enabled locale. For the latest approved bilateral application delivery, set the existing Basic backend/frontend root items to exactly `en-us`, `zh-cn`, `ja-jp`, `zh-tw` with aligned default `en-us`, and verify the effective paired configuration proportionately at the approved locations under SRS-LOC-09. The four-language root enabled set and configured-default behavior remain unchanged by the latest placement correction under SRS-LOC-09. Retain existing framework policy proof; no business consumer or menu/route integration is required. Traceability: `PRD-LOC-02`, `WBS-LOC-20-01`, `WBS-LOC-40-01`.
- **SRS-LOC-06**: Resolve active language centrally on each stack: canonicalize supported input to lowercase hyphenated IDs, apply existing explicit aliases where applicable, accept only own enabled-item keys, and otherwise use the validated default. Cover request negotiation, direct current-locale assignment, cookies, saved user preference, SSR locale route input, and navigation restoration without changing authorization or the existing negotiation source order. Aliases cannot enable a disabled target. Web route-specific language menus may restrict but not expand the global set. For a matched locale-bearing route with disabled input, use the default's existing canonical URL policy so route state, SSR language, and client state agree; do not introduce aliases or new route identities. Preserve explicitly requested low-level translation lookup independently from current-language selection. Traceability: `PRD-LOC-02`, `WBS-LOC-20-01`.

## Lookup and Translation Contracts

- **SRS-LOC-07**: Preserve lookup order: target current language -> global current language -> target en-us -> global en-us -> original key, including explicit module-qualified lookups and existing interpolation/plural conventions. Configured default governs active-language selection, not missing-key fallback. Do not add implicit zh-tw-to-zh-cn fallback, blanket simplified-to-traditional conversion, or a new localeutil cache redesign. Project global defaults are not described as universal overrides of all scoped dictionaries. Traceability: `PRD-LOC-04`, `WBS-LOC-20-01`.
- **SRS-LOC-08**: Both providers supply translations for the release revision's authored locale-bearing module inventory, plus necessary backend core error/status messages, language display names, and existing schema label keys. Target dictionaries retain original message keys, placeholder names/counts, plural variants, and formatting tokens. Compose per-target files in `src/lib/locales`, and explicitly map language IDs through `src/locales/index.ts`; neither belongs to the ordinary nonrecursive `src/config/locale` scan. Do not treat helper names as locale IDs. Extend ILocaleRecord through authored exported declarations and adapt exhaustive locale maps to optional installed languages without forcing enablement. Record source inventory, exclusions with reasons, missing/extra keys, placeholder/plural checks, and attributed Japanese/Taiwan terminology review. Baseline estimates (~704 module entries per language plus core text) are sizing observations, never a completeness threshold. Coverage excludes generated bundles/dependencies and does not promise translation of arbitrary hard-coded or future module strings. Traceability: `PRD-LOC-01`, `PRD-LOC-05`, `WBS-LOC-30-01`.
- **SRS-LOC-09**: Configure the existing backend `vona/src/backend/config/config/config.ts` and frontend `zova/src/front/config/config/config.ts` roots with exactly `en-us`, `zh-cn`, `ja-jp`, `zh-tw`, retaining aligned baseline/fallback default `en-us` and the frontend's supported `APP_LOCALE_DEFAULT` override; no environment file is read or changed. The latest user correction supersedes project-monkey placement and the home-base byte-unchanged constraint. Extend the existing backend `vona/src/suite/a-home/modules/home-base/src/main.ts` and frontend `zova/src/suite/a-home/modules/home-base/src/main.ts` moduleLoaded hooks to register the complete factory map `{ 'en-us': en, 'zh-cn': zhCN, 'ja-jp': ja, 'zh-tw': zhTW }` through their existing `this.app.util.setLocaleErrors` adapters. Backend uses `this.app.config.locale.default`; frontend uses `this.sys.config.locale.default` only inside `process.env.CLIENT`, never during SSR. Registration replaces the map and is startup-only, never per request; do not add or retain project-monkey registration for this increment. Provider modules remain data-only: installation neither enables languages nor registers vendor validation. These placements and bounded WBS-LOC-40-01 execution are approved, not pending reconfirmation; prior project-monkey results are historical and corrected-placement ATP-LOC-03/07 proof requires rerun. Verify paired effective configuration and actual Zod mappings with existing supported scoped adapter/validation tests, retaining original-language/default controls. Guidance alone does not prove delivery. No business consumer, profile/flavor, runner expansion, schema/draft flow or SSR/browser acceptance is required. Language names remain available to home-base-scoped selectors with optional packs. Locale-reactive API/ModelResource schema ownership remains a framework safety constraint, not a business-flow acceptance gate. Do not restore a test-only policy switch, move registration into providers, duplicate schema metadata/business API owners or equate dictionary installation with vendor validation. Traceability: `PRD-LOC-03`, `PRD-LOC-05`, `WBS-LOC-40-01`, `WBS-LOC-50-01`.

## Generation and Development Contracts

- **SRS-LOC-10**: Keep ordinary Vona/Zova metadata generation unchanged: it scans `src/config/locale`, not provider `src/locales`. Provider language maps and the `localesProvider` entrypoint export are authored source and must survive normal metadata regeneration. A provider with only ja-jp or zh-tw is valid without a dummy English dictionary, a bogus `modules` message key, or provider-owned English-base scope/key/helper inference. Verify capability propagation, authored export preservation, generated scope/resource boundaries and typechecks; do not claim that ordinary generators discover provider dictionaries or have provider-specific inference. Ordinary target metadata/key inference remains unchanged. Use CLI-backed creation/dependency/metadata workflows; the existing `:init:locale` creates ordinary resources and is not a verified provider scaffolder. Preserve actual .ts/.tsx targets in Zova authored/generated application imports. Never hand-edit generated consumers or dependency files. Traceability: `PRD-LOC-06`, `WBS-LOC-20-01`.
- **SRS-LOC-11**: Vona's HMR override snapshot is captured after project and provider resources but before ordinary dictionaries, so reloading a normal target preserves provider precedence. Provider resource edits, including imported per-target helper changes and deleted contributions, must invalidate through existing complete worker reload/restart behavior rather than append-only stale merges; verify the watcher coverage during implementation. Frontend provider edits likewise use existing full reload/Sys reinitialization when incremental handling cannot remove stale keys safely. Do not add a generic ownership registry or incremental rebuild subsystem. Traceability: `PRD-LOC-06`, `WBS-LOC-30-02`.

## Tenant, Identity, Privacy, and Authorization Contracts

No new persistence or authorization boundary is created. Ordinary Vona instance scoping and existing Site admission remain server authoritative. A locale value may select text only; it cannot select an identity, tenant, module permission, or protected SSR data. Static dictionaries may be Sys/application shared; selected locale stays request/app scoped. Request/app isolation remains a framework safety constraint, not a requirement to establish a business consumer or demonstrate an SSR/concurrent-request business flow for current scope. Backend scoped validation tests own mockCtx/request boundaries as applicable; each intentionally competing operation uses a separate boundary, without process-global library-locale mutation. Do not persist user data in pack dictionaries or logs.

## Transactional, Concurrency, Idempotency, Audit, and Recovery Requirements

No new database writes, transactions, locks, idempotency keys, domain audit stream, or migration is justified. Registration must be deterministic and must not duplicate installation across capability stages. Reinitialization uses fresh registry state, not mutation of imported pack definitions. Existing lookup caches are not broadened in this feature; actual regressions discovered in supported flows require focused fixes rather than an unrelated cache project.

## API, DTO, OpenAPI, and Contract-Loop Contracts

No new endpoint or DTO is planned. Existing backend locale-aware schema output remains contract truth. Resource text changes alone do not justify new generated schema definitions. If implementation changes a backend contract, inspect emitted OpenAPI and use the forward contract-loop specialist to regenerate consumers; never patch generated consumers by hand.

## Frontend State, Route, Site, and SSR Contracts

Observed Basic `admin` / `web` Sites and `cabloyBasicAdmin` / `cabloyBasicWeb` flavors remain compatible existing hosts, not mandatory enabled-language consumer targets. Current delivery uses the approved existing root configs and home-base moduleLoaded registrations (frontend CLIENT-only) in SRS-LOC-09 on both stacks, without selecting a business flow or requiring page, schema/draft, SSR, hydration, navigation or browser integration acceptance. No new page, route name, alias, flavor, bundle identity, SSR profile or test runner is introduced. As framework safety, Web public/session and Admin admission contracts remain intact; app-scoped active locale remains reactive and shared registry registration stays independent of per-request current locale. Neutral SSR shells retain equivalent hydration-time content and must not query private/browser-only state early just to prove language support. These constraints do not reinstate a real-flow demonstration requirement.
