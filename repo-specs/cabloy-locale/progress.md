### Backend isolation conflict and recommended disposition

Backend [a-locale](../../vona/src/suite-vendor/a-vona/modules/a-locale/src/main.ts) resolves both assignment and negotiation against `ctx.app.config.locale`. A Commerce SSR Site and frontend flavor do not establish a separate backend policy. One Vona application cannot retain two-language Basic backend policy while independently enabling Commerce languages through this root-policy contract.

The existing Vona configuration selector uses `flavor` and `mode`, not a Commerce `appMode`. The authored backend config directory contains no Commerce layer. A proposed `vona/src/backend/config/config/config.commerce.ts` requires a **new backend flavor `commerce`**; this is not an existing selector or a rename that avoids the current PRD/ADR no-new-flavor exclusion. Shared root policy changes, request-time global Zod changes, a per-Site locale engine and a test-only enablement switch are not acceptable substitutes.

**Recommendation, not an accepted decision:** permit exactly one production-usable backend Commerce flavor/profile using the existing Vona mechanism, while retaining the existing Commerce frontend Site/flavor. Preserve normal Basic configuration and both home-base adapters byte-for-byte. Different backend policies require separate Basic-normal and Commerce application runs/processes; the Commerce backend policy applies to every Site/API hosted in its own process, not only `/commerce`.
