# Home User Account Settings Test Strategy and Acceptance Plan

## Purpose and Authority

This document defines the verification strategy, executable acceptance scenarios, evidence format, and release proof for Home User account settings. It completes the following planning traceability chain:

```text
PRD requirement -> SRS contract -> PDP/WBS task -> ATP scenario -> observed evidence
```

The [PRD](./prd.md) owns product outcomes and business acceptance; the [SRS](./srs.md) owns API, security, state, and SSR contracts; the [PDP/WBS](./pdp-wbs.md) owns delivery order. This plan specifies only how to prove them and cannot redefine any decision.

All `ATP-HUA-*` begin as planned/unverified. Planning documents are not implementation, test, or production evidence.

## Scope and Quality Priorities

This plan covers risks that cannot be accepted on the basis of manual page confidence:

1. The current Passport-only self-service identity scope and direct API authorization;
2. Profile-field allowlists, controlled avatar ownership, and Passport/preference synchronization;
3. Current-password validation, password policy, atomic change, and session invalidation for existing local-password users;
4. Restricted candidate binding of OAuth-only users’ explicit email input, existing-email matching, and eligibility to set the first password;
5. Purpose isolation, short lifetime, one-time use, and replay/expiry/race safety of `password-set`;
6. Security auditing, rate limiting, and red lines for password/token/identity data;
7. Web Account session SSR, anonymous route admission, and hydration equivalence;
8. Separation of Admin session SSR, Site admission, and Vona API authorization;
9. Shared Web/Admin capabilities, their respective navigation entry points, and independent form state;
10. Synchronization of Vona/OpenAPI/Zova generated contracts and paired SSR/REST artifacts.
11. Registration and Login, enumeration protection for anonymous reset requests, URL query token transport, credential replacement, session revocation, and reissue/consume races.

Email/mobile binding verification, address-level email-provenance migration, MFA, device/session-management UI, OAuth account management, administrators editing other accounts, and arbitrary external avatar URLs are outside the ATP scope of this delivery.

## Verification Model

### Narrow-Scope Verification

Prioritize the smallest backend module-local tests that own the changed invariants. Vona scoped tests must own `app.bean.executor.mockCtx(...)`; every intentionally competing caller runs in a separate `mockCtx(...)`. Race proof must explicitly run concurrent operations and assert the combined durable result; it must not rely on node:test runner parallelism or scheduling.

Each test deletes all test-persisted resources in `finally`, using precise owned identities and reverse dependency order. Shared seeds may only be created by the owning module’s `meta.version.ts` `seed()` and are treated as read-only by tests.

### Contract Verification

When changing Vona DTOs, controllers, or API schemas, establish backend contract truth first, inspect emitted OpenAPI, then generate Zova consumers. When changing shared Account Zova routes/metadata/pages/resources, build paired Web and Admin SSR/REST outputs, then run `npm run deps:vona`; REST output alone is insufficient proof of synchronization.

### Full Closure Verification

Before Phase 70, complete focused tests for every capability, OpenAPI/generation verification, Web/Admin SSR/hydration, Playwright browser acceptance journeys, type/lint/format checks, and required root checks. Direct API security acceptance must be independent of Playwright browser acceptance.

| Credential/token tests        | Password validation, hash update, session policy, token issue/consume/races      | Test directories of the ultimately selected `home-user`, `auth-simple`, and token-infrastructure modules |

The existing test-only activation endpoint may serve only as a controlled fixture-preparation aid; it is not an acceptance substitute for the production Account Settings API, password policy, or email/token flows.

## Fixture and Data-Handling Rules

### Minimum Fixture Set

Every applicable test combination prepares at least:

- Current account A: a usable user with `auth-simple`;
- Current account B: an OAuth-only user with a nonempty, synthetic `EntityUser.email`, for existing-address normalization match/mismatch;
- Current account C: an OAuth-only user without `EntityUser.email`, for a short-lived token-bound candidate and binding upon successful consumption;
- Another user in the same instance and, where necessary, a user in another instance, for ownership/isolation negative tests;
- An Admin Site-admitted user and a Web Site-admitted user;
- Synthetic `password-set` token states that are valid, expired, consumed, wrong-purpose, superseded, and concurrently consumed, as well as states in which the candidate is already owned by another current-instance user or the account email changes after issuance;
- Avatar-reference states that are owned, external/unowned, invalid type, and invalid size (depending on the selected media-test mechanism).

### Evidence and Sensitive Data

Every accepted ATP records:

- PRD, SRS, WBS, and ATP references;
- Source revision, database, flavor/Site;
- Exact command, fixture, and concurrency-interleaving description;
- Pass/fail result and retained log, response, screenshot, or artifact location;
- Output containing only synthetic or redacted data;
- Owner, reason, and expiry date of any temporary waiver.

Plaintext passwords, password hashes, raw tokens, usable email links, complete sensitive email addresses, real identity data, authentication-internal IDs, and unapproved security logs must not be retained. An expired waiver is a release blocker.

## Contract, SSR, and Browser Verification Procedure

During implementation, select the narrowest meaningful check according to the WBS, then expand in Phase 70:

```bash
# Discover/run final Vona module-local tests that own Account invariants
npm run vona -- :bin:test -- <selected-home-user-and-auth-tests> --flavor=normal

# After Vona Account DTO/controller changes: inspect emitted OpenAPI, then generate expected Home API consumers
npm run zova :openapi:generate home-api

# After shared Web/Admin frontend route, metadata, page, or resource changes: paired artifacts for both flavors, then synchronize Vona
npm run build:zova:web
npm run build:zova:admin
npm run deps:vona

# Closure checks; run as applicable to the change and environment
npm run tsc
npm run lint
npm run format
npm run test
npm run test:e2e home-user-account -- --grep @account
```

Any `meta.version.ts` modification requires `npm run test`. Test tags must include at least `@account`, plus either `@web` or `@admin`; tagged E2E is created and run only after the corresponding product implementation exists.

This is an internal planning-document change only. Generation, builds, dependency synchronization, E2E, and broad code tests are not run. They are commands for future WBS implementation gates, not evidence for this documentation change.

## Release Closure Gate

This delivery may be released only after all of the following are satisfied:

- Every applicable `PRD-*`, `SRS-*`, and `WBS-HUA-*` has one or more passing `ATP-HUA-*` evidence items;
- Every direct API, token race, session policy, audit/red-line, Web SSR/hydration, Admin SSR, Web/Admin navigation, and generated-contract path is proven separately;
- No expired waiver or unexplained generated/type/SSR artifact drift exists;
- Retained evidence uses only synthetic/redacted data and includes revision, environment, command, and result;
- Public registration and password-reset contracts, backend race tests, and frontend/browser ATPs each retain evidence under their respective requirement IDs; address-level email provenance remains future hardening scope.
