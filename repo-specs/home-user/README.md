# Home User Account Settings Internal Planning

This directory records the product, technical, delivery, and acceptance baselines for `home-user` account settings. It is internal planning material for maintainers, not end-user product documentation.

## Reading Order

1. The [Product Requirements Document](./prd.md) defines user outcomes, scope, business rules, and product acceptance.
2. The [Software Requirements Specification](./srs.md) defines the self-service account API/DTOs, authentication and tokens, sessions, auditing, SSR, frontend state, and technical acceptance contracts.
3. The [Product Delivery Plan and Work Breakdown Structure](./pdp-wbs.md) defines dependency order, implementation tasks, and completion checks.
4. The [Test Strategy and Acceptance Plan](./test-plan.md) defines `ATP-HUA-*` scenarios, evidence formats, and release proof.
5. [Delivery Progress](./progress.md) records derived implementation status, evidence, blockers, and the next proof; it does not redefine requirements or contracts.
6. [ADR 0001: Establish Account Settings Boundaries](./decisions/0001-account-settings-boundaries.md) records the persistent domain and security boundaries for this capability.

Current source contains the Account controller/page, Web/Admin entries, local password change, first-password setup, registration, and signed-out password recovery. This is implementation presence, not full contract acceptance: controlled avatar ownership, profile-update audit/rate limiting, reset `activated` eligibility, and the post-commit password-change revocation/audit failure boundary remain open. The legacy password-reset callback does not participate in the Account recovery flow. Historical tests and their limited applicability are indexed in [progress](./progress.md); no task is currently `verified`.

## Current Ownership and Runtime Topology

- Vona `home-user` owns Passport-oriented registration, login, OAuth, current-identity interfaces, and a dedicated Account controller/service/DTO surface for self-service; that surface requires the remaining security and acceptance work described in the SRS.
- Zova `home-passport` owns Passport/JWT state and runtime preference synchronization; Account profile changes must synchronize it through the SRS projection/refresh contract.
- `home-layoutadmin` owns the Admin avatar-menu Account entry and `home-layoutweb` owns a separate Web user entry. Neither owns the account domain or self-service API; browser evidence for one Site does not automatically prove the other.
- Account is an authentication-protected session-SSR route; its static canonical entry point is `/home/user/account`, with no route name or alias. Public Login/registration/reset and password-set/reset token pages use a token-free neutral shell under public SSR; the absence of locale params does not itself change that choice. Site admission, SSR rendering, and Vona API authorization are responsibilities of different layers.

## Document Authority

- The PRD owns product objectives, scope, business rules, and product acceptance.
- The SRS owns API/DTO, authentication, tokens, sessions, auditing, state, SSR, frontend ownership, and technical acceptance contracts.
- The PDP/WBS owns delivery order, dependencies, and implementation completion checks.
- The test plan owns executable acceptance scenarios, evidence formats, and release proof.
- The progress register owns only the status and evidence index; it does not rewrite the PRD, SRS, WBS, or test procedure.
- ADRs own architecture, scope, and trade-off decisions that should remain in force across phases.

When documents conflict, first update the authoritative document that owns the relevant type of fact, then update all downstream references and derived status.

## Traceability Chain and Status Rules

```text
PRD requirement -> SRS contract -> PDP/WBS task -> ATP scenario -> observed evidence
```

Formal exact-ID `Traceability:` links live with their PRD/SRS/WBS declarations; family and range matrices summarize rather than prove atomic coverage. Every `verified` status must have traceable `ATP-HUA-*` evidence for the applicable source revision, environment, exact procedure, result, and durable redacted artifact location. A static spec audit or generated chart neither verifies implementation nor accepts an ADR. Every temporary waiver must include an owner, reason, and expiry date; an expired waiver is a release blocker. Phase 70 release closure follows Phase 80 registration/reset and remains open.
