Current statuses reconcile the WBS completion checks with the present source and available historical evidence; no implementation or ATP was executed during this review. Historical focused passes do not prove current-revision acceptance: the records lack a source revision, environment, and durable redacted artifact location. Release remains open, and no task is `verified`.

## Status Definitions

| Status                    | Meaning                                                                                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `not-started`             | Defined, but implementation or verification has not started.                                                                                |
| `in-progress`             | Under implementation or verification and does not yet meet its completion criteria.                                                         |
| `implementation-complete` | The implementation task is complete, but all required ATP evidence is not yet available.                                                    |
| `verified`                | The corresponding ATP has passed, with evidence that includes the revision, environment, command, result, and a redacted artifact location. |
| `blocked`                 | An unresolved external dependency, decision, or failed verification prevents further closure.                                               |
| `deferred`                | Out of scope for the current delivery after documentation; it is not complete.                                                              |

`verified` cannot be obtained through code reading, a manual UI demonstration, planning files, or a single browser screenshot. Every status change must update its WBS, ATP, and evidence links together. Every waiver requires an owner, reason, and expiry date; an expired waiver automatically becomes `blocked`.

## Update Rules and Next Steps

1. Retain `EVD-HUA-E2E-03` for its dated Account/Login admission, registration activation-pending, authenticated Web menu, profile/menu and draft-isolation, session-SSR/hydration, and Admin navigation observations; only its fragment token-transport conclusion is superseded. `EVD-HUA-E2E-04` reports eight Web-tagged query-transport tests, not Admin coverage or successful real-token consumption. The historical notes describe controlled, newly registered and activated synthetic users for self-service writes; they are not current-revision ATP artifacts.
2. Retain `mockCtx(...)` race tests, `finally` cleanup, and redacted artifacts for every security state transition not independently closed before marking it `verified`.
3. A browser regression for a real reset token must first establish a trace/artifact-redaction strategy; until then, Vona tests continue to prove the real lifecycle while the browser uses only synthetic, unusable query values. Usable tokens or complete sensitive email must likewise not be retained.
4. Add independent ATPs for reset expiry, recipient cooldown, `kickOut` server-token revocation, and serialization of reset with authenticated password change; these outstanding evidence items must not be marked `verified` just because the focused suite has passed.
5. If a persisted schema change is introduced in the future, first ask whether `vonaModule.fileVersion` should be incremented; no full `npm run test` triggered by a `meta.version.ts` change is required in this delivery.
6. Retain the Web/Admin reverse chain: after every frontend change that affects both flavors, run `npm run build:zova:web`, `npm run build:zova:admin`, and `npm run deps:vona`.
