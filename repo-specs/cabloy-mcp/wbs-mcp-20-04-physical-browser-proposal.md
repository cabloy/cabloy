# WBS-MCP-20-04 Database-Neutral State and Zova Authorization Proposal

## Status and decision boundary

**Database-neutral atomic-commit and Zova presentation directions selected; physical state and interaction proposal unaccepted, not execution-ready or runtime proof.** This record initially explored a multi-record state representation and AS backend HTML. [ADR 0009](./decisions/0009-mcp-as-state-boundary.md) supersedes the HTML direction and, as clarified on 2026-10-11, does not require an explicit multi-statement transaction by default; it **retains the requirement that code consumption and resulting token activation share one atomic commit**. The integrated `a-auth` logical AS retains server-side grant and issuance authority, with `zhennann` responsible for implementation and operations. No database brand, deployed dialect/topology, physical representation, client registry, Zova site/flavor, admission contract, session/CSRF implementation, lifetimes, migration or `fileVersion` has been approved. This document offers candidates for later review, not an implementation disposition.

No AS source, schema, UI, credentials, issuer configuration, runtime ATP or evidence is created. `WBS-MCP-20-04` and dependent `WBS-MCP-20-02` stay `blocked`; `ATP-MCP-AUTH-03` remains prospective. The [execution dossier](./wbs-mcp-20-04-execution-dossier.md) remains unapproved. The selected first profile still uses pre-registered public/confidential clients, Authorization Code + explicit PKCE S256, short-lived MCP-only opaque access tokens with current lookup, explicit per-request approval or denial, and no refresh issuance or remembered consent.

## Observed constraints (not endorsements of a candidate)

- Existing `a-auth` has `fileVersion: 1` in [`package.json`](../../vona/src/suite-vendor/a-auth/modules/a-auth/package.json); [`meta.version.ts`](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/bean/meta.version.ts) version 1 creates only `aAuth` and `aAuthProvider`. The [version runner](../../vona/src/suite-vendor/a-vona/modules/a-version/src/service/version.ts) applies later versions on existing installations. Merely adding tables to version 1 would not migrate an existing installation. A new version is a candidate, **not** a `fileVersion` decision.
- [Backend database configuration](../../vona/src/backend/config/config/config.ts) supports SQLite, PostgreSQL and MySQL; source defaults do not establish the deployed dialect. Model operations use `database.current` and [apply the selected instance](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_meta.ts) only after trusted admission. An incorrectly selected instance remains an authorization defect.
- [`getForUpdate`](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_cache.ts) requires an active transaction, bypasses model caches and returns only one match. Cached [model `update()`](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_cache.ts) can replace a state/version predicate with selected IDs; the underlying [mutation](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_crud_inner.ts) returns data rather than an affected-row count. Ordinary `model.update()` is not a proven conditional transition. [`REQUIRED` transactions](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/service/transaction_.ts) join ambient transactions without upgrading isolation; post-commit callback failure does not roll back a committed grant.
- Existing [`a-auth` provider callback](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/controller/passport.ts) handles **upstream provider login**, not MCP authorization. Its [continuation handling](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/service/auth.ts) is not exact registered-client redirect validation. The development [`mock` authorize form](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/controller/mock.ts) is not production consent, redirect validation, CSRF or issuance. [ADR 0004](./decisions/0004-mcp-host-instance-binding.md)'s proposed `/mcp` admission does not cover every AS route.
- Zova's client-managed token cookie is **not** an HttpOnly AS session; the backend [JWT extractor](../../vona/src/suite-vendor/a-vona/modules/a-jwt/src/service/jwtExtract.ts) does not authenticate requests from that cookie. The [global CSRF assertion](../../vona/src/suite-vendor/a-vona/modules/a-security/src/lib/middlewares/csrf.ts) is disabled. The [listener](../../vona/src/suite-vendor/a-vona/modules/a-web/src/bean/startup.listen.ts) enters `newCtx` before system middleware; the [instance resolver](../../vona/src/suite-vendor/a-vona/modules/a-instance/src/main.ts) can choose query/header/subdomain selectors before a route or Zova guard acts. An AS decision API needs a reviewed, server-verifiable identity, request binding, CSRF and early-instance admission contract.

## Database-neutral logical authority (representation requires approval)

**Selected design direction:** one AS-owned database-backed authority, without selecting a database product or defaulting to an explicit multi-statement transaction. All AS workers and the RS lookup must observe authoritative current state or fail closed. The MCP resource module remains schema-free. The supported deployed dialect, datasource, topology, atomic mutation semantics, uniqueness and migration path require separate approval and proof. A state model and its transaction, if used, must share the verified datasource/context.

A _single authoritative authorization aggregate_ is the preferred **candidate to evaluate**, not an approved table design: it would retain immutable pending/client/redirect/resource/instance/scope/PKCE and approved subject bindings, one code digest, token digest and active/revoked state, terminal decision and absolute expiries. Approval/code assignment and code consumption/token activation could each be one conditional mutation **only if** the actual dialect, affected-row count, digest lookup uniqueness, cache bypass, worker concurrency and revocation ordering prove the accepted invariant. A multi-record pending/grant/token design remains a candidate where required, but a transaction or equally proven single atomic commit must cover code consumption and token activation; consuming a code before writing a token is **not** an approved shortcut. A one-statement solution still relies on database atomicity and is not a promise of portability across drivers.

**Portable invariant, not a lock recipe:** each pending request reaches one terminal approve/deny/cancel/expiry outcome; an approved request yields at most one redeemable code; a code activates at most one token in **the same atomic commit** that consumes it. Failed verifier/client/resource checks activate nothing; competing redemption/revocation must not result in a usable token outside the bound grant. A committed token followed by a lost HTTP response remains issued and is not reissued on replay. Current lookup verifies issuer, client, subject, canonical resource, instance, scope, absolute expiry and grant/token revocation, and denies when authoritative state is unavailable or ambiguous. Cleanup is not authorization.

For any candidate, specify trusted tenant scoping after early admission, creation-time tenant-aware uniqueness, digest algorithm/key custody, collision/ambiguous-lookup rejection, clock source, retention and redaction before DDL. In shared-database multitenancy do not use `table.unique(...)` for business uniqueness: enforce instance-aware uniqueness in the business layer with a dialect-validated strategy and ordinary supporting indexes. A compare-and-set on an existing row does not prevent duplicate creation. A [scoped Knex builder](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_knex.ts) may retain transition predicates and expose affected-row counts, but its instance scope, cache/write side effects and secret-safe logging must be reviewed; it is not approved source guidance. SQLite `forUpdate()` is not PostgreSQL row-lock proof; no dialect's migration atomicity or stale replica behavior is presumed for another. The existing auth tables/Redis session marker are not the new opaque-token/grant authority. Redis-only or split SQL/Redis authority would require a new decision.

**Unselected values:** physical store/dialect and migration/partial recovery; request, code and access-token lifetimes; cleanup and retention; client registration/secret custody and policy rollout; worker/replica topology; invalid-attempt policy; revocation triggers and incident response. Illustrative lifetime numbers are not approved defaults. Review cache invalidation/queue dependencies even if token reads bypass a cache; deny on authoritative-store outage rather than falling back to process-local or Redis token acceptance.

## Candidate Zova browser and protocol interaction (requires approval)

1. **Admit before instance initialization.** The AS validates issuer, registered client and exact redirect, one canonical registered MCP resource, explicit S256 challenge, scope and client compatibility. Resolve the resource through a trusted AS/deployment resource-to-enabled-instance map before generic query/header/subdomain instance selection or `initInstance()`; bind the result to server-held pending state. Authorization entry, page/resume, login bridge, summary/decision APIs, token and discovery routes each need their own early admission disposition. A route guard cannot undo earlier instance selection; ADR 0004's `/mcp` hook does not prove this AS path. Token exchange independently resolves the submitted canonical resource before scoped code lookup and checks the immutable bound client/resource/instance relation. RS token lookup first uses trusted `/mcp` endpoint-to-instance binding, then verifies the returned immutable relation; no raw cross-instance probe explains a miss.
2. **Create server-held pending truth.** Validate client/redirect/resource before creating a one-use pending request. Browser correlation uses an opaque, short-lived, browser-bound reference, separate from client OAuth `state`, upstream-login state, decision CSRF and PKCE. Invalid client/redirect failures terminate locally, never redirecting to an unvalidated URI. Zova receives only a minimal display projection; it does not choose or return authoritative client, redirect, scope or resource values. Never place code, verifier, access token, client secret or complete subject data into a URL, rendered page, query cache, browser persistence, telemetry or logs.
3. **Present and resume with Zova; AS authenticates.** The selected presentation direction is a thin Zova authorization page with explicit approve/deny for this request, not an Admin management page or a new MCP resource frontend. Existing Web hosting is a _candidate only_: protected Web and Admin pages have site admission rules, so confirm the authorizing population before deciding Web/Admin/new site, route or flavor. The AS must verify current account, pending/browser/instance continuity and expiry via a reviewed server-authenticated session or login bridge; a client-written cookie, frontend authentication flag, upstream callback state or pending handle alone is not identity proof. A login continuation must be fixed and internal with an opaque pending reference, never an arbitrary `returnTo` or the client's OAuth `state`. For SSR, select a privacy-aware session/admission profile, maintain server/hydration initial-render equivalence and keep private pending data out of unintended hydration/persistence; a neutral shell with post-admission load is a candidate, not an approved implementation.
4. **Approve or deny exactly once.** A same-origin, request-bound decision POST includes an independent CSRF proof. The AS revalidates identity, account activation, site/instance admission, client/resource/redirect policy, scope, pending expiry and browser correlation immediately before the single-use transition. Missing/invalid CSRF, hostile origin, stale tab, switched account, expired session and concurrent/duplicate submission fail closed or restart with a fresh request; denial issues no code. Treat the existing disabled CSRF assertion as absent. Apply escaped display, frame protection and no-store/no-referrer/error/redirect response protections to the entire interaction. A JSON/AJAX redirect is not by itself top-level browser navigation: the AS alone constructs the final redirect to the **previously validated bound URI**, with appropriate error/state where allowed, and the navigation mechanism needs explicit design. Never return an MCP code as reusable query state.
5. **Redeem under the bound client/resource.** Require the same canonical `resource` at authorization and token exchange as a stricter local rule than RFC 8707's general subset rule; invalid resource targets use `invalid_target`. Enforce S256 verifier and confidential-client authentication where applicable. OAuth 2.1 draft-13 §10.2 does not universally require token-request `redirect_uri`; if an OAuth 2.0 compatibility branch is explicitly supported, require the identical value under RFC 6749 §4.1.3. Select and test one branch per client profile. If RFC 9207 `iss` is selected, emit it on every redirectable success **and error**, matching advertised metadata; otherwise review mix-up defense and do not advertise unsupported `iss`. Omitted PKCE challenge method defaults to `plain` under RFC 7636 and is rejected by the S256-only profile. Do not advertise refresh or Dynamic Client Registration when unimplemented.

The Zova page's owner, actual site/flavor, admission and account population, early AS ingress map, session/CSRF mechanism, SSR privacy, login continuation, exact routes and redirects, OAuth compatibility and response policy remain **unselected**. A plain browser form POST is not automatically authenticated by the Zova cookie; an AJAX decision is not automatically a browser redirect. The selected presentation does not transfer authority from AS to Zova or authorize a general OAuth console, independent site, source code or live provider integration.

## Separate decisions and prospective proof

1. **Physical authority:** approve a database product/dialect, datasource and topology only at execution design; prove the concrete single-aggregate conditional mutation or a multi-record transaction, affected-row and creation-time uniqueness behavior, same-commit redemption/activation, fresh/existing install migration, partial recovery and current lookup with the actual dialect. Select an owning AS module/service, client-registration approach and secret custody. Do not alter the deployment database client to fit planning.
2. **State contract:** review state shape, instance scope, concurrent decisions/redemption/revocation, digest and lifetime policy, invalid attempts, lost response and cleanup. Before **any persisted field/schema edit**, ask whether the owning `vonaModule.fileVersion` will increment; do not select or edit it from this proposal. A separately approved `meta.version.ts` edit requires root `npm run test`.
3. **Browser and protocol:** select Zova site/admission, an AS pre-instance ingress contract, server-verifiable identity/session or login bridge, request-bound CSRF, SSR privacy, exact routes and redirect behavior, client/redirect/issuer policy and supported OAuth branch. Prove AS and RS instance/resource maps align rather than treating ADR 0004's `/mcp` hook as AS proof.
4. **Then, and only then:** re-review the blocked [AS execution dossier](./wbs-mcp-20-04-execution-dossier.md) for bounded execution approval before source/configuration/tests. Prospective `ATP-MCP-AUTH-03` must prove competing decisions/redemptions in separate Vona contexts and their combined durable outcome, current multi-worker/revocation/outage behavior, and real HTTP Zova SSR/hydration, login continuation, two-instance/account admission, CSRF, invalid redirects and response secrecy on the actual chosen deployment. Tests on one dialect do not prove another. Keep `WBS-MCP-20-02` and `ATP-MCP-AUTH-01` separate.
