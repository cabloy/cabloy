# WBS-MCP-20-04 Database-Neutral State and Zova Authorization Proposal

## Status and decision boundary

**Database-neutral atomic-commit and Zova presentation directions selected; physical state and interaction proposal unaccepted, not execution-ready or runtime proof.** This record initially explored a multi-record state representation and AS backend HTML. [ADR 0009](./decisions/0009-mcp-as-state-boundary.md) supersedes the HTML direction and, as clarified on 2026-10-11, does not require an explicit multi-statement transaction by default; it **retains the requirement that code consumption and resulting token activation share one atomic commit**. The integrated `a-auth` logical AS retains server-side grant and issuance authority, with `zhennann` responsible for implementation and operations. At this historical proposal stage, no database brand or deployed dialect/topology was selected. The later [ADR 0009](./decisions/0009-mcp-as-state-boundary.md) records SQLite via `better-sqlite3` on Vona's existing primary datasource as the first AS implementation target, not an observed deployed configuration or atomicity proof. Physical representation, client registry, Zova site/flavor, admission contract, session/CSRF implementation, lifetimes and migration/check implementation remain unapproved; the later installation-scope disposition is recorded below. The later 2026-10-15 inputs select same-host multiple Vona workers sharing persistent SQLite and, conditionally on persistence in existing `a-auth`, keeping `fileVersion: 1` and folding schema into version 1's creation path. Already-recorded v1 databases do not automatically upgrade; no version-2 migration, cross-host SQLite or replica support is selected. This document offers candidates for later review, not an implementation disposition.

No AS source, schema, UI, credentials, issuer configuration, runtime ATP or evidence is created. `WBS-MCP-20-04` and dependent `WBS-MCP-20-02` stay `blocked`; `ATP-MCP-AUTH-03` remains prospective. The [execution dossier](./wbs-mcp-20-04-execution-dossier.md) remains unapproved. The selected first profile still uses pre-registered public/confidential clients, Authorization Code + explicit PKCE S256, short-lived MCP-only opaque access tokens with current lookup, explicit per-request approval or denial, and no refresh issuance or remembered consent.

### Later installation and deployment-requirements disposition (2026-10-15)

The later bounded design approval in [ADR 0009](./decisions/0009-mcp-as-state-boundary.md) and [concrete dossier §9.2](./wbs-mcp-20-04-as-contract-dossier.md#92-installation-applicability-accepted-bounded-design-only) accepts fresh physical-database/v1 creation only under the conditional existing-`a-auth` keep-v1 strategy. Existing-v1 upgrade/adoption, existing objects with missing history, and partial/unknown states are excluded or blocked pending separate treatment. Shared instances share the physical database's schema-update history; a new shared instance does not create a fresh schema-installation path. The secret-free deployment-confirmation requirements in concrete dossier §§9.3–9.4 are accepted, but **all deployment observations remain unconfirmed** and no actual installation is classified. The same-host shared persistent SQLite inputs and conditional keep-v1 strategy are unchanged. No schema/source, concrete precondition/check mechanics, connection settings, browser contracts, execution or runtime proof is approved by this later disposition. Historical candidates below do not reopen the accepted installation scope/exclusions.

### Later owner, lifecycle and activation disposition (2026-10-15; bounded design only)

After separate candidate preparation, [ADR 0009](./decisions/0009-mcp-as-state-boundary.md), SRS-MCP-AUTH-04 and [concrete dossier sections 9.5–9.8](./wbs-mcp-20-04-as-contract-dossier.md#95-owner-and-runtime-boundary-bounded-design-accepted) record acceptance of four bounded rows: existing-`a-auth` physical persistence and dedicated service-scene authorization/readiness responsibilities; one logical aggregate/lifecycle; layered read-only activation responsibilities/timing; and only verifiable continuity of the same approved fresh-v1 installation across restart. This supersedes historical open-owner/logical-lifecycle/check-responsibility wording below only at that bounded level, satisfies the existing conditional keep-v1 owner premise, and does not admit arbitrary existing-v1 installations. Exact source targets/dependencies, schema/DDL, SQL/cache/transaction/credential/connection mechanisms, provenance producer/integrity/binding/retention/restart verification, check hooks/reuse/coherence and remaining browser/protocol/ingress contracts remain gated. All deployment observations remain unconfirmed; no actual installation qualifies. WBS-MCP-20-04 and WBS-MCP-20-02 remain blocked, ATP-MCP-AUTH-03 prospective, with no source, deployment inspection, execution or runtime approval.

## Observed constraints (not endorsements of a candidate)

- Existing `a-auth` has `fileVersion: 1` in [`package.json`](../../vona/src/suite-vendor/a-auth/modules/a-auth/package.json); [`meta.version.ts`](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/bean/meta.version.ts) version 1 creates only `aAuth` and `aAuthProvider`. The [version runner](../../vona/src/suite-vendor/a-vona/modules/a-version/src/service/version.ts) applies later versions on existing installations. Merely adding tables to version 1 would not migrate an existing installation. A new version is a candidate, **not** a `fileVersion` decision.
- [Backend database configuration](../../vona/src/backend/config/config/config.ts) supports SQLite, PostgreSQL and MySQL; source defaults do not establish the deployed dialect. Model operations use `database.current` and [apply the selected instance](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_meta.ts) only after trusted admission. An incorrectly selected instance remains an authorization defect.
- [`getForUpdate`](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_cache.ts) requires an active transaction, bypasses model caches and returns only one match. Cached [model `update()`](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_cache.ts) can replace a state/version predicate with selected IDs; the underlying [mutation](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_crud_inner.ts) returns data rather than an affected-row count. Ordinary `model.update()` is not a proven conditional transition. [`REQUIRED` transactions](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/service/transaction_.ts) join ambient transactions without upgrading isolation; post-commit callback failure does not roll back a committed grant.
- Existing [`a-auth` provider callback](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/controller/passport.ts) handles **upstream provider login**, not MCP authorization. Its [continuation handling](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/service/auth.ts) is not exact registered-client redirect validation. The development [`mock` authorize form](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/controller/mock.ts) is not production consent, redirect validation, CSRF or issuance. [ADR 0004](./decisions/0004-mcp-host-instance-binding.md)'s proposed `/mcp` admission does not cover every AS route.
- Zova's client-managed token cookie is **not** an HttpOnly AS session; the backend [JWT extractor](../../vona/src/suite-vendor/a-vona/modules/a-jwt/src/service/jwtExtract.ts) does not authenticate requests from that cookie. The [global CSRF assertion](../../vona/src/suite-vendor/a-vona/modules/a-security/src/lib/middlewares/csrf.ts) is disabled. The [listener](../../vona/src/suite-vendor/a-vona/modules/a-web/src/bean/startup.listen.ts) enters `newCtx` before system middleware; the [instance resolver](../../vona/src/suite-vendor/a-vona/modules/a-instance/src/main.ts) can choose query/header/subdomain selectors before a route or Zova guard acts. An AS decision API needs a reviewed, server-verifiable identity, request binding, CSRF and early-instance admission contract.

## Database-neutral logical authority (representation requires approval)

**Originally selected design direction:** one AS-owned database-backed authority, without initially selecting a database product or defaulting to an explicit multi-statement transaction. The subsequent first implementation target is SQLite via `better-sqlite3` on Vona's existing primary datasource. All AS workers and the RS lookup must observe authoritative current state or fail closed. The MCP resource module remains schema-free. Actual deployment alignment and worker count/connection policy within the later-selected same-host multi-worker shared-SQLite topology, SQLite atomic mutation semantics, uniqueness and migration path require separate approval and proof; this target does not select PostgreSQL/MySQL AS support. A state model and its transaction, if used, must share the verified datasource/context.

A _single authoritative authorization aggregate_ is the preferred **candidate to evaluate**, not an approved table design: it would retain immutable pending/client/redirect/resource/instance/scope/PKCE and approved subject bindings, one code digest, token digest and active/revoked state, terminal decision and absolute expiries. Approval/code assignment and code consumption/token activation could each be one conditional mutation **only if** the actual dialect, affected-row count, credential lookup, cache bypass, worker concurrency and revocation ordering prove the accepted invariant. A multi-record pending/grant/token design remains a candidate where required, but a transaction or equally proven single atomic commit must cover code consumption and token activation; consuming a code before writing a token is **not** an approved shortcut. A one-statement solution still relies on database atomicity and is not a promise of portability across drivers.

### Reviewable state-transition candidate — not selected DDL

| Transition     | Candidate server-side preconditions and one-commit effect                                                                                                                                                                                                                                                                                                                                                                                                                                         | Reject/race outcome to prove                                                                                                                                                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create pending | After trusted early instance admission and registered client, redirect, resource-to-enabled-instance, scope and explicit S256 validation, create one AS-owned pending aggregate bound to immutable issuer/client/redirect/resource/instance/challenge and absolute expiry. Browser correlation is separate from client OAuth `state`.                                                                                                                                                             | An untrusted selector, duplicate/colliding locator, disabled instance or partial insert cannot create an ambiguous usable request; creation-time uniqueness is a separate invariant from later CAS.                                                                     |
| Decide         | For one currently authenticated, admitted, browser-correlated subject, conditionally move a live pending request to **approved/code-ready** (record bound subject, approved scope and code digest) or **denied/cancelled**. Expiry is enforced in predicates/current reads even before cleanup.                                                                                                                                                                                                   | Duplicate, competing approve/deny, expiry, changed account or stale browser identity yields one terminal result and at most one code. A second request needs its own new decision, never remembered consent.                                                            |
| Redeem         | With verified client, code secret, S256 verifier, canonical `resource`, bound instance, approved scope and applicable redirect profile, conditionally move **code-ready → code-consumed/token-active** in **one committed mutation**, setting consumption time, fresh token digest, token absolute expiry and active state together. Generate the raw candidate token in memory first; release it **only to the winning request after confirmed commit**, and do not retain it in authority/logs. | Affected-row result must prove exactly one winner. Failed checks or mutation activate nothing; collision, ambiguous lookup, revocation, retry and replay issue no second usable token. A lost response after commit is not a reason to reveal/reissue the stored token. |
| Revoke/read    | Make revocation monotonic and effective on the same authority; current lookup verifies issuer, MCP profile, bound client/subject/resource/instance/scope, grant and token state and absolute expiry.                                                                                                                                                                                                                                                                                              | Redemption racing revocation cannot produce a token accepted after revocation; lookup on stale replica/cache/worker, missing/ambiguous state or outage denies. Define account/client/resource disablement and cleanup separately.                                       |

**Credential lookup variant requiring disposition:** Instead of a global digest-only business key, an opaque code/token could carry a non-authoritative aggregate locator plus a high-entropy secret; the AS first establishes the trusted instance/resource, then selects exactly `(instance, aggregate locator, credential kind)` and compares the secret digest. A primary row identity is only a locator, **not** a claim that client-selected identifiers or tenant business keys are unique or authorized. Approve the wire format, secret/digest custody, enumeration resistance, identifier scope and current RS lookup contract before using this variant. A pure digest lookup instead needs a separately proven instance-aware creation-time uniqueness and ambiguity strategy. Random generation plus preflight lookup or a later compare-and-set is not atomic uniqueness proof; where creation needs serialization or multiple writes, explicitly approve a short atomic creation boundary even if redemption uses one statement. Do not infer that the MVP's no-default-multi-statement-transaction preference forbids a transaction when the chosen invariant needs one.

**Portable invariant, not a lock recipe:** each pending request reaches one terminal approve/deny/cancel/expiry outcome; an approved request yields at most one redeemable code; a code activates at most one token in **the same atomic commit** that consumes it. Failed verifier/client/resource checks activate nothing; competing redemption/revocation must not result in a usable token outside the bound grant. A committed token followed by a lost HTTP response remains issued and is not reissued on replay. Current lookup verifies issuer, client, subject, canonical resource, instance, scope, absolute expiry and grant/token revocation, and denies when authoritative state is unavailable or ambiguous. Cleanup is not authorization.

For any candidate, specify trusted tenant scoping after early admission, creation-time tenant-aware uniqueness, digest algorithm/key custody, collision/ambiguous-lookup rejection, clock source, retention and redaction before DDL. In shared-database multitenancy do not use `table.unique(...)` for business uniqueness: enforce instance-aware uniqueness in the business layer with a dialect-validated strategy and ordinary supporting indexes. A compare-and-set on an existing row does not prevent duplicate creation. A [scoped Knex builder](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_knex.ts) may retain transition predicates and expose affected-row counts, but its instance scope, cache/write side effects, raw type conversion and secret-safe logging must be reviewed; plain `builder()` is not scoped merely by its name. It is not approved source guidance. An affected-row count of exactly one for a scoped row and complete state/version/revocation predicate must mean a **committed** winner: [the database connection](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/service/db_.ts) can join an ambient transaction, so returning a raw token before the owning commit is not permitted even when one update reports success. Review whether this AS boundary excludes ambient transactions or waits for their verified commit; do not silently use `REQUIRES_NEW`. Mutation/commit acknowledgement uncertainty is not success or permission to retry issuance. SQLite `forUpdate()` is not PostgreSQL row-lock proof; no dialect's migration atomicity or stale replica behavior is presumed for another. The existing auth tables/Redis session marker are not the new opaque-token/grant authority. Redis-only or split SQL/Redis authority would require a new decision.

**Still unselected after the SQLite/primary-datasource target choice:** physical schema/service and migration/partial recovery; request, code and access-token lifetimes; cleanup and retention; client registration/secret custody and policy rollout; actual deployment attestation, worker count/connection policy within the later-selected same-host multi-worker shared-persistent-SQLite topology (cross-host SQLite and replicas are not selected); invalid-attempt policy; revocation triggers and incident response. Illustrative lifetime numbers are not approved defaults. Review cache invalidation/queue dependencies even if token reads bypass a cache; deny on authoritative-store outage rather than falling back to process-local or Redis token acceptance.

## Candidate Zova browser and protocol interaction (requires approval)

1. **Admit before instance initialization.** An approved early mechanism first classifies the trusted issuer/path and resolves the instance from the registered AS/deployment resource relation without accepting untrusted query/header/subdomain selectors as authority. The AS then validates the registered client and exact redirect, canonical MCP resource, explicit S256 challenge, scope and client compatibility against that trusted context before creating pending state. This ordering is a candidate, not an observed route implementation; establish the required safe parsing/lookup before generic instance resolution or `initInstance()`. Authorization entry, page/resume, login bridge, summary/decision APIs, token and discovery routes each need their own early admission disposition. A route guard cannot undo earlier instance selection; ADR 0004's `/mcp` hook does not prove this AS path. Token exchange independently resolves the submitted canonical resource before scoped code lookup and checks the immutable bound client/resource/instance relation. RS token lookup first uses trusted `/mcp` endpoint-to-instance binding, then verifies the returned immutable relation; no raw cross-instance probe explains a miss.
2. **Create server-held pending truth.** Validate client/redirect/resource before creating a one-use pending request. Browser correlation uses an opaque, short-lived, browser-bound reference, separate from client OAuth `state`, upstream-login state, decision CSRF and PKCE. Invalid client/redirect failures terminate locally, never redirecting to an unvalidated URI. Zova receives only a minimal display projection; it does not choose or return authoritative client, redirect, scope or resource values. Do not expose a code except in the AS-generated authorization response to the **validated registered redirect** under the approved OAuth response mode; never place it in an internal Zova URL, rendered page, query cache, browser persistence, telemetry or logs. Keep the verifier, access token, client secret and complete subject data out of URLs, rendered pages, browser persistence, telemetry and logs.
3. **Present and resume with Zova; AS authenticates.** The selected presentation direction is a thin Zova authorization page with explicit approve/deny for this request, not an Admin management page or a new MCP resource frontend. Existing Cabloy Basic Web hosting (the observed [`SsrSiteWeb`](../../vona/src/suite/cabloy-basic/modules/basic-siteweb/src/bean/ssrSite.web.ts)) is a _smallest-change candidate only_, not a synonym for all end users or an approved site: both Web and Admin protected pages use [`routerGuards`](../../zova/src/suite/a-home/modules/home-base/src/service/routerGuards.ts) to check authentication and role `siteIds`, and the built-in registered-user/system-admin roles currently admit `*` under [`roles.ts`](../../vona/src/suite/a-home/modules/home-user/src/config/roles.ts). Confirm the intended authorizing population and actual site policy before deciding Web/Admin/new site, route or flavor; never widen admission by assigning roles merely to make the AS page work. The AS must verify current account, pending/browser/instance continuity and expiry via a reviewed server-authenticated session or login bridge; a client-written cookie, frontend authentication flag, upstream callback state or pending handle alone is not identity proof. A login continuation must be fixed and internal with an opaque pending reference, never an arbitrary `returnTo` or the client's OAuth `state`. For this cookie-backed, protected/personalized interaction, an explicit Zova `ssrProfile: 'session'` and a neutral server/hydration initial shell with post-hydration admission/load are review candidates, not an approved route or implementation. The session SSR handler sets `private, no-store`, but that alone does not prevent query dehydration: the model config only excludes queries marked `ssr.dehydrate: false` or sync-persisted queries. If a query-backed minimal AS summary is needed after admission, prefer model-owned reactive state with `persister: false` and `ssr.dehydrate: false`, without keeping a duplicate controller/render owner; confirm actual API options and hydration behavior at implementation. Never fetch or serialize a private summary during server rendering merely because the page uses the `session` profile.
4. **Approve or deny exactly once.** A same-origin, request-bound decision POST includes an independent CSRF proof. The AS revalidates identity, account activation, site/instance admission, client/resource/redirect policy, scope, pending expiry and browser correlation immediately before the single-use transition. Missing/invalid CSRF, hostile origin, stale tab, switched account, expired session and concurrent/duplicate submission fail closed or restart with a fresh request; denial issues no code. Treat the existing disabled CSRF assertion as absent. Apply escaped display, frame protection and no-store/no-referrer/error/redirect response protections to the entire interaction. A review candidate is a same-origin, browser-native decision POST to a protected AS endpoint that validates CSRF and responds with a top-level redirect to the **previously validated bound URI**; the Zova page renders the form but does not construct the URI. This is not an authenticated flow until an approved browser-to-AS identity/session bridge actually authenticates the native POST; the frontend's cookie-to-Authorization interceptor only covers its API requests. JSON/AJAX auto-following a redirect is not itself top-level browser navigation. Define one explicit navigation/response mechanism, denial and local-error rules, browser/session cookie scope and replay behavior before execution. Never return an MCP code as reusable query state.
5. **Redeem under the bound client/resource.** Require the same canonical `resource` at authorization and token exchange as a stricter local rule than RFC 8707's general subset rule; invalid resource targets use `invalid_target`. Enforce S256 verifier and confidential-client authentication where applicable. OAuth 2.1 draft-13 §10.2 does not universally require token-request `redirect_uri`; if an OAuth 2.0 compatibility branch is explicitly supported, require the identical value under RFC 6749 §4.1.3. Select and test one branch per client profile. If RFC 9207 `iss` is selected, emit it on every redirectable success **and error**, matching advertised metadata; otherwise review mix-up defense and do not advertise unsupported `iss`. Omitted PKCE challenge method defaults to `plain` under RFC 7636 and is rejected by the S256-only profile. Do not advertise refresh or Dynamic Client Registration when unimplemented.

### Reviewable interaction sequence and unresolved owner choices

1. On an AS authorization entry, classify the trusted issuer/path and resolve an enabled instance **before Vona instance initialization** through a separately approved pre-instance admission mechanism. Validate client/redirect/resource/S256 against the resolved trusted registration before creating the server-held pending transaction. Route-local middleware must not be mistaken for early admission; token/discovery/global paths may need a different explicitly reviewed admission rule.
2. Present the Zova page on a separately approved site. If identity is absent, continue only to a fixed same-origin login/resume route with an opaque browser-bound pending reference; on return the AS verifies the current server-authenticated account/instance and pending lifetime again. The Web-site, session-SSR/neutral-shell and post-hydration minimal-summary combination is a **review candidate**, not a selected site or an assertion that a client-written token cookie authenticates the AS.
3. Obtain an independently reviewed browser-to-AS identity mechanism (for example an AS-owned HttpOnly session or a tightly scoped, server-validated login bridge), bind browser correlation and a distinct per-pending request CSRF proof, and revalidate account/site/resource/client/redirect policy before a native same-origin decision POST. The AS decides approve or deny once, and the browser follows only an AS-built response to its original validated redirect. Rejected/expired/conflicting requests end locally or require a fresh authorization, never a client-constructed redirect.
4. Token exchange and later resource-server lookup use the trusted bound resource/instance and fresh authority as specified above; the authorization-page site/session cannot authorize `/mcp` calls. Protected AS summary/decision, authorization/resume/login, token and discovery paths need individually reviewed pre-instance ingress, authentication, cache and disclosure rules.

**Explicit decisions before implementation:** identify the intended authorizing users and chosen site/flavor/module/page route; AS route and deployment resource-to-instance map with per-route pre-instance treatment; server-verifiable login/session bridge and its lifecycle/cookie scope; browser correlation and CSRF validation; layout/SSR/hydration privacy and no-store/referrer/framing policy; exact decision POST/top-level redirect/error/cancel behavior; client compatibility and issuer metadata. These remain **unselected**. The selected presentation does not transfer authority from AS to Zova or authorize a general OAuth console, independent site, source code or live provider integration.

## Separate decisions and prospective proof

1. **Physical authority:** review an addressed opaque credential versus digest-only lookup, locator/secret format and tenant-scoped creation strategy before DDL; neither lookup nor its uniqueness strategy is selected. Confirm the selected SQLite/`better-sqlite3` target on Vona's existing primary datasource against the actual deployment and attest to its selected same-host multi-worker shared-persistent-SQLite topology and resolve worker count/connection policy; prove the concrete single-aggregate conditional mutation or a multi-record transaction, committed affected-row result including ambient transaction handling, creation-time uniqueness/collisions, same-commit redemption/activation, approved keep-v1 fresh creation, existing-v1 non-replay/denied activation and missing-history/partial/unknown-state rejection within the accepted exclusions, plus current lookup with the actual dialect. Any upgrade/adoption or recovery treatment remains separately gated, not part of the first installation scope. Select an owning AS module/service, client-registration approach and secret custody. Do not alter the deployment database client to fit planning.
2. **State contract:** review state shape, instance scope, concurrent decisions/redemption/revocation, digest and lifetime policy, invalid attempts, lost response and cleanup. A lookup that began before revocation can have already admitted work; require at least that lookups begun after acknowledged revocation fail, and define any stronger in-flight cancellation separately in the RS/domain contract. Preserve a monotonic revocation marker and ensure revocation does not silently lose to a stale revision. The later ADR 0009 disposition resolves the conditional existing-`a-auth` strategy: keep `vonaModule.fileVersion: 1` and fold schema into its version-1 creation path, with no version-2 migration or automatic upgrade of already-recorded v1 databases. Fresh-only installation scope/exclusions are accepted; exact owner/schema, actual-target classification and migration/check implementation still require approval before persisted edits, while excluded existing-install/adoption and partial/unknown-state treatment remain blocked pending separate disposition; a different owning-module premise requires its own version disposition. A separately approved `meta.version.ts` edit requires root `npm run test`.
3. **Browser and protocol:** select Zova site/admission, an AS pre-instance ingress contract, server-verifiable identity/session or login bridge, request-bound CSRF, SSR privacy, exact routes and redirect behavior, client/redirect/issuer policy and supported OAuth branch. Prove AS and RS instance/resource maps align rather than treating ADR 0004's `/mcp` hook as AS proof.
4. **Then, and only then:** re-review the blocked [AS execution dossier](./wbs-mcp-20-04-execution-dossier.md) for bounded execution approval before source/configuration/tests. Prospective `ATP-MCP-AUTH-03` must prove competing decisions/redemptions in separate Vona contexts and their combined durable outcome, current multi-worker/revocation/outage behavior, and real HTTP Zova SSR/hydration, login continuation, two-instance/account admission, CSRF, invalid redirects and response secrecy on the actual chosen deployment. Tests on one dialect do not prove another. Keep `WBS-MCP-20-02` and `ATP-MCP-AUTH-01` separate.
