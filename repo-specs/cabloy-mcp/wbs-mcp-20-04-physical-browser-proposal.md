# WBS-MCP-20-04 Database-Neutral State and AS Backend HTML Proposal

## Status and decision boundary

**Database-neutral and backend HTML design directions selected; concrete state/interaction proposal unaccepted, not execution-ready or runtime proof.** Prepared for Cabloy Basic (`__CABLOY_BASIC__`) against `9cca451dff` on 2026-10-10, with attributable planning edits already in the worktree. [ADR 0009](./decisions/0009-mcp-as-state-boundary.md) selects the integrated `a-auth` logical AS, one AS-owned transactional-database authority, an AS-owned browser approve/deny interaction on every request, `zhennann`'s implementation/operations responsibility, and the later clarification to keep the design database-neutral with AS backend-rendered HTML. No PostgreSQL-primary selection remains proposed here. The deployed dialect/topology, state representation, client registry, HTML/session/CSRF implementation, admission hook, lifetimes, migration and `fileVersion` are **not** selected. This document refines the selected directions into a reviewable contract and lists the outstanding decisions; it does not itself approve source, schema or execution.

No AS source, schema, UI, credentials, issuer configuration, runtime ATP, or evidence is created. `WBS-MCP-20-04` and its dependent `WBS-MCP-20-02` stay `blocked`; `ATP-MCP-AUTH-03` remains prospective. The separate [execution dossier](./wbs-mcp-20-04-execution-dossier.md) remains unapproved. The first profile still has pre-registered public/confidential clients, Authorization Code + PKCE S256, short-lived MCP-only opaque access tokens with current lookup, explicit per-request approval or denial, and no refresh issuance or remembered consent.

## Observed constraints (not endorsements of this proposal)

- Existing `a-auth` has `fileVersion: 1` in [`package.json`](../../vona/src/suite-vendor/a-auth/modules/a-auth/package.json); [`meta.version.ts`](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/bean/meta.version.ts) version 1 creates only `aAuth` and `aAuthProvider`. The [version runner](../../vona/src/suite-vendor/a-vona/modules/a-version/src/service/version.ts) applies versions above the recorded version on an existing installation. Merely adding tables to version 1 would not migrate that installation; the selected dialect also needs fresh-install, upgrade and partial-migration recovery proof, rather than assuming transactional DDL is portable. A new migration version is a **candidate**, not a `fileVersion` decision or permission to edit either file.
- [Backend database configuration](../../vona/src/backend/config/config/config.ts) supports SQLite (`better-sqlite3`), PostgreSQL (`pg`), and MySQL (`mysql2`), selecting a default by environment. The actual deployment dialect and topology were not inspected; source defaults do not establish them. Model operations normally use `database.current` and [apply `ctx.instance.id`](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_meta.ts) to ordinary instance-scoped records, **after** trusted instance admission. A caller-supplied `iid` is removed by the model, but an incorrectly selected context still reads the wrong instance.
- [`getForUpdate`](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_cache.ts) requires an active transaction and bypasses model caches, but selects only one match; it cannot establish uniqueness. The cached [model `update()` path](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_cache.ts) can replace a state/version predicate with previously selected IDs; the underlying [mutation](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_crud_inner.ts) returns data rather than the affected-row count. Neither an ordinary successful model update nor disabling only the query cache proves a compare-and-set win. [`REQUIRED` transactions](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/service/transaction_.ts) join an ambient transaction without upgrading isolation; post-commit callbacks can fail after durable commit. Lock semantics must be proven against the selected dialect: SQLite's Knex `forUpdate()` is not PostgreSQL row-lock proof. Disabling entity/query cache reads alone does not prove absence of cache invalidation or queue/double-delete side effects; review writes and callbacks before claiming an SQL-only availability dependency.
- Existing [`a-auth` provider callback](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/controller/passport.ts) verifies signed **upstream provider-login** state and enters an executor context; it is not an MCP authorization/consent flow. Its [continuation validation](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/service/auth.ts) and generic [origin checks](../../vona/src/suite-vendor/a-vona/modules/a-security/src/bean/bean.security.ts) are not exact registered OAuth client redirect validation: the existing starts-with-slash path allows protocol-relative `//...` values to skip an origin check. The [`mock` authorize form](../../vona/src/suite-vendor/a-auth/modules/a-auth/src/controller/mock.ts) is dev-only and echoes supplied redirect/state; it is not production consent, redirect validation, CSRF or issuance. [ADR 0004](./decisions/0004-mcp-host-instance-binding.md)'s proposed early `/mcp`/resource-metadata admission does not cover AS authorization, approval, token or discovery routes.
- Existing browser login returns local JWT/Passport data, and Zova's client-side token cookie is **not** an HttpOnly AS session. The [backend JWT extractor](../../vona/src/suite-vendor/a-vona/modules/a-jwt/src/service/jwtExtract.ts) does not read cookies; a plain protected backend HTML GET will not inherit Zova login merely from the browser cookie. An AS-owned session/identity bridge must be separately designed and proven. [Global CSRF middleware](../../vona/src/suite-vendor/a-vona/modules/a-security/src/lib/middlewares/csrf.ts) has its assertion commented out; toggling its configuration does not protect an approval POST. The HTTP [listener](../../vona/src/suite-vendor/a-vona/modules/a-web/src/bean/startup.listen.ts) enters executor `newCtx` **before** system middleware; the [instance resolver](../../vona/src/suite-vendor/a-vona/modules/a-instance/src/main.ts) may choose a query/header/subdomain selector at that earlier point. Normal [instance middleware](../../vona/src/suite-vendor/a-vona/modules/a-instance/src/bean/middlewareSystem.instance.ts) invokes `initInstance()` before a controller, and executor `newCtx({ instance: true })` does not reproduce its disabled-instance check. Do not assume AS routes are globally exempt from instance initialization.

## Database-neutral logical authority (representation requires approval)

**Selected design direction:** one AS-owned transactional database authority, described without choosing PostgreSQL, MySQL or SQLite. A dedicated MCP AS service under the existing `a-auth` capability and the following record shape remain **candidates**. All AS workers and the resource-server lookup must see the same current authoritative state; a replica whose freshness cannot be established is not sufficient. Do not switch the deployment's database client to fit a planning proposal. The supported deployed dialect, datasource/topology and implementation of atomic transitions are separate execution decisions and must be demonstrated with that dialect and migration path. Keep the MCP resource module schema-free. Do not bind a state model to another datasource while enclosing it in a transaction on `database.current`; the model and transaction must use the same verified datasource and context.

| Candidate record/boundary    | Minimal authoritative contents and invariant (logical fields, **not** a table DDL)                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pre-registered client policy | Reviewed client ID/type, exact allowed redirects (only a separately approved native loopback variable-port exception), approved resource/scope limits and confidential authentication method/secret custody. Candidate: controlled, deployment-reviewed AS configuration rather than a mutable client table in this increment; changes must have explicit activation/revocation behavior across workers. Existing upstream OAuth-provider credentials are not MCP client registrations. |
| Pending request              | Random AS-only pending handle **digest**, issuer, client ID, validated redirect binding, canonical registered resource and bound instance, requested scope, S256 challenge, creation/absolute expiry, browser/session correlation and terminal state. A client `state` is opaque correlation retained only as needed to echo after a validated redirect; never treat it as a session token or log it. Enforce one terminal outcome (approve, deny, cancel, expire) under concurrency.   |
| Approved grant/code          | A single code digest and its immutable pending/grant linkage: issuer, approved current subject, client, redirect, canonical resource/instance, subset of requested and authorized scopes, creation/absolute expiry, single-consumption state and revocation. No general consent ledger or remembered approval. Treat the code as unredeemable after grant revocation/expiry; no plaintext code at rest.                                                                                 |
| MCP opaque access token      | A separate high-entropy token digest and immutable grant/client/subject/issuer/MCP-profile/resource/instance/scope binding, issue/absolute expiry and active/revoked status, or an unambiguous immutable join to those attributes. Lookup must verify the grant and current policy, not just a token-row existence flag; no raw token at rest and no refresh family.                                                                                                                    |

This three-record shape is a **candidate**, not approved table names, columns, indexes or migrations. Specify precise tenant scope (`iid` after trusted instance admission), uniqueness/lookup constraints, non-secret public IDs, digest algorithm/key custody and rotation, clock source, and deletion policy before DDL. For every digest lookup, detect malformed/ambiguous matches and deny; `getForUpdate` returning one row is insufficient proof of uniqueness. In a shared-database multitenant deployment do not introduce `table.unique(...)` for business uniqueness: enforce instance-aware uniqueness and single-use state in the business layer with a dialect-validated serialization or conditional-transition strategy and supporting ordinary indexes. Evaluate digest collision handling and duplicate rows explicitly rather than trusting a `limit: 1` query. SQL debug/AOP logs and retained error payloads must never capture code/token values, verifier, client secret, cookie, signed provider state or complete private subject data.

**Portable invariant, not a portable lock recipe:** each pending handle has one terminal decision; an approved pending request yields at most one redeemable code; one code can activate at most one token in the same durable transaction that consumes it; revocation must be ordered against redemption so a newly checked token cannot be accepted as current after its revocation has committed (this does not retroactively undo a request already admitted before revocation). The implementation must ensure that every contingent write is conditional on the previous state and the transition is rejected if its actual matched/changed outcome is not exactly the expected one, or use an equally proven serialization mechanism. A compare-and-set on an existing row does **not** prevent concurrent creation of the same tenant-scoped handle/digest under unrelated parents: design creation-time uniqueness as its own serialized check-and-insert protocol, and treat a duplicate/ambiguous lookup as failure, not as an arbitrary first match. A candidate [scoped Knex builder](../../vona/src/suite-vendor/a-vona/modules/a-orm/src/lib/bean.model/bean.model_knex.ts) can retain predicates in the actual UPDATE and expose an affected-row result, but raw mutations need explicit trusted instance scope, cache/write-side-effect review and secret-safe logging; it is not approved source guidance. Define retryable contention versus terminal conflict without replaying a committed response or an external effect. A transactional decorator alone does not prove the isolation, locking, conditional-write count or cache/callback behavior. Evaluate these properties with the chosen driver, transaction owner and database version; in particular an already-open `REQUIRED` transaction cannot silently supply stronger isolation, and a cacheless read in a long-lived snapshot or from a stale replica is not necessarily a current authorization read. SQLite Knex `forUpdate()` emits no row-lock clause, whereas PostgreSQL/MySQL require independent proof of their lock, isolation and affected-row semantics; MySQL DDL may commit independently of a migration wrapper. A SQLite-only or in-memory test does not verify the PostgreSQL/MySQL behavior (or vice versa).

**Proposed transaction and failure contract:** the AS chooses a canonical lock/serialization order for competing terminal pending decisions, then a consistent grant-before-token order for redemption/revocation. At browser approval, validate current user, account, client/resource/instance and pending expiry inside the owning transaction; perform a conditional single-use terminal transition and create **at most one** code. Denial/cancellation/expiry cannot later approve. At token redemption, authenticate the registered client as required, validate S256 and immutable bindings, lock or atomically claim the unconsumed code/grant, and consume it **in the same durable commit** that activates one access token; competing redemption and revocation cannot both create a usable token. On replay, deny and evaluate revoking any token previously issued from that code when feasible (RFC 6749 §4.1.2); document exact behavior. Invalid verifier/resource/client must never activate a token; define whether bad attempts leave an otherwise valid code consumable before implementation. A committed token followed by a lost HTTP response remains issued but unavailable to that response; do not mint it again on retry. A post-commit callback failure is not rollback. No `REQUIRES_NEW` escape or silently joined ambient transaction may split the code/token boundary. Current token/grant lookup denies on outage, ambiguous row, stale read replica, expired/revoked state, or a changed resource/instance/client/subject relationship; cleanup is not authorization. Set a bounded no-sliding expiry and a revocation/retention/deletion schedule separately.

**Unselected operational values:** physical database/primary, migration version and rollout, request/code/access lifetimes, cleanup interval and retention, client registry administration, worker/replica topology, revocation triggers (logout, user disablement, client/resource disablement, grant withdrawal), availability and incident response. Values such as 10-minute pending, 60-second code, or 15-minute access lifetimes are **review candidates only**, not defaults or approved policy. If the same DB is unavailable, fail closed without a Redis/process-local authorization fallback. Verify independently whether model cache invalidation/queue dependencies remain even with cacheless token reads and writes; if they do, include them in availability/failure policy rather than claiming no Redis dependency.

## Candidate AS browser and protocol interaction (requires approval)

1. **Admit before instance initialization.** Treat the authorization request's `resource` only as a request for a registered canonical recipient. The AS validates issuer, client, registered redirect, exactly one registered canonical MCP resource, PKCE challenge **and explicit `code_challenge_method=S256`**, narrow scope and client compatibility. Resolve that resource through an AS/deployment-owned one-to-one resource → enabled instance map before any generic Vona query/header/subdomain selection or `initInstance()`, then bind the resulting instance to the pending request. A dedicated AS-path integration in the **pre-`newCtx` instance-name resolver** is a candidate, **not** a feature of ADR 0004's `/mcp` hook. A route-level guard or controller cannot undo an already-selected instance. Candidate narrow ingress shapes include one deployment-configured enabled instance per AS origin or an allowlisted, trusted endpoint/path → instance map; both must reject conflicting query/header/subdomain selectors and prove the same binding on callback/resume and POST paths. A tenantless bootstrap would instead require explicit early-context and `initInstance()` handling, not merely returning `null`. For token exchange, independently resolve the required registered `resource` through that map before scoped code lookup, then check the looked-up code's immutable client/resource/instance binding in the transaction; a raw Host, forwarded value, browser/query selector, unverified code or token is never instance authority. For resource-server token lookup, use the already trusted `/mcp` endpoint-to-instance binding before scoped digest lookup, then compare the returned immutable issuer/resource/instance relation. Neither flow may probe another instance to explain a miss. Public AS discovery must expose only approved issuer metadata without accidental tenant initialization or cross-resource leakage. If this early path cannot be demonstrated for all AS routes, keep them disabled.
2. **Create one pending request.** After redirect/client/resource validation, persist only the data required for a one-time decision, then issue an AS-owned, random, short-lived, session-bound browser correlation handle. Keep the client-supplied OAuth `state` separate from this handle, upstream provider-login `state`, approval-form CSRF, and PKCE; none substitutes for another. Never put a code, verifier, access token, client secret or private account data in the page URL, browser storage, rendered HTML, telemetry or logs. Unvalidated client/redirect errors terminate locally and **never** redirect to the supplied URI. The existing provider continuation's slash-prefix/origin check, including its treatment of `//host`, is not an AS client-redirect registry check; keep a separate exact-registration validator. A browser session/handle may correlate this page, but only the AS transaction remains code/grant/token authority.
3. **Establish current local identity, then render the selected AS backend HTML page.** The AS-owned browser GET uses the trusted instance and pending binding to authenticate or re-check the active local user. A plain backend HTML GET cannot assume the existing frontend login cookie authenticates Passport: specify a server-verifiable AS identity/session or an explicit, separately reviewed authentication bridge, bound to the admitted instance and pending transaction. Neither a client-written JWT cookie, provider callback state nor possession of the pending handle alone is identity proof. If login is necessary, consider a bounded AS-owned backend login form with a separately reviewed credential verifier, abuse/captcha policy and session rotation; calling an existing service does not inherit the application login route's guards/interceptors and ordinary `passport.signin()` also mints application JWTs. An upstream-provider login is an **optional later bridge**, not an already safe callback: it needs an AS-owned browser-bound, one-use attempt and fixed internal continuation, verified across success, denial and replay. Preserve only a protected AS continuation reference, re-resolve it after return and verify current account, instance, session and pending expiry; do not forward the OAuth client `state` as provider-login state, trust a login callback's instance selector as admission, reuse a callback code as an AS code, or accept a caller-chosen external `returnTo`. Escape all server-held and display values in the HTML, including reviewed client label, resource, current account and requested/approved scopes; one existing login session establishes identity, **not approval**. Never silently grant a new request. The selected presentation is AS backend-rendered HTML, **not** a Zova page/site/SSR flow; exact rendering and identity mechanics still need approval.
4. **Approve or deny explicitly and exactly once.** A same-origin, state-changing POST submits an approve/deny choice bound to the pending handle, the current server-authenticated account/session and an independent, request-bound anti-CSRF token; the existing global middleware has no active CSRF assertion and cannot be assumed to supply this control. If a dedicated CSRF guard reads a form field, account for the current route ordering (guards run before body-parsing interceptors): put verification at a stage with the bounded form already parsed, or provide a separately proven parser/guard order. Bind an opaque session cookie to an AS-owned required store and rotate it at authentication; storage disablement or outage denies rather than silently downgrading to client-held identity. A separately approved transient browser-session store is not an alternative code/grant/token authority or a second issuance commit. Review cookie attributes, rotation, expiration and logout invalidation for the selected session; verify a hostile origin, missing/invalid token, stale tab, account switch or duplicate submission is rejected before any code issuance. Check the exact expected Origin where available (and a separately reviewed Referer fallback) as defense in depth, deny cross-site form submissions and clickjacking, use escaped output and restrictive content/security headers, and disable caching/referrer leakage for **all** AS HTML, local error and redirect responses. Framework CSP/X-Frame middleware sets headers after downstream success and may not cover thrown redirects/errors; `@Api.setHeader` on a successful response does not prove error/redirect coverage. Define a path-bounded early response policy and error/redirect helper, with tests ensuring generic middleware cannot overwrite it. The current `ctx.redirect()` handles 301/302 via exceptions, so do not assume a proposed POST/redirect/GET 303 is supported by that helper without a separate implementation. Re-check account activation, instance/resource registration, client policy, pending expiry, scope and session continuity immediately before the transactional terminal transition. A different account, expired session, cross-tab stale request or duplicate/back-button submission fails closed or restarts a fresh authorization; it never reuses an earlier grant. Denial/cancellation issues no code. A finalized authorization response may redirect **only** to the prevalidated bound URI, returning an applicable OAuth error and the exact supplied client `state` when present; invalid client/redirect failures remain local. Do not expose internal failure details via redirects.
5. **Redeem under the bound client and resource.** Require the same single canonical `resource` at authorization and token exchange as a **stricter local profile** than RFC 8707's general token-request subset rule; use `invalid_target` for invalid resource targets. Require S256 verifier, code, client authentication (when confidential), scope and current grant/instance state, then execute the one-commit redemption. OAuth 2.1 draft-13 §10.2 removes token-request `redirect_uri`; do not require or advertise it as universal. If a separately selected OAuth 2.0 compatibility branch accepts authorization requests with `redirect_uri`, RFC 6749 §4.1.3 requires the _identical_ token-request redirect in that branch, not merely comparison when optionally supplied. Select and test **one** branch per supported client/profile before implementation. If RFC 9207 response `iss` is selected, emit it on every redirectable authorization success **and error**, match metadata `issuer` exactly and advertise `authorization_response_iss_parameter_supported: true`; if omitted, do not advertise support and explicitly review the client mix-up defense. RFC 7636 defaults an omitted challenge method to `plain`, so omission is rejected by this S256-only profile. Advertise only implemented metadata, including no refresh grant and no Dynamic Client Registration unless added in a new decision.

The **AS backend HTML direction is selected**, but exact AS browser routes, templating/escaping and security headers, session/CSRF owner and cookie attributes, login continuation storage, fallback for browsers without an existing local session, credential-login versus provider-bridge scope, issuer-host/topology, native-loopback registration exception, confidential client method, HTTP error taxonomy, response `iss` policy and OAuth 2.0 compatibility branch are **unselected**. A narrow candidate route family is authorize GET, AS interaction GET, login POST and decision POST, with optional session logout/provider callback only after separate review; these are **not** existing or approved routes. The token endpoint is a separate non-HTML client/protocol path and must not accept ambient browser cookies or trigger a login redirect. A local login JWT or cookie must not become an MCP resource credential. If a framework session/CSRF primitive cannot safely support this flow, design a dedicated AS interaction rather than copying the dev mock form or adding an unreviewed Zova site. Real HTTP tests must show early admission, login continuation, two-instance/account/cross-tab boundaries, browser denial, output escaping and CSRF behavior; model/executor-only tests do not prove them.

## Separate decisions and prospective proof

1. **Physical authority:** The database-neutral contract and AS backend HTML presentation direction are selected; no PostgreSQL-primary choice is pending or implied. Before executing, select the deployed dialect, datasource and multi-worker topology and prove its concrete transition/locking, affected-row and creation-time uniqueness semantics, fresh-install and existing-install migration/partial-recovery, and current-lookup behavior there. Review the candidate dedicated `a-auth` MCP AS service separately; confirm fail-closed dependencies without publishing credentials or live endpoints. Decide reviewed configuration versus persisted client registration, secret custody and policy rollout.
2. **State contract:** Review the pending/grant/token shape, instance scoping, concurrency and replay/revocation order, digest/key lifecycle, absolute lifetimes, invalid-attempt and lost-response behavior, retention and cleanup. Record the approval in governing ADR/SRS/WBS/ATP authorities **only after a separate disposition**. Before **any persisted field/schema edit**, ask whether the owning `vonaModule.fileVersion` will increment; do not select or edit it from this proposal. If `meta.version.ts` is separately approved and edited, root `npm run test` is required.
3. **Browser and protocol:** For the selected AS backend HTML direction, approve an actual AS-path pre-instance admission hook, server-verifiable identity/session or login bridge, request-bound CSRF/continuation, HTML rendering and response protections, exact routes, denial/cancel/error matrix, login/account-switch handling, issuer and `iss` behavior, client and redirect policies, OAuth 2.1 versus explicit OAuth 2.0 token-request redirect compatibility, scope vocabulary and supported client matrix. Prove the registration map aligns with the still-proposed DEC-MCP-04 protected-resource endpoint relation; do not use its `/mcp` hook as AS proof.
4. **Then, and only then:** amend the governing design authority and prospective `ATP-MCP-AUTH-03` procedures for the separately approved concrete values; re-review the blocked [AS execution dossier](./wbs-mcp-20-04-execution-dossier.md) for explicit approval before source/configuration/tests. ATP must demonstrate competing approval and redemption using separately owned Vona contexts, combined durable outcome on the selected dialect, cross-worker/current revocation and outage behavior, and real HTTP backend HTML/instance/metadata behavior with synthetic redacted fixtures. Tests against one dialect do not prove another dialect's locking or migration. Keep `WBS-MCP-20-02` and `ATP-MCP-AUTH-01` separate.
