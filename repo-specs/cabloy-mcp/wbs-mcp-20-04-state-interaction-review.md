# WBS-MCP-20-04 AS State and Interaction Review (Proposal)

## Review status and scope

**Planning proposal for a separate design decision — not an accepted storage/interaction disposition or execution approval.** Prepared for the Cabloy Basic worktree at `2dda23660f` on 2026-10-10 with prior attributable planning edits present. [ADR 0009](./decisions/0009-mcp-as-state-boundary.md) permits planning AS-owned shared authorization state; it approves no database, Redis namespace, schema, consent record, retention policy, migration, or `fileVersion` choice. This review proposes a concrete direction for `WBS-MCP-20-04` and `SRS-MCP-AUTH-04`, subject to a named decision by `zhennann` and a later, separately approved execution dossier. Neither this proposal nor a static planning check creates AS source or `ATP-MCP-AUTH-03` evidence.

The accepted first profile and selected ownership remain unchanged: integrated `a-auth` logical AS, `zhennann` responsible for implementation and operations, pre-registered public/confidential clients, Authorization Code + PKCE S256, short-lived MCP-only opaque access tokens with current lookup, a new explicit grant decision for each authorization request, and **no refresh-token issuance**. The separate `cabloy-mcp` resource server owns no AS transaction or token store. Its initial scaffold remains schema-free.

## Read-only feasibility findings

- `a-auth/src/service/auth.ts` and `a-user/src/bean/bean.passport.ts` implement provider-login callback and local JWT-backed code redemption, not observed one-time MCP code consumption, exact registered redirect matching, or PKCE. Upstream provider client configuration is not registration of downstream MCP OAuth clients.
- `a-user/src/service/redisToken.ts` owns an instance-scoped user/auth session marker, not per-client/resource/grant opaque-token state. Generic `a-cache/src/service/cacheRedisBase_.ts` renews TTL on read by default, uses separate read/delete operations, and may skip writes when disabled; do not treat it as an authorization transaction store by default.
- `a-orm/src/lib/bean.model/bean.model_cache.ts` exposes transactional locking reads; `a-orm/src/service/transaction_.ts` supports a single database transaction. This is a candidate atomic boundary, not proof of the selected database dialect or concurrency under an AS load. Cache rollback compensation and a Redis lock do not turn Redis plus SQL into one atomic commit.
- `home-user/src/service/account.ts` provides a token-digest precedent but not an AS lifecycle template. The existing browser login/provider callback and local Passport refresh do not prove an AS authorization/approval surface or a safe browser session handoff; that interaction must be independently designed and tested.

These paths are read-only feasibility inputs, not selected AS source files or evidence of working issuance. No environment values, credentials, raw tokens, or state payloads were inspected or retained for this review.

## Recommended state design for decision (not selected)

**Recommendation: one AS-owned transactional database authority for authorization request/code/grant linkage and opaque access-token active/revocation state.** Co-locate code consumption and access-token activation in one explicitly owned transaction rather than splitting the authoritative transition across SQL and Redis. This favors auditable single-commit behavior and database row locking over Redis-only atomic scripting; it is **not** approval to add `a-auth` tables, fields, indexes, migrations, or a module dependency. The exact owning module/service and physical representation remain to be decided. A separately reviewed Redis-only design could instead use fixed TTLs, atomic compare-and-consume, a defined shared deployment/namespace, persistence and eviction policy, and an equally current token/revocation view; generic cache `get`/`del` or process-local maps are insufficient. Mixed SQL+Redis authority is not proposed without an explicit cross-store failure/reconciliation contract.

| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pre-registered client and redirect policy      | AS-owned reviewed client records or configuration, separate from upstream login-provider clients. Public clients use PKCE without a secret; confidential clients additionally use an approved authentication method.                                                                   | Registry/configuration representation, administrator and credential custody, exact supported redirect forms, onboarding and compatibility limits. |
| Pending authorization request                  | AS-owned shared, short-lived transaction binds issuer, registered client, exact redirect URI, canonical registered resource and instance relation, requested scope, S256 challenge, browser/login correlation and a fixed expiry.                                                      | Owning service, representation, absolute TTL, cancellation and recovery behavior, privacy classification.                                         |
| Explicit grant and one-time authorization code | After current user authentication and an explicit per-request approve decision, create a short-lived code represented by a digest or comparably protected lookup. Bind user, approved scope, client, redirect, resource, instance and transaction. Denial/cancellation issues no code. | Exact expiry, grant history/retention and transaction model; no remembered-consent record is approved.                                            |
| MCP opaque access token                        | Issue a high-entropy value only after atomic successful code redemption. Store only a digest or equivalently protected representation with current client/grant/subject/resource/instance/scope/issued/expiry/active state.                                                            | Token lifetime, digest/key management, revocation policy, retention/deletion and lookup API; no refresh family.                                   |

**Proposed atomic boundary:** validate the code, `S256` verifier, registered client/authentication method, exact redirect, requested resource, approved scope and bound subject/instance against the same authoritative record; under a single store-owned atomic transaction, consume the code once and activate only the resulting access token. A competing redemption must produce at most one active token. A failed validation must not mint a token, widen the grant, or consume unrelated state. Specify whether invalid attempts consume or preserve the code before acceptance. A successful commit followed by a lost HTTP response is an uncertain result, not permission to retry issuance with the same code; the client must begin a fresh authorization, without exposing an already committed token. Token lookup checks active/revoked and absolute expiry from current AS-owned state on every protected request; cleanup scheduling is not validity enforcement. A missing, stale, ambiguous, unavailable or cross-resource record fails closed, including on another worker. Exact revocation triggers (user logout, account disablement, credential reset, client removal, resource disablement, grant withdrawal), reconciliation, operator action and retention remain open.

**No schema decision is implied.** If the approved physical choice changes a persisted field/schema or `meta.version.ts`, ask whether the owning `vonaModule.fileVersion` increments **before editing**; a separately approved `meta.version.ts` change requires root `npm run test`. Even a Redis/external choice requires explicit namespace, expiration, eviction/persistence, outage and operations approval.

## Recommended resource-owner interaction for decision (not selected)

1. AS validates issuer, registered client, exact redirect, canonical registered resource, requested narrow scopes and PKCE challenge **before** starting a pending transaction. Invalid or unregistered redirects fail locally without redirecting to an attacker-supplied URI. Only approved response fields go to the validated redirect.
2. Through a separately approved AS-owned browser interaction, authenticate or re-check the local user for the registered resource's instance, then display the verified client, active account, resource and requested/approved scopes. An existing login session may establish identity, **not consent**; every authorization request still requires an explicit approve or deny action. Account switching, disabled accounts, session loss and a resource/instance mismatch abort or restart safely rather than inheriting prior authorization.
3. Bind the approval submission to the pending AS transaction and current authenticated user with an independently reviewed CSRF control. Distinguish client-supplied OAuth `state` (opaque client correlation returned unchanged where applicable), AS-owned pending-transaction/browser correlation, upstream provider-login state (if used), form CSRF protection, and the PKCE challenge/verifier. Possession of client `state`, a login cookie or provider callback does not imply grant approval; do not invent a mandatory `state` parameter at the token endpoint.
4. Approve once to issue a code for the exact client/redirect/resource/instance and a subset of authorized scopes. Deny, cancel, expire or cross-tab/account-switch conflict issues no code or token; any error redirect must first pass exact registered-redirect validation. Do not persist remembered consent or permit silent approval on later reauthorization.
5. Token exchange requires the original client and exact redirect, `S256` verifier and the authorized canonical resource; it cannot widen resource, instance or scope. Publish only metadata that matches implemented methods/grants/client authentication and no-refresh behavior. Browser-login session refresh, if used solely to maintain AS identity, is not MCP access-token refresh and cannot bypass a new grant decision.

The browser surface, route/SSR owner, safe session handoff, same-origin/CSRF and clickjacking policy, login continuation, form-cache and redirect-leakage controls, and actual compatible clients are **not selected**. No new Zova site is implied by the resource-server no-site decision; a selected AS UI or site requires its own source/privacy/browser/SSR and verification scope. The protected `/mcp` endpoint still rejects cookies and ordinary login JWTs as credentials.

## Decision checklist before revising ADR 0009 or execution readiness

1. Select the authoritative state store and exact `a-auth` module/service boundary; name the database or shared-service owner and operations topology without recording live secrets or endpoints. Record whether client registration uses reviewed configuration or state.
2. Decide code/request/token absolute TTLs, retention/deletion and privacy policy, digest/custody, fixed-versus-sliding expiration, atomic redemption/revocation, inter-worker consistency, outage response and recovery. Demonstrate one active issuance at most under competing redemptions and a truthful lost-response outcome.
3. Select the AS resource-owner authentication and approval surface, resource-to-instance registry lookup, user/session continuity and CSRF policy. Decide denial/cancellation, cross-tab, account-switch, disabled-user, and invalid-redirect behavior; keep client `state`, AS correlation and provider state separate.
4. Confirm issuer/discovery topology, registration of the canonical resource/instance, exact pre-registered client/redirect forms and confidential authentication method, supported-client compatibility, scope vocabulary and access lifetime. Verify the selected protocol fields against authoritative OAuth/MCP references before implementation; this review is not a conformance claim.
5. If a schema edit is proposed, ask the owning module's `vonaModule.fileVersion` question before editing. Approve the exact physical representation and any UI/site scope separately, then update ADR/SRS/WBS/ATP authority and re-review the [AS execution dossier](./wbs-mcp-20-04-execution-dossier.md) for an explicit bounded execution decision.
