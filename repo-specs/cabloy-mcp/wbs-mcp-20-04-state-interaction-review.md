# WBS-MCP-20-04 AS State and Interaction Review (Design Basis)

## Review status and scope

**Bounded design selection and planning review — not physical storage/browser implementation or execution approval.** Initially prepared for the Cabloy Basic worktree at `2dda23660f` on 2026-10-10; reviewed again against clean `9cca451dff` on 2026-10-10. In a separate 2026-10-10 decision, `zhennann` selected the single AS-owned transactional database authority direction and an AS-owned browser approve/deny flow for every authorization request, as recorded in [ADR 0009](./decisions/0009-mcp-as-state-boundary.md). The comparison and interaction sketch below are the basis for that **logical** design selection. A subsequent bounded clarification chose a database-neutral state/transaction contract and AS backend-rendered HTML presentation rather than a PostgreSQL-primary or Zova authorization-site design; this does not establish dialect-independent locking or a server identity/session bridge. Physical store/module/schema, browser routes/session/CSRF, consent retention, TTL, migration and `fileVersion` remain undecided. Neither this review nor static planning checks create AS source or `ATP-MCP-AUTH-03` evidence.

The accepted first profile and selected ownership remain unchanged: integrated `a-auth` logical AS, `zhennann` responsible for implementation and operations, pre-registered public/confidential clients, Authorization Code + PKCE S256, short-lived MCP-only opaque access tokens with current lookup, a new explicit grant decision for each authorization request, and **no refresh-token issuance**. The separate `cabloy-mcp` resource server owns no AS transaction or token store. Its initial scaffold remains schema-free.

## Read-only feasibility findings

- `a-auth/src/service/auth.ts` and `a-user/src/bean/bean.passport.ts` implement provider-login callback and local JWT-backed code redemption, not observed one-time MCP code consumption, exact registered redirect matching, or PKCE. Upstream provider client configuration is not registration of downstream MCP OAuth clients.
- `a-user/src/service/redisToken.ts` owns an instance-scoped user/auth session marker, not per-client/resource/grant opaque-token state. Generic `a-cache/src/service/cacheRedisBase_.ts` renews TTL on read by default, uses separate read/delete operations, and may skip writes when disabled; do not treat it as an authorization transaction store by default.
- `a-orm/src/lib/bean.model/bean.model_cache.ts` exposes transactional locking reads; `a-orm/src/service/transaction_.ts` supports a single database transaction. This is a candidate atomic boundary, not proof of the selected database dialect or concurrency under an AS load. Cache rollback compensation and a Redis lock do not turn Redis plus SQL into one atomic commit.
- `home-user/src/service/account.ts` provides a token-digest precedent but not an AS lifecycle template. The existing browser login/provider callback and local Passport refresh do not prove an AS authorization/approval surface or a safe browser session handoff; that interaction must be independently designed and tested.

These paths are read-only feasibility inputs, not selected AS source files or evidence of working issuance. No environment values, credentials, raw tokens, or state payloads were inspected or retained for this review.

## Selected logical database authority (physical design open)

**Selected design direction: one AS-owned transactional database authority for authorization request/code/grant linkage and opaque access-token active/revocation state.** Code consumption and resulting token activation belong to one atomic commit rather than separate SQL and Redis authority. This selection favors auditable single-commit behavior and database locking but **does not** approve `a-auth` tables, fields, indexes, migrations, a module dependency, a database product or a runtime service. The exact owning module/service and physical representation remain to be decided. Redis-only is not selected for the first profile; changing to it would require a new direction decision plus fixed TTLs, atomic compare-and-consume, a defined shared deployment/namespace, persistence/eviction policy and current token/revocation view. Generic cache `get`/`del` or process-local maps are insufficient. Mixed SQL+Redis authority is not selected without a new cross-store failure/reconciliation decision.

| Logical state                                  | Proposed authority and invariant                                                                                                                                                                                                                                                                                                                       | Decision still required                                                                                                                            |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pre-registered client and redirect policy      | AS-owned reviewed client records or configuration, separate from upstream login-provider clients. Public clients use PKCE without a secret; confidential clients additionally use an approved authentication method. Registration and authorization-time redirect matching are exact except for a separately approved native-app loopback port policy. | Registry/configuration representation, administrator and credential custody, supported native-loopback forms, onboarding and compatibility limits. |
| Pending authorization request                  | AS-owned shared, short-lived transaction binds issuer, registered client, validated redirect URI, canonical registered resource and instance relation, requested scope, S256 challenge, browser/login correlation and a fixed expiry.                                                                                                                  | Owning service, representation, absolute TTL, cancellation and recovery behavior, privacy classification.                                          |
| Explicit grant and one-time authorization code | After current user authentication and an explicit per-request approve decision, make the pending transaction terminal and create at most one short-lived code represented by a digest or comparably protected lookup. Bind user, approved scope, client, validated redirect, resource, instance and transaction. Denial/cancellation issues no code.   | Exact expiry, atomic approval/denial/expiry state machine, grant history/retention; no remembered-consent record is approved.                      |

Store only a digest or equivalently protected representation, with current MCP profile, issuer, client/grant/subject/resource/instance/scope/issued/expiry/active state stored or unambiguously derived from immutable authoritative linkage.                                 | Token lifetime, digest/key management, revocation policy, retention/deletion and lookup API; no refresh family.                                    |

**Selected atomicity requirement, with terminal-state and isolation details still open:** validate the code, `S256` verifier, registered client/authentication method, the authorization-time redirect binding, mandatory token-request `resource`, approved scope and bound subject/instance against the same authoritative record. OAuth 2.1 draft-13 §10.2 removes token-request `redirect_uri`; it must not be universally required. An explicitly supported OAuth 2.0 compatibility branch instead follows RFC 6749 §4.1.3: when the authorization request included `redirect_uri`, the token request must include the identical value. Merely comparing a supplied value is insufficient for that branch. The code always retains the validated authorization-time redirect binding; the supported profile/compatibility branch still needs a separate decision. Under a single store-owned atomic transaction, consume the code once and activate only the resulting access token. A competing redemption must produce at most one active token. Separately, make approval versus denial/cancellation/expiry and duplicate approval submissions terminal, single-use transitions so the same pending request cannot issue two codes. A failed validation must not mint a token, widen the grant, or consume unrelated state. Specify whether invalid attempts consume or preserve the code before acceptance, and how redemption races with grant/token revocation. A successful commit followed by a lost HTTP response is an uncertain result, not permission to retry issuance with the same code; the client must begin a fresh authorization, without exposing an already committed token. Token lookup checks issuer, MCP profile, active/revoked, grant status and absolute expiry from current AS-owned state on every protected request; cleanup scheduling is not validity enforcement. A missing, stale, ambiguous, unavailable or cross-resource record fails closed, including on another worker. Exact revocation triggers (user logout, account disablement, credential reset, client removal, resource disablement, grant withdrawal), reconciliation, operator action and retention remain open.

**No schema decision is implied.** If the approved physical choice changes a persisted field/schema or `meta.version.ts`, ask whether the owning `vonaModule.fileVersion` increments **before editing**; a separately approved `meta.version.ts` change requires root `npm run test`. Even a Redis/external choice requires explicit namespace, expiration, eviction/persistence, outage and operations approval.

## Selected AS-owned browser direction (exact interaction open)

1. AS validates issuer, registered client, registered redirect (exact except for a separately approved native-app loopback port rule), required canonical registered `resource`, requested narrow scopes, and PKCE challenge with an explicit `S256` method **before** starting a pending transaction. Under RFC 7636, omitted `code_challenge_method` otherwise means `plain`, so omission is rejected by this S256-only profile. Invalid or unregistered redirects fail locally without redirecting to an attacker-supplied URI. Only approved response fields go to the validated redirect.
2. Through a separately approved AS-owned browser interaction, authenticate or re-check the local user for the registered resource's instance, then display the verified client, active account, resource and requested/approved scopes. An existing login session may establish identity, **not consent**; the selected first profile requires an explicit approve or deny action for every authorization request, rather than claiming this is a universal OAuth requirement. Account switching, disabled accounts, session loss and a resource/instance mismatch abort or restart safely rather than inheriting prior authorization.
3. Bind the approval submission to the pending AS transaction and current authenticated user with an independently reviewed CSRF control. Distinguish client-supplied OAuth `state` (opaque client correlation echoed exactly on valid-redirect success/error responses when supplied), AS-owned pending-transaction/browser correlation, upstream provider-login state (if used), form CSRF protection, and the PKCE challenge/verifier. Possession of client `state`, a login cookie or provider callback does not imply grant approval; do not invent a mandatory `state` parameter at the token endpoint.
4. Atomically approve once to issue at most one code for the exact client/validated redirect/resource/instance and a subset of authorized scopes. Deny, cancel, expire or cross-tab/account-switch conflict issues no code or token; any error redirect must first pass registered-redirect validation. Do not persist remembered consent or permit silent approval on later reauthorization.
5. Token exchange requires the original client, `S256` verifier and the same canonical `resource` in the token request; it cannot widen resource, instance or scope. Preserve the validated redirect binding on the code and apply the selected protocol branch: omit a token-request redirect requirement for the OAuth 2.1 draft-13 profile; for an explicitly supported OAuth 2.0 branch require its identical value when provided at authorization (RFC 6749 §4.1.3). Publish truthful metadata including `code_challenge_methods_supported` with `S256`, actual grants/client authentication and no-refresh behavior. Decide whether to implement RFC 9207 authorization-response `iss`; if selected, emit it on every redirectable success **and error**, advertise `authorization_response_iss_parameter_supported: true`, and match the issuer metadata exactly. Errors for invalid client/redirect never redirect. Browser-login session refresh, if used solely to maintain AS identity, is not MCP access-token refresh and cannot bypass a new grant decision.

The selected direction assigns the browser authorization/grant flow to the integrated `a-auth` AS, **not** to a separate Zova frontend; AS backend-rendered HTML is the selected presentation direction. Its AS request-to-instance admission point before any Vona instance initialization, exact backend HTML routes/renderer, server-verifiable session or login identity bridge, same-origin/CSRF and clickjacking policy, login continuation, form-cache and redirect-leakage controls, and compatible clients are **not selected**. ADR 0004's proposed early `/mcp`/protected-resource-metadata hook does not by itself cover AS authorization, approval or token routes; do not infer that an AS-side instance binding exists from the RS design. No Zova authorization site is selected; the AS backend HTML page still requires its own source, privacy, browser-security and real-HTTP verification scope. The protected `/mcp` endpoint still rejects cookies and ordinary login JWTs as credentials.

## Remaining decisions before execution readiness

1. The transactional database **class** and database-neutral contract direction are selected; choose the deployed dialect, exact AS module/service, transaction authority and operations topology, and verify dialect-specific serialization, conditional writes and migration without recording live secrets or endpoints. Decide whether client registration uses reviewed configuration or transactional state. Do not read this selection as permission to create schema.
2. Decide code/request/token absolute TTLs, retention/deletion and privacy policy, digest/custody, fixed-versus-sliding expiration, atomic redemption/revocation, inter-worker consistency, outage response and recovery. Demonstrate one active issuance at most under competing redemptions and a truthful lost-response outcome.
3. The AS-owned browser flow and backend-rendered HTML presentation are selected; choose the exact HTML routes/renderer, resource-to-instance registry lookup, server-verifiable identity/session or login bridge, user/session continuity, independently enforced CSRF and browser response protections. Decide denial/cancellation, cross-tab, account-switch, disabled-user and invalid-redirect behavior; keep client `state`, AS correlation and provider state separate.
4. Confirm issuer/discovery topology, registration of the canonical resource/instance, exact pre-registered client/redirect forms and confidential authentication method, supported-client compatibility, scope vocabulary and access lifetime. Define the issuer/profile linkage returned by current token lookup and a separate AS-side request-to-instance admission point before ordinary Vona initialization; the proposed ADR 0004 RS hook does not provide this. Settle metadata fields, response `iss` behavior and any OAuth 2.0 token-request redirect compatibility against authoritative OAuth/MCP references before implementation; this review is not a conformance claim.
5. Decide terminal pending-request transitions, concurrent approval/denial/expiry, code-redemption/revocation races and lost-response behavior in addition to one-time redemption. If a schema edit is proposed, ask the owning module's `vonaModule.fileVersion` question before editing. Approve the exact physical representation and any UI/site scope separately, update the governing ADR/SRS/WBS and prospective ATP procedures **before** seeking a separate bounded execution decision, then re-review the [AS execution dossier](./wbs-mcp-20-04-execution-dossier.md). Runtime ATP evidence follows only after approved implementation.

## Prospective verification and current disposition

The prospective `ATP-MCP-AUTH-03` procedures now cover public/confidential clients; invalid PKCE and `resource` inputs; redirect mismatches; client/AS/upstream state separation and authorization-response metadata; denied, cancelled, duplicate-submitted, cross-tab, account-switched and CSRF-rejected browser flows; concurrent and replayed code redemption; committed-but-lost response; wrong-instance/resource/scope exchange; current cross-worker revocation and store outage. Refine these cases for the approved physical store, browser implementation and optional native-loopback policy before execution. This is prospective test-plan authority, not an executed ATP. Execute it only after design, source and safe-fixture approval; retain only synthetic labels, procedure/interleaving, counts and redacted outcomes. The actual AS/browser UI, database/Redis topology and test fixture must exist before these are executable; `ATP-MCP-AUTH-01` remains separate RS proof.
