## 2. Contract state vocabulary and approval rule

Each row below uses one of these dispositions:

- **Observed fact** — confirmed in current source or an existing planning authority; it is not a target decision.
- **Proposed review candidate** — a finite recommendation prepared for separate approval; it does not settle its proposed values, attest deployment, or permit execution.
- **Bounded direction accepted** — the user accepted the direction or a first implementation target only; remaining concrete values and implementation remain gated.
- **Decision required** — a user-owned design choice is needed before execution review.
- **Execution proof required** — the contract may be selected, but implementation-specific behavior must be demonstrated before closure.
- **Not selected** — explicitly outside this first profile.

A row marked **decision required** blocks the relevant execution gate. No row may be promoted by a chart, static audit, source reading, successful method return, or planning status update. Concrete approval must be recorded in the owning ADR/SRS/WBS authority before source or persisted-state work begins. The user must approve physical-state rows and browser rows separately; approving this dossier's preparation is not approval of those rows.

## 5. First-profile protocol and trust contract

The following is the recommended contract shape for separate approval. Concrete issuer, endpoint, client, resource, scope, and compatibility values remain `decision required`.

### 5.1 Selected bounded protocol behavior

- Accept only pre-registered public and confidential clients in the first profile. Dynamic Client Registration is not selected; any Client ID Metadata Documents compatibility is explicitly documented rather than assumed.
- Use Authorization Code with explicit PKCE `S256`. An omitted `code_challenge_method` is rejected under the strict profile; it must not silently fall back to RFC 7636 `plain`.
- Validate the redirect URI against the registered exact value before any redirectable response. Invalid, unknown, or ambiguous redirect input must terminate locally and must never become a redirect target.
- Bind the authorization transaction and resulting grant to the canonical registered `resource`, enabled resource-to-instance relation, client, exact authorization-time redirect, requested narrow scopes, and PKCE challenge. Client OAuth `state` is correlation for the validated redirect, not a token-endpoint credential.
- Issue only high-entropy MCP-specific opaque access tokens. The resource server validates current authoritative state on every protected request. Ordinary Cabloy JWTs, Redis session markers, provider tokens, temporary OAuth-code JWTs, cookies, and Passport state are not MCP token authority.
- Do not issue refresh tokens, advertise refresh capability, or remember consent in this profile. An expired access token requires reauthorization. Any refresh profile requires a new decision and separate rotation/reuse/outage proof.
- Keep issuer comparison, resource canonicalization, local instance relation, and subject mapping as separate checks. A client-supplied resource or state value cannot select a tenant, instance, identity, or redirect.

## 6. AS-owned physical state and transition contract

### 6.1 Invariants that must hold regardless of representation

1. The AS owns one authoritative state boundary for authorization request, code/grant linkage, and current MCP opaque-token state. `cabloy-mcp` owns none of those records.
2. Each authorization request is bound to one trusted instance, issuer/profile, pre-registered client, exact redirect, canonical resource, enabled resource-instance relation, narrow scope set, explicit `S256` challenge, browser binding, and absolute expiry.
3. A pending request has one winning transition to approved/code-ready or one terminal denial/cancellation/expiry. A losing worker must not issue or reconstruct a code.
4. Redemption verifies the client, original binding, code secret, PKCE verifier, canonical resource, scope, expiry, revocation and selected redirect branch. **Code consumption and resulting token activation must be one committed atomic outcome.** A single conditional mutation is acceptable only if the deployed dialect and driver prove the complete outcome and reliable exactly-one winner result. Multiple writes require an approved atomic transaction or a new authority decision.
5. The raw code/token exists only in request memory and the one intended response; state stores a protected digest or equivalent non-recoverable representation. No raw credential is logged or retained in evidence.
6. Current token lookup is fresh and authoritative. Missing, stale, ambiguous, expired, revoked, disabled, or unavailable state fails closed. A lookup begun after acknowledged revocation cannot use an older ambient snapshot, positive cache, or stale replica to accept the grant.
7. A committed-but-lost response or unknown commit acknowledgment never authorizes retry/reissuance. A returned model, successful preliminary read, or method return inside an uncommitted ambient transaction is not commit proof.
8. Revocation is monotonic and visible to every worker under the selected topology. Cleanup is not validity enforcement.
9. Tenant-aware business uniqueness is enforced by the approved business/conditional-creation strategy. `table.unique(...)` is not a substitute for shared-instance business uniqueness.

### 6.3 ORM and transaction gate

The dossier does not bless a particular SQL statement, isolation level, lock, or ORM API. Before execution, the implementation dossier must confirm the actual deployment matches the selected SQLite/`better-sqlite3` primary-datasource target and demonstrate all of the following against that driver; another deployed dialect requires a separate AS-support decision and proof:

- the mutation addresses exactly one trusted aggregate and includes the full instance/deleted/status/revision/expiry/revocation predicate;
- a successful result proves one committed winner, while zero, more-than-one, or unknown affected-row outcome fails closed;
- cache-layer preselection cannot discard the state predicate;
- lower-level builders explicitly carry instance/deleted scope and redact SQL/error/binding output;
- ambient `REQUIRED` transactions cannot let a token become externally valid before the owning commit, and current lookup cannot inherit a stale snapshot after acknowledged revocation;
- if more than one durable record is needed, code consumption and token activation are committed atomically; and
- an uncertain commit acknowledgment cannot be handled by replaying issuance.

## 7. Browser-presented AS contract

### 7.1 Required trust boundary

Zova presents the authorization summary and approve/deny choices. The AS remains authoritative for authentication verification, site/role admission, current request state, scope intersection, approval/denial, code issuance, token activation, and final redirect. A frontend flag, hidden field, pending reference, OAuth `state`, or browser possession alone is never an authorization decision.

The recommended flow, subject to separate approval, is:

1. The AS validates client, exact redirect, canonical resource, scope, strict PKCE, and enabled resource-instance relation before creating pending state.
2. The AS admits the request to a trusted instance before ordinary Vona initialization on the relevant path. It separates issuer-global and instance-bound routes.
3. If login is needed, the AS uses a fixed internal continuation bound to the pending request. It never forwards the client redirect or arbitrary `returnTo` to existing login helpers.
4. A same-origin bootstrap/bridge explicitly verifies the existing access token through the approved identity primitive, active account and activation/site rules, and binds the verified subject to a short-lived AS-owned HttpOnly session. The bridge is not the frontend Passport cookie and is not an existing temporary OAuth/JWT credential.
5. The protected Zova page obtains only a minimal escaped summary after admission. Its model state is nonpersistent and nondehydrated, and the server/hydration shell is equivalent.
6. A native same-origin decision POST carries an independent request-bound CSRF proof. The AS revalidates current identity, instance, registration, redirect, resource, scope, browser binding, expiry and pending status, then commits approve or deny.
7. Only the AS constructs a redirect to the previously validated callback. Invalid redirect input terminates locally. An AJAX response containing a URL is not itself top-level navigation.

### 7.3 Distinct correlation values

The implementation contract must keep these values separate in storage, validation, lifecycle and redaction:

- OAuth client `state`: authorization-response correlation for the prevalidated callback;
- AS pending/browser locator: server-side request addressing only;
- browser bridge/session identifier: AS-authenticated browser binding;
- upstream provider-login state, if any: provider callback correlation only;
- decision CSRF token: request-bound browser form protection; and
- PKCE challenge/verifier: authorization-code proof, not browser identity or redirect authorization.

No one of these values may be accepted in place of another.

### 9.6 Logical representation and lifecycle (bounded design accepted)

The accepted logical representation is **one durable authorization aggregate per request** covering pending request, approval/code assignment, grant and resulting access-token state. This makes the same-commit boundary reviewable without presuming a multi-statement transaction. A logical aggregate does not establish that one SQL row or any particular update is sufficient. The later schema must demonstrate that its actual representation implements these groups and invariants; a multi-record alternative must reconcile the atomic boundary before acceptance.

| Logical group                    | Accepted logical content and authority                                                                                                                                                                       | Remaining concrete decision                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Aggregate identity and binding   | Server-owned aggregate locator, trusted instance, issuer/profile, registered client identity and registration revision, exact bound redirect, canonical resource/relation, requested and approved scope sets | Physical identifiers/types/limits, registration-change behavior, canonicalization and creation uniqueness                                    |
| Request lifetime and correlation | Creation/deadline, PKCE `S256` challenge, separately bound browser/decision correlation, optional client `state` used only for authorization response                                                        | Clock/skew/TTL, storage/minimization of correlation, concrete bridge/CSRF lifecycle; no raw cookie or signed provider state storage selected |
| Decision and approved grant      | Lifecycle/revision, verified subject when bound, explicit decision and approved narrow scopes, decision time; no remembered consent                                                                          | Exact subject/admission checks, immutable-field rules, permitted revision changes and minimized audit projection                             |
| Code phase                       | Nonrecoverable code verifier representation and domain, code deadline, transition marker                                                                                                                     | Wire encoding/entropy/digest/custody and predicate implementation; raw code never durable                                                    |
| Access-token phase               | Independent token verifier representation and domain, activation/deadline, current grant/client/subject/resource/scope binding                                                                               | Token format/digest, validity checks, current client/subject policy; raw token never durable                                                 |
| Terminal and revocation state    | Monotonic denial/cancellation/revocation information, lifecycle revision and relevant timestamps                                                                                                             | Exact reason allowlist, revocation ordering, retention/deletion and cleanup owner                                                            |

Accepted logical lifecycle labels are `pending`, `code-ready`, `token-active`, `denied`, `cancelled`, `revoked` and effective `expired`. These are review labels, not column values or an enum implementation. Deadline failure makes a phase invalid immediately even if no cleanup/status write runs. `code-ready` is a successful explicit approval, not reusable consent; entering `token-active` is the same committed event that makes the code unusable. A later authorization request creates a new aggregate, not a reset of this one.

| Transition / read          | Accepted logical rule                                                                                                                                                                                           | Release / failure boundary                                                                                                                                    |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create → pending           | Validate registration, exact redirect, resource/instance relation, narrow scopes and explicit S256; trusted scoped creation with collision/ambiguity handling                                                   | Locator alone grants no decision, redemption or lookup authority; no code/token yet                                                                           |
| Pending → code-ready       | Full current pending/revision/deadline/not-revoked predicate plus independently authenticated subject/site/browser/CSRF decision; code verifier assigned with the winning decision                              | Release the raw code only after one acknowledged committed winner; losing/unknown outcome never reconstructs a code                                           |
| Pending → denied/cancelled | Compete with approval using the same pending boundary; no code/token assignment                                                                                                                                 | Final redirect/local response follows the separately approved protocol/browser contract                                                                       |
| Code-ready → token-active  | Verify code secret, PKCE, client auth and all original bindings; full scoped lifecycle/revision/expiry/revocation predicate; consume code and install token verifier/activation in one atomic committed outcome | Exactly-one affected effect and acknowledged owning commit required; preliminary read, cached Model return or uncommitted ambient transaction is insufficient |
| Revocation / expiry        | Revocation only narrows authority; expired code cannot activate a token and expired/revoked access cannot validate                                                                                              | No resurrection/replay; code and token have different deadlines, so code expiry after valid redemption does not by itself expire the resulting token          |
| Current access lookup      | Fresh scoped authoritative current-token/grant check with current expiry/revocation and the approved validity policy                                                                                            | No positive token cache, stale replica, old ambient snapshot or readiness bit substitutes for current state                                                   |

A failed/ambiguous commit or committed-but-lost response does not allow automatic replay, token recovery or reissuance. Exact SQL, cache bypass, row-count handling, ambient-transaction prohibition/ownership, creation serialization, secret-safe logging and cross-worker proof remain separate decisions. Do not select `table.unique(...)` for tenant business uniqueness or treat `getForUpdate()` as a winner primitive. Client registration and the browser bridge are interfaces to this aggregate, not newly selected tables or additional grant authorities; their representations remain open.

### 9.7 Read-only activation responsibilities and timing (bounded design accepted)

The accepted responsibility/timing contract is a **layered AS-owned gate**, not a single `ready=true` flag. Operations attestation, physical schema compatibility, trusted routing, instance/account admission and fresh credential validity answer different questions. None can replace another. Gate results are internal bounded classifications, not token authority or externally diagnostic errors.

| Layer / timing                                           | Accepted responsibility and timing                                                                                                                                                                | Failure boundary                                                                                                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authorized installation preflight, before fresh creation | Operations/migration boundary confirms a newly provisioned clean physical target, absent prior auth/AS objects/history and intended routing under a separately approved allowlisted procedure     | Missing history alone cannot pass; incompatible/nonfresh/partial/unknown targets remain blocked; this candidate performs no provisioning or preflight |
| After acknowledged creation, before first AS use         | Readiness owner compares physical target, completed module history and the exact later-approved physical contract with accepted installation provenance and artifact/contract revision            | A v1 record/table name alone cannot pass; failed creation or incomplete physical contract keeps AS unavailable; no startup DDL, repair or replay      |

| Every decision/redemption/lookup/revocation              | Authorization owner enforces current scoped state, complete transition predicate/commit boundary or fresh lookup, independently of structural readiness                                           | Schema readiness does not prove current grant validity, committed winner, browser identity or revocation freshness                                    |
| Restart / artifact / routing / storage change            | Re-evaluate affected worker/instance/physical-contract coverage; operations re-attests relevant deployment fields through a separately authorized procedure                                       | No inherited unqualified process-local success or cross-worker readiness promise; loss of verifiable continuity blocks use                            |

**Fresh creation versus later restart:** a successfully completed, separately approved fresh-v1 creation naturally leaves a v1 record. The accepted continuity rule permits later restart of that _same eligible installation_, not a new upgrade/adoption path, only when allowlisted provenance, target identity and artifact/physical-contract compatibility remain verifiable. This bounded acceptance is not permission to admit arbitrary existing-v1 databases. A matching schema/marker or a claim of prior creation is insufficient. Exact provenance producer, binding, integrity/retention, restart verification and lifecycle are `TODO(confirm)`; no provenance table, signed artifact, repair journal or secret retention is selected here. **Timing and ordering:** an asynchronous schema/readiness check must occur only after trusted instance admission and actual datasource resolution, and before authority use; it cannot be inserted into the synchronous pre-instance selector or used to repair wrong-instance admission. A worker-startup preflight may provide an availability hint only for routes it truly covers. Dynamic or lazily initialized instances still require the actual bound check. No exact startup hook is selected merely because it has an `execute()` method, and no lifecycle hook is assumed to cover every worker or routed datasource.

**Freshness and coherence:** the accepted requirement starts fail-closed, with no long-lived positive readiness shortcut. Every authority entry must establish that its installed contract and effective binding are still the checked ones, using a separately approved read-only validation procedure; until a bounded reuse/invalidation contract is explicitly selected, a cached readiness result cannot admit an operation. Recheck/invalidation on artifact, routing or storage changes is mandatory. A separate pre-read does not make a later write race-free or prove a snapshot fresh. Runtime schema/routing changes without an approved quiescence/coherence boundary are unsupported; if the checker cannot establish a coherent binding through the operation, it must not proceed. No locking algorithm, extra connection, pool/timeout, polling interval or fingerprint scheme is selected.

**Conceptual internal outcome classes (not source enums or mappings):** `unconfirmed`, `eligible-and-compatible`, `excluded-installation`, `incompatible-contract`, `routing-mismatch`, `authority-unavailable`. They are conceptual outcome classes, not source enums, HTTP statuses or retained raw diagnostics. Missing/unknown/failed checks never become `eligible-and-compatible`; unavailable revocation must not be acknowledged as completed. Public protocol/error mappings remain open. Limit readiness failure to the affected AS authority/instance; do not change ordinary login/provider behavior or globally disable unrelated capabilities. A combined process that serves both AS and RS must also deny current-token acceptance when the authority cannot be confirmed, without JWT/Redis/process-local fallback.

Do not read unrelated tenant business rows to classify installations. Physical module history/schema checks are not cross-instance authorization probes and must use an approved least-privilege, secret-safe procedure. Retain only allowlisted contract revision, synthetic worker/instance/target aliases, check classification and redacted result references; no raw schema, SQL/bindings, paths, configuration, secrets or credential data. ### 9.11 Reuse, invalidation and coherence limits (bounded design accepted)

Concrete admission/drain enforcement, coverage membership, timeouts and deployment control remain `TODO(confirm)`; no command or operative lock is introduced here.

Concurrent business-state transitions still require their own complete predicates, atomic commit and fresh-read proof; quiescence is not a global authorization lock or contention algorithm.

### 9.18 State shapes and conditional transition contract (bounded design accepted)
