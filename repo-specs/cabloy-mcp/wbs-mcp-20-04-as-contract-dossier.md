# WBS-MCP-20-04 Concrete AS Contract Dossier

## 1. Disposition, scope, and authority

**Design-only contract dossier; not execution approval.** This record turns the bounded directions already accepted by [ADR 0009](./decisions/0009-mcp-as-state-boundary.md) and the [physical/browser decision dossier](./wbs-mcp-20-04-physical-browser-decision-dossier.md) into a finite review and sign-off surface for the integrated `a-auth` authorization server (AS). It does not create an AS, establish the actual deployment database, select a schema, add a browser route, or establish runtime evidence.

The current disposition is:

- Cabloy Basic is the active edition; the only edition marker is `__CABLOY_BASIC__`.
- `a-auth` is the selected **logical** AS owner. `cabloy-mcp` remains the resource-server owner and must not issue credentials, own grants/consent, or create a second token authority.
- The first profile is pre-registered public/confidential clients, Authorization Code, strict PKCE `S256`, exact redirect validation, canonical `resource` binding, MCP-only opaque access tokens, current authoritative lookup, explicit approve/deny on every request, and no refresh tokens or remembered consent.
- The accepted physical direction is one trusted-instance-scoped AS authorization aggregate per request, addressed by a non-authoritative locator and independent high-entropy-secret opaque credentials, with complete conditional transitions, same-commit code consumption/token activation, and fresh fail-closed lookup. A multi-record representation remains possible only if it is reconciled with the same invariant before execution.
- The accepted browser direction is evaluation of the observed Basic Web site with a narrow Zova-presented AS page, an AS-verifiable short-lived HttpOnly bridge, fixed internal continuation, independent request-bound CSRF, synchronous per-path early instance admission, and an AS-built final redirect.
- On 2026-10-15, the user selected SQLite via `better-sqlite3` as the first AS implementation target on Vona's existing primary datasource. This is a bounded target choice, not an observation of actual deployment configuration, an approved schema or transition mechanism, or SQLite atomicity proof; PostgreSQL/MySQL AS support remains unselected.
- The further 2026-10-15 inputs select same-host multiple Vona workers sharing persistent SQLite through that primary datasource and, if persistence resides in existing `a-auth`, keeping `vonaModule.fileVersion: 1` and folding the AS schema into its version-1 creation path. No version-2 migration or automatic upgrade of already-recorded v1 databases is selected. Installation applicability remains open; cross-host SQLite and replica support are not selected.
- Other concrete values in this dossier remain `decision required` unless explicitly marked as an observed fact or an already accepted bounded direction.
- `WBS-MCP-20-04`, dependent `WBS-MCP-20-02`, and `ATP-MCP-AUTH-03` remain blocked/prospective. No source, schema, configuration, dependency, provider, deployment, runtime test, credential, or ATP evidence follows from this record.

This dossier is subordinate to the PRD/SRS and does not replace the [AS execution dossier](./wbs-mcp-20-04-execution-dossier.md). The PRD owns outcomes, the SRS owns technical contracts, the PDP/WBS owns delivery order, the test plan owns ATP procedures and evidence, ADRs own durable decisions, and progress is derived status only.

## 2. Contract state vocabulary and approval rule

Each row below uses one of these dispositions:

- **Observed fact** — confirmed in current source or an existing planning authority; it is not a target decision.
- **Proposed review candidate** — a finite recommendation prepared for separate approval; it does not settle installation applicability, attest deployment, or permit execution.
- **Bounded direction accepted** — the user accepted the direction or a first implementation target only; remaining concrete values and implementation remain gated.
- **Decision required** — a user-owned design choice is needed before execution review.
- **Execution proof required** — the contract may be selected, but implementation-specific behavior must be demonstrated before closure.
- **Not selected** — explicitly outside this first profile.

A row marked **decision required** blocks the relevant execution gate. No row may be promoted by a chart, static audit, source reading, successful method return, or planning status update. Concrete approval must be recorded in the owning ADR/SRS/WBS authority before source or persisted-state work begins. The user must approve physical-state rows and browser rows separately; approving this dossier's preparation is not approval of those rows.

## 5. First-profile protocol and trust contract

The following is the recommended contract shape for separate approval. Concrete issuer, endpoint, client, resource, scope, and compatibility values remain `decision required`.

### 5.1 Selected bounded protocol behavior

- Accept only pre-registered public and confidential clients in the first profile. Dynamic Client Registration is not selected; any Client ID Metadata Documents compatibility is explicitly documented rather than assumed.
- Use Authorization Code with explicit PKCE `S256`. An omitted `code_challenge_method` is rejected under the strict profile; it must not silently fall back to RFC 7636 `plain`.
- Validate the redirect URI against the registered exact value before any redirectable response. Invalid, unknown, or ambiguous redirect input must terminate locally and must never become a redirect target.
- Bind the authorization transaction and resulting grant to the canonical registered `resource`, enabled resource-to-instance relation, client, exact authorization-time redirect, requested narrow scopes, and PKCE challenge. Client OAuth `state` is correlation for the validated redirect, not a token-endpoint credential.
- Issue only high-entropy MCP-specific opaque access tokens. The resource server validates current authoritative state on every protected request. Ordinary Cabloy JWTs, Redis session markers, provider tokens, temporary OAuth-code JWTs, cookies, and Passport state are not MCP token authority.
- Do not issue refresh tokens, advertise refresh capability, or remember consent in this profile. An expired access token requires reauthorization. Any refresh profile requires a new decision and separate rotation/reuse/outage proof.
- Keep issuer comparison, resource canonicalization, local instance relation, and subject mapping as separate checks. A client-supplied resource or state value cannot select a tenant, instance, identity, or redirect.

## 6. AS-owned physical state and transition contract

### 6.1 Invariants that must hold regardless of representation

1. The AS owns one authoritative state boundary for authorization request, code/grant linkage, and current MCP opaque-token state. `cabloy-mcp` owns none of those records.
2. Each authorization request is bound to one trusted instance, issuer/profile, pre-registered client, exact redirect, canonical resource, enabled resource-instance relation, narrow scope set, explicit `S256` challenge, browser binding, and absolute expiry.
3. A pending request has one winning transition to approved/code-ready or one terminal denial/cancellation/expiry. A losing worker must not issue or reconstruct a code.
4. Redemption verifies the client, original binding, code secret, PKCE verifier, canonical resource, scope, expiry, revocation and selected redirect branch. **Code consumption and resulting token activation must be one committed atomic outcome.** A single conditional mutation is acceptable only if the deployed dialect and driver prove the complete outcome and reliable exactly-one winner result. Multiple writes require an approved atomic transaction or a new authority decision.
5. The raw code/token exists only in request memory and the one intended response; state stores a protected digest or equivalent non-recoverable representation. No raw credential is logged or retained in evidence.
6. Current token lookup is fresh and authoritative. Missing, stale, ambiguous, expired, revoked, disabled, or unavailable state fails closed. A lookup begun after acknowledged revocation cannot use an older ambient snapshot, positive cache, or stale replica to accept the grant.
7. A committed-but-lost response or unknown commit acknowledgment never authorizes retry/reissuance. A returned model, successful preliminary read, or method return inside an uncommitted ambient transaction is not commit proof.
8. Revocation is monotonic and visible to every worker under the selected topology. Cleanup is not validity enforcement.
9. Tenant-aware business uniqueness is enforced by the approved business/conditional-creation strategy. `table.unique(...)` is not a substitute for shared-instance business uniqueness.

### 6.3 ORM and transaction gate

The dossier does not bless a particular SQL statement, isolation level, lock, or ORM API. Before execution, the implementation dossier must confirm the actual deployment matches the selected SQLite/`better-sqlite3` primary-datasource target and demonstrate all of the following against that driver; another deployed dialect requires a separate AS-support decision and proof:

- the mutation addresses exactly one trusted aggregate and includes the full instance/deleted/status/revision/expiry/revocation predicate;
- a successful result proves one committed winner, while zero, more-than-one, or unknown affected-row outcome fails closed;
- cache-layer preselection cannot discard the state predicate;
- lower-level builders explicitly carry instance/deleted scope and redact SQL/error/binding output;
- ambient `REQUIRED` transactions cannot let a token become externally valid before the owning commit, and current lookup cannot inherit a stale snapshot after acknowledged revocation;
- if more than one durable record is needed, code consumption and token activation are committed atomically; and
- an uncertain commit acknowledgment cannot be handled by replaying issuance.

## 7. Browser-presented AS contract

### 7.1 Required trust boundary

Zova presents the authorization summary and approve/deny choices. The AS remains authoritative for authentication verification, site/role admission, current request state, scope intersection, approval/denial, code issuance, token activation, and final redirect. A frontend flag, hidden field, pending reference, OAuth `state`, or browser possession alone is never an authorization decision.

The recommended flow, subject to separate approval, is:

1. The AS validates client, exact redirect, canonical resource, scope, strict PKCE, and enabled resource-instance relation before creating pending state.
2. The AS admits the request to a trusted instance before ordinary Vona initialization on the relevant path. It separates issuer-global and instance-bound routes.
3. If login is needed, the AS uses a fixed internal continuation bound to the pending request. It never forwards the client redirect or arbitrary `returnTo` to existing login helpers.
4. A same-origin bootstrap/bridge explicitly verifies the existing access token through the approved identity primitive, active account and activation/site rules, and binds the verified subject to a short-lived AS-owned HttpOnly session. The bridge is not the frontend Passport cookie and is not an existing temporary OAuth/JWT credential.
5. The protected Zova page obtains only a minimal escaped summary after admission. Its model state is nonpersistent and nondehydrated, and the server/hydration shell is equivalent.
6. A native same-origin decision POST carries an independent request-bound CSRF proof. The AS revalidates current identity, instance, registration, redirect, resource, scope, browser binding, expiry and pending status, then commits approve or deny.
7. Only the AS constructs a redirect to the previously validated callback. Invalid redirect input terminates locally. An AJAX response containing a URL is not itself top-level navigation.

### 7.3 Distinct correlation values

The implementation contract must keep these values separate in storage, validation, lifecycle and redaction:

- OAuth client `state`: authorization-response correlation for the prevalidated callback;
- AS pending/browser locator: server-side request addressing only;
- browser bridge/session identifier: AS-authenticated browser binding;
- upstream provider-login state, if any: provider callback correlation only;
- decision CSRF token: request-bound browser form protection; and
- PKCE challenge/verifier: authorization-code proof, not browser identity or redirect authorization.

No one of these values may be accepted in place of another.
