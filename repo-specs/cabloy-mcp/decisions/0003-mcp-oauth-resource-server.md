# ADR 0003: MCP OAuth Resource-Server Boundary

## Current bounded supersession (2026-10-23)

[ADR 0010](./0010-mcp-browser-execution-profile.md) controls the approved browser-to-MCP increment: AS ownership moves to backend `cabloy-mcp/modules/mcp-auth`, consent presentation to Zova `cabloy-mcp/modules/cabloy-mcp`, and existing SSR cookie/login/API authentication is reused without a new bridge. It supersedes incompatible unimplemented ownership/mechanism gates and former preparation handoffs below, not OAuth/tenant/local-authorization invariants. The current client path is RFC 7591 DCR only for public and confidential clients; static-client configuration and compatibility are removed. The approved 2026-10-24 simplification removes authored `mcp-auth.issuer`/`resources` and `registration.enabled`: issuer and resource are both the exact `${origin}/mcp` derived from root backend `server.serve.protocol`/`host`, with a nonproduction requestless `http://localhost:<SERVER_LISTEN_PORT>` fallback and a required public serve pair in production. Validate Host and use existing automatic instance routing in a fresh selector-free context, not an MCP resource/instance registry; arbitrary Host/proxy input cannot mint authority. DCR and `registration_endpoint` follow existing AS/MCP ingress availability, retaining body/redirect and rate limits. `allowLoopbackHttp` defaults to `true`, supports explicit `false`, and permits HTTP only for exact `localhost`, `127.0.0.1` or `[::1]`. AS metadata is canonically `/.well-known/oauth-authorization-server/mcp`; `/mcp/auth`, `/mcp/token`, `/mcp/register` and PRM `/.well-known/oauth-protected-resource/mcp` remain. Old origin-only issuer grants/codes/tokens fail exact comparison and require new authorization, not reset. Public/confidential authentication, scope/resource binding, PKCE, consent and existing identity remain unchanged. E2E uses normal defaults without the special backend injection/helper. The user-approved `mcp-auth` strategy keeps `fileVersion: 1` and creates both authorization and client tables in v1; it does not change `a-auth`, add a v2 migration, authorize reset or automatically replay v1 against existing databases. Historical design-only status and evidence limits below are not current execution blockers for that approved slice, nor proof of runtime or release acceptance.

## Historical status

**Accepted for design only — not implementation, configuration, or runtime proof.** On 2026-10-09, the accountable decision owner `zhennann` accepted the bounded design disposition recorded in [the AS design review dossier](../wbs-mcp-20-04-as-design-review.md): keep `cabloy-mcp` as a separate resource server, support pre-registered public/confidential clients with Authorization Code + PKCE S256, use MCP-specific opaque access tokens with current server-owned lookup, and use **no refresh-token issuance in the first profile**. The 2026-10-23 bounded implementation supersession in [ADR 0010](./0010-mcp-browser-execution-profile.md) implements RFC 7591 Dynamic Client Registration as the only public/confidential client-registration path in `mcp-auth`, without static compatibility; the later 2026-10-24 simplification removes the original opt-in switch, as recorded above; this paragraph preserves the historical design baseline and does not claim that the older record alone authorized implementation. On 2026-10-10, `zhennann` selected an integrated `a-auth` logical AS route and accepted responsibility for AS implementation and operations. The separately operated AS remains an alternative only through a future decision. The separately recorded [ADR 0009](./0009-mcp-as-state-boundary.md) permits planning for AS-owned shared authorization state and, as revised on 2026-10-11, selects one AS-owned database-backed authority with code consumption and token activation in one atomic commit and Zova presentation of the AS per-request approval/denial as **bounded design directions**. It does not assume a default explicit multi-statement transaction or authorize a physical database, schema, Zova site/flavor/SSR/admission, identity/session/CSRF implementation, durable consent record, provider, endpoint, dependency, source, OAuth operation, or ATP. The earlier deny-on-JWKS-refresh-failure sub-policy remains only for a future JWT/JWKS alternative and is not the selected opaque-token profile.

The accepted design still leaves concrete issuer and endpoint/resource registration, storage representation and availability, client records, resource-owner interaction implementation, scope vocabulary, subject mapping, and HTTP/runtime behavior for separate authority and proof. Naming an operations owner is not approving a deployed operator configuration. `WBS-MCP-20-04` remains blocked until those gates and a separate execution approval are resolved.

This accepted design defines the OAuth boundary for the remote MCP endpoint described by [ADR 0002](./0002-mcp-transport.md). It keeps transport wire behavior in DEC-MCP-02 and trusted host/domain-to-instance binding in DEC-MCP-04. DEC-MCP-03 and DEC-MCP-04 must agree on the shared resource/instance interface below, but neither draft's **acceptance** presupposes that the other has already been accepted. Their joint integration and real-HTTP proof remain separate execution gates.

## Current-source findings

The inspected Cabloy Basic source does not provide a complete MCP OAuth authorization-server/resource-server contract, but it does provide reusable authentication and token primitives:

- `vona/src/suite-vendor/a-auth/modules/auth-oauth/src/bean/authProvider.oauth.ts` registers OAuth **login/provider** strategies (the observed default is GitHub) and supports authorization-code login flows; it is not by itself an MCP protected-resource metadata publisher, authorization-code/token endpoint, or bearer-token resource validator.
- `vona/src/suite-vendor/a-vona/modules/a-jwt/src/service/jwtClient.ts` provides Cabloy JWT signing/verification using application configuration and issuer settings. This is a reusable token primitive, not by itself an MCP access-token profile or resource/audience/scope contract.
- `vona/src/suite-vendor/a-vona/modules/a-jwt/src/bean/bean.jwt.ts` exposes access/refresh JWT creation and temporary access-token creation. These capabilities are reference points; ordinary tokens must not be accepted as MCP credentials without an explicit MCP profile.
- `vona/src/suite-vendor/a-vona/modules/a-jwt/src/service/jwtExtract.ts` checks a configured query token before the Authorization header. MCP must not reuse that broad extraction path: protected calls accept only an HTTP `Authorization: Bearer` credential, never query, cookie, or an unrelated custom token header.
- `vona/src/suite-vendor/a-vona/modules/a-user/src/bean/bean.passport.ts` owns local Passport serialization, auth-token refresh, and temporary-token helpers. Its default refresh strategy retrieves an existing session marker and extends its TTL before issuing a new JWT pair; it does not consume the previous refresh JWT or track a refresh-token family. It is a possible identity foundation, not MCP OAuth refresh rotation.
- `vona/src/suite-vendor/a-vona/modules/a-user/src/service/redisToken.ts` stores one instance-scoped session marker keyed by local user/auth identity, not a token-hash-to-grant lookup or consent/revocation ledger. `vona/src/suite-vendor/a-auth/modules/a-auth/src/bean/meta.version.ts` creates provider and user-auth association tables, not MCP client/grant/token tables.
- `vona/src/suite/a-home/modules/home-user/src/controller/passport.ts` exposes the existing user-facing refresh and temporary-token endpoints. Their browser/application semantics must not be widened to MCP without a profile and audience/resource review.

These observations are source facts with limits, not implementation authorization. No currently inspected owner establishes a complete MCP authorization-server or opaque-token lifecycle.

## Accepted first-profile design (bounded)

### Ownership and deployment model

The accepted first-profile route is a **Cabloy-integrated OAuth authorization server** under the `a-auth` logical capability, sharing Vona identity ownership but exposing a distinct MCP AS contract. `zhennann` owns implementation and operations for this AS route, including issuer metadata, client/redirect registration, authorization interaction, token-state availability and revocation, credential custody, incident response and retention policy. This named responsibility does not select values or authorize deployment. The `cabloy-mcp` resource-server boundary separately owns protected-resource metadata, Bearer access-token validation, resource/scope checks, and local subject/instance mapping; it does not receive refresh tokens.

The existing `a-auth` login/provider flow is a foundation to evaluate, not an automatic MCP authorization server. The exact issuer identifier, public endpoints, client records, shared-state representation, retention and worker consistency remain `TODO(confirm)` before implementation. Metadata must not expose client secrets, private keys, internal topology, or local Passport details. A separately operated AS is a later alternative requiring a new explicit selection.

The MCP authorization server must satisfy the selected 2026-07-28 authorization contract, including OAuth 2.1, RFC 8414 authorization-server metadata or OIDC discovery, authorization code + PKCE, validated redirect/client authentication policy, resource indicators, and an approved client-registration path. For this candidate, evaluate RFC 8414 OAuth metadata rather than implying a complete OIDC provider. The current bounded profile supports RFC 7591 DCR only, with no static-client compatibility; CIMD remains deferred. Under ADR 0010's approved simplification, `registration_endpoint` and bounded DCR follow existing AS/MCP ingress availability without `registration.enabled`. Registration fixes the derived canonical `${origin}/mcp` resource and binds a supported `mcp:all`/`mcp:read` ceiling under ADR 0010's dual-scope amendment, rather than accepting arbitrary client authority. New DCR omission defaults to `mcp:all`; either explicit scope or a valid space-separated list in either order is supported, with the pair canonicalized to `mcp:all`. Authorization omission inherits the registered ceiling; `mcp:all` permits narrowed `mcp:read`, while `mcp:read` cannot authorize `mcp:all`. Existing read-only registrations, grants and tokens are not promoted; broader access requires new registration and fresh authorization. Both scopes retain local RBAC, ownership, data and tenant/instance limits. The three current tools remain read-only; no mutation or dispatch registry is added. Future actual mutations require scope enforcement at dispatch denying `mcp:read`; no existing mutation dispatcher is claimed. DCR compatibility with a requested `authorization_code`/`refresh_token` pair still returns/registers only `authorization_code`, without advertising, issuing or accepting refresh. No configuration is needed for the new-registration default; Codex may request narrower authorization with top-level `scopes = ["mcp:read"]` in its server table. Issuer identity must be compared exactly after form decoding, not normalized like a resource URI. Client requests carry the canonical `resource` at authorization and token exchange; the AS must preserve the approved recipient, client, subject, instance and granted scope on code redemption without cross-resource expansion. A later refresh profile requires a separate authority change. Exact field behavior and delegated discovery/security requirements need their own protocol review before implementation approval; the locally inspected authorization page alone is not full conformance proof.

The accepted first profile issues **no refresh tokens**: AS metadata and client registration do not advertise the `refresh_token` grant or imply `offline_access`. The MCP protected resource does not advertise `offline_access` in `scopes_supported` or challenge scope hints. Clients reauthorize after access-token expiry, and `/mcp` never accepts refresh credentials. A later refresh profile requires separate approval of client registration, grant/resource/scope preservation, replay safety and AS-only token-endpoint handling. Public/confidential client identities are created only through DCR in `mcp-auth` under existing AS/MCP ingress availability, with no static configuration or compatibility; DCR does not authenticate a user, grant local authority, or replace consent and PKCE. Exact client records and resource-owner interaction remain AS-owned. The MCP protocol does not require a particular Zova site, but ADR 0009 now selects Zova to present a narrow AS per-request approve/deny interaction. The AS retains authenticated decision, code issuance and final redirect authority; the resource-server dossier does not own that interaction or any Zova page.

### Token format and validation

The accepted first profile uses **short-lived opaque MCP access tokens** backed by current AS-owned token/grant state and issues no refresh tokens. Exact lifetime and state representation remain open. This avoids making JWKS a required dependency while retaining OAuth resource binding and fail-closed validation. The opaque token profile is not the ordinary Cabloy temporary-token profile: it must carry or reference an explicit MCP profile and bind the client, canonical resource, subject, scope, bound instance, issued/expiry times, and revocation/grant state.

The existing `createTempAuthToken()` and `bean.jwt.create(...)` capabilities inform authentication and token-service design but sign JWTs; their signed output does not implement an opaque token. Reuse safe lower-level identity or lifecycle primitives only after semantic and storage review. If the temporary URL-bound or application-JWT semantics differ materially from an OAuth bearer access token, provide an MCP-specific authorization-server entry rather than widening the existing method. Exact operations, owners, and storage are `TODO(confirm)`; never accept an ordinary temporary token merely because it is valid or signed by Cabloy.

For each protected MCP request, the resource-server boundary must:

1. require exactly one `Authorization` header using the `Bearer` scheme; reject query, cookie, `x-vona-passport-code`, refresh-token, and other token locations;
2. look up or introspect only an MCP-profile access token through the approved server-owned token service, and fail closed when current authorization state cannot be confirmed; do not use stale lookup state to extend trust;
3. verify that the token is active, unexpired, not revoked, bound to the configured canonical MCP resource, associated with the approved client/grant, and carries a nonempty stable subject and the required scope;
4. verify the token's bound instance relation against the trusted DEC-MCP-04 endpoint binding. A client-supplied resource parameter is not proof of the token's resource, and no token claim may select an instance;
5. reject a wrong resource, inactive/revoked/expired token, missing subject, invalid profile, insufficient scope, ambiguous mapping, or token-service outage before protected `server/discover` policy, `tools/list`, or `tools/call` reaches a business controller;
6. map the stable authorization-server subject to exactly one active local identity in the bound instance and construct a fresh request-owned Passport projection; external scopes/roles never directly grant local RBAC or data scope;
7. reject refresh tokens at the resource endpoint; the accepted AS first profile issues none and requires client reauthorization after access-token expiry. Any later refresh issuance belongs exclusively to an AS token endpoint and requires a separate replay-safe grant/resource/scope/client/subject/instance and public-client policy decision.

The opaque-token format is accepted for bounded design only. Its concrete store and module/service owner, digest representation, lookup consistency, access-token lifetime, revocation, multi-worker availability, exact scope vocabulary, and HTTP status taxonomy remain `TODO(confirm)` before implementation. Neither existing Redis session markers nor `a-auth` provider tables establish an opaque token/grant store. [ADR 0009](./0009-mcp-as-state-boundary.md) amends DEC-MCP-09 to permit planning AS-owned shared authorization state and selects one database-backed AS authority with a database-neutral atomic code-consumption/token-activation outcome as a logical design direction while preserving the no-new-MCP-resource-module-persistence boundary. An explicit multi-statement transaction is not presumed for the MVP; a proven single conditional mutation may satisfy the same commit requirement, while multiple writes require an appropriate transaction or new authority decision. This does not approve a physical database, schema, Redis/external store, durable consent, retention, migration, or `vonaModule.fileVersion` choice. Ask and record the owning module's fileVersion strategy before any schema edit. A future JWT/JWKS alternative remains possible but is not the accepted first profile. Only if that alternative is explicitly selected, the previously approved deny-on-required-JWKS-refresh-failure sub-policy applies: a successfully fetched and currently valid key cache may be used before refresh is required, but failure of a required refresh denies the token even when a prior key remains cached; the failure cannot extend that key's trust. Its finite refresh bounds, algorithms, and implementation would need separate approval and proof. This key-cache policy must not be mixed into opaque-token behavior.

### Protected-resource metadata and discovery

Publish RFC 9728 protected-resource metadata containing the canonical MCP `resource` identifier and `authorization_servers` with at least one approved authorization-server **issuer identifier** (not a metadata-document URL). For a canonical resource of `https://example.com/mcp`, the path-specific well-known location is `https://example.com/.well-known/oauth-protected-resource/mcp`. Serving this path-specific document satisfies the proposed discovery route; the origin-wide well-known location is a client fallback, not an additional mandatory server route. If an origin-wide document is also offered, its `resource` must match the resource it represents and cannot conflict with the path-specific document. Do not derive issuer or resource values from an untrusted request Host.

The metadata response is a direct standards JSON response, not Vona's `{ code: 0, data }` application envelope. It contains only approved public resource/discovery information, supported scopes/authorization details as applicable, and no secrets, access tokens, private keys, subject mappings, internal instance names, or tool catalog. Cache headers and host/instance variation are owned jointly by this decision and DEC-MCP-04; a cached metadata document must never advertise one instance's resource for another host.

Missing/invalid/expired tokens receive HTTP `401`; insufficient scope or permission receives HTTP `403` at the HTTP authorization boundary, without publishing sensitive denial details. A malformed authorization _request_ is classified separately (typically HTTP `400`); distinguish it from an invalid credential and settle ambiguous credential syntax in the approved failure matrix. A standards-compliant `WWW-Authenticate: Bearer` challenge is required where the OAuth Bearer resource-request rules require it, including missing or unusable credentials. This bounded design uses the path-specific well-known metadata URL for discovery: adding `resource_metadata` to a Bearer challenge is optional when the well-known route is available, **not** a reason to omit a required Bearer challenge. Any advertised metadata URL must be trusted and endpoint-bound. Scope hints are a protocol SHOULD where applicable, not mandatory; record a reason for omitting them and never advertise `offline_access` as an MCP resource scope. Verify exact challenge/error fields and HTTP versus protocol ownership against the selected SDK and revision.

### Subject mapping to local Passport

After MCP access-token validation and trusted endpoint-instance binding, map the token's stable `sub` (and, only where explicitly approved, an issuer/client namespace) to exactly one active local identity in the bound Vona instance. The mapping is a server-owned configuration/service boundary and must not be selected by tool arguments or a client-provided local user ID.

The bounded design requires a deterministic mapping keyed by `(issuer, sub)` and constrained to the instance established under DEC-MCP-04; the actual adapter remains unimplemented. No match, multiple matches, disabled account, inactive account, wrong instance, or mapping-store outage fails closed. The adapter then constructs a fresh request-owned local Passport projection for normal controller guards and data-scope/RBAC evaluation. It must not reuse a Passport from the parent HTTP context or treat OAuth claims/roles as local roles without an explicit server-side mapping.

A token's `scope`, `roles`, `groups`, `tenant`, or profile claims cannot directly grant local roles, system-admin status, ownership, or unrestricted instance access. Local account activation, disabled-account checks, role guards, resource ownership, and row/data scope remain authoritative. A subject may be valid at the OAuth layer and still see no tools or receive a local authorization denial.

### Client registration, scopes, and revocation

The implemented `mcp-auth` authorization-server module owns client registration, redirect URIs, PKCE, explicit grant interaction, AS authorization state and token revocation; it issues no refresh tokens in the first profile. RFC 7591 DCR is the only path for creating AS-owned public or confidential client records through `POST /mcp/register`; static-client configuration and compatibility are removed. Registration and `registration_endpoint` follow existing AS/MCP ingress availability, with no `registration.enabled`; retain body/redirect and rate limits and ongoing validity checks. Registration fixes the root-serve-derived canonical `${origin}/mcp` resource and `mcp:read` scope. DCR does not authenticate a user, grant Cabloy roles or tenant access, issue an authorization code/token, or replace explicit consent and PKCE. CIMD, dynamic scopes, remembered consent, client-management UI, and public registration update/delete endpoints remain deferred. The `cabloy-mcp` resource module does not own registration or consent; Zova's separately scoped AS presentation is not a resource-module page.

Use narrow, deployment-defined scopes that name MCP capabilities or policy classes rather than broad `admin` or raw Cabloy role names. The exact vocabulary and per-tool requirements remain `TODO(confirm)` under DEC-MCP-06. Every request checks the token's scope and current deployment policy; a previously issued token does not survive endpoint disablement or tool-policy removal.

Opaque tokens can support revocation through the server-owned token/grant state, but only when lookup is current and available. Before activation, the selected AS/token-service design must define revocation, lookup consistency, outage behavior and access-token lifetime for the accepted **no-refresh** first profile. Any later refresh issuance needs a separate public/confidential-client, replay, lifetime and worker-failure decision; ordinary Passport refresh is not proof. Short-lived opaque access tokens and exclusion of destructive/unclassified tools do not establish a runtime revocation guarantee.

### Failure and privacy policy

- Missing, wrong-issuer/resource, expired/not-yet-valid, or otherwise invalid bearer credentials: bounded HTTP `401` with the required Bearer challenge; a metadata discovery hint is optional when the path-specific well-known route works. Malformed authorization requests use the separately approved `400` class where required rather than being universally labeled `401`.
- Insufficient scope or local permission: bounded HTTP `403` at the HTTP authorization boundary, with Bearer challenge information when the applicable OAuth rules require it. Unknown subject, disabled/ambiguous mapping, and instance mismatch fail closed without disclosing unrelated subject/resource existence; finalize their nondiagnostic HTTP mapping before acceptance.
- Authorization-server metadata mismatch or token lookup/introspection outage: deny unless the selected profile has an independently approved, current validation state. Under the accepted opaque profile, do not use stale token state to extend trust. Ambiguous subject mapping always denies. Emit only a protected, redacted operator event. If a JWT/JWKS alternative is later selected, apply the separately retained deny-on-required-refresh-failure rule.
- No raw Authorization value, JWT, claims, JWKS response, client secret, refresh token, cookie, or complete subject profile may enter logs, traces, metrics, audit, or retained evidence.
- OAuth validation never expands authority beyond the intersection of endpoint enablement, DEC-MCP-04 instance binding, deployment tool policy, local Passport/RBAC, data scope, resource ownership, and DEC-MCP-06 risk policy.

## Shared DEC-MCP-03/04 design interface (accepted by DEC-MCP-03 only)

Both decisions must use one deployment-owned, validated configuration contract: a canonical external HTTPS `/mcp` endpoint URL maps to **one** protected-resource identifier and **one** enabled Vona instance; that resource is registered for an allowlisted authorization-server issuer and is the expected recipient of its tokens. The path-specific protected-resource metadata publishes the configured resource and issuer identifiers for that same endpoint. DEC-MCP-04 supplies the trusted endpoint/instance binding before instance initialization; DEC-MCP-03 confirms the opaque token's issuer and recipient from current server-owned lookup state against that binding, then maps `(issuer, sub, bound instance)` to exactly one active local identity. Neither raw Host nor a token claim may select the instance, and the same resource cannot bind to different instances. An unconfigured, ambiguous, mismatched, or disabled binding prevents MCP activation or dispatch; an absent trusted instance claim does not bypass resource registration and local mapping.

Design acceptance may establish this interface, configuration ownership, and fail-closed opaque-token validation profile **without claiming** that an authorization server, live Host/instance/resource tuple, proxy operator, client registration, local mapping, token store, or test fixture is already provisioned. DEC-MCP-03 acceptance must not depend on DEC-MCP-04 already being accepted, nor vice versa: each owner review must check the same interface in both drafts and record any incompatible change before accepting either. If the interface cannot be agreed independently, hold both decisions for a joint design disposition rather than accepting one on the assumption that the other will change. Concrete deployment values, authorization-server grant semantics, and token-store behavior must be approved before they are used; installed-library behavior, proxy/metadata isolation, local mapping and HTTP outcomes require separately approved integration and ATP proof. No design acceptance alone enables exposure.

## Boundaries with adjacent decisions

- **DEC-MCP-02:** owns the 2026-07-28 transport method, protocol metadata, wire errors, and request/response handling. This decision supplies auth challenge and protected-resource inputs but does not alter the wire profile.
- **DEC-MCP-04:** owns trusted Host/forwarded-host processing, canonical host-to-instance mapping, selector conflicts, and token-instance consistency. This decision only requires the token resource/instance relationship to be checked after that binding is established.
- **DEC-MCP-06:** owns scope vocabulary, per-tool policy, confirmation, side-effect classification, and result/data minimization. This decision does not make a broad scope sufficient for a call.
- **DEC-MCP-07:** owns fresh context/Passport construction and executor adaptation. This decision requires a fresh local subject projection but does not select its implementation.
- **DEC-MCP-08:** owns validation telemetry, redaction, retention, rate/timeout limits, and operational ownership. This decision supplies only the OAuth-specific events that must be classified safely.

## Alternatives rejected or deferred

- **Reuse Cabloy `auth-oauth` as the MCP authorization server:** rejected as an assumption; current source demonstrates login/provider integration, not the complete MCP authorization-server/resource-indicator contract.
- **Accept ordinary Cabloy JWTs or temporary tokens as MCP bearer tokens:** rejected because local signing/Passport or URL-bound temporary-token semantics do not establish the MCP resource, client grant, scope, instance, revocation, and lifecycle contract.
- **Use generic Vona JWT extraction:** rejected because the current extractor checks query before Authorization; MCP accepts only the protected-resource Bearer header.
- **Map OAuth claims directly to local roles or tenant/instance:** rejected because external claims are not local authority or data scope.
- **Require JWT/JWKS for the first increment:** deferred as an alternative; the accepted first profile uses MCP-specific opaque tokens and current token lookup/introspection. The retained deny-on-required-refresh-failure rule applies only if JWT/JWKS is later selected.
- **Build a separate MCP authorization UI/client registry in the resource module:** deferred; the integrated `a-auth` route is selected for the first profile, while the resource module adds no independent consent or identity authority.

## Authorization-server delivery boundary (blocked implementation)

`WBS-MCP-20-04` is a separate, blocked authorization-server work package for the selected integrated `a-auth` AS route. `zhennann` owns its implementation and operations; the exact authorization/token interaction, issuer/discovery and client registration, resource/grant/token lifecycle, shared-state design and AS-owned proof remain separate gates before `WBS-MCP-20-02` can rely on a real token service. The accepted first profile issues no refresh tokens. Its WBS number does not imply it executes after the resource server: it is a prerequisite. The `WBS-MCP-20-02` dossier remains resource-server-only; synthetic token lookup fixtures cannot prove an available AS or an end-to-end grant. A separately operated AS would require a new route decision plus equivalent approved configuration and observed contract proof; it is not automatically provided by existing `auth-oauth` login.

[ADR 0009](./0009-mcp-as-state-boundary.md) selects one AS-owned database-backed authority with an atomic code-consumption/token-activation commit and Zova presentation of the narrow AS per-request grant flow for bounded design, but accepts no physical store, schema, Zova site/flavor/SSR/admission, concrete identity/session/CSRF implementation, consent record or execution. Provider enablement, source and OAuth tests still need separate approval. Obtain the owning module's fileVersion choice before a schema edit and run the mandated root test path if `meta.version.ts` changes. The grant/token service's state must support current MCP-profile lookup and fail-closed resource validation; do not place issuance or consent persistence inside the `cabloy-mcp` resource module as a shortcut.

## Acceptance and execution gates

The 2026-10-09 **design-only** review of `DEC-MCP-03` considered the following boundaries; later ADR 0009 and the selected `a-auth` route resolve logical AS ownership, the database-backed atomic-commit authority direction and Zova presentation of the AS-owned browser flow, not physical implementation or execution:

1. the shared DEC-MCP-03/04 interface above, including configuration owners and validation of issuer → protected resource → canonical endpoint → instance, token recipient, optional trusted instance-claim semantics, and `(issuer, sub, bound instance)` mapping; reconcile the same interface in ADR 0004 without requiring DEC-MCP-04's prior acceptance;
2. the selected integrated `a-auth` AS versus MCP resource-server responsibilities and its separately owned `WBS-MCP-20-04` prerequisite; RFC 8414 or OIDC discovery, truthful metadata/authorization-response `iss`, PKCE/redirect and pre-registered public/confidential-client compatibility, explicit authorization interaction, opaque token lookup/introspection, no refresh in the first profile, recipient binding at authorization/code exchange, issuer-versus-resource URI comparison, scope-policy ownership, token-store availability/consistency, and nondiagnostic `400`/`401`/`403`/Bearer-challenge taxonomy; retain the deny-on-required-JWKS-refresh-failure rule only for a separately selected JWT/JWKS alternative;
3. path-specific protected-resource metadata, required `resource`/`authorization_servers` fields, per-bound-endpoint variation and cache isolation, direct unwrapped JSON, applicable scope hints excluding `offline_access`, and no secret/topology disclosure; deterministic local mapping failure behavior and the fresh Passport handoff to DEC-MCP-07;
4. a disposition for DEC-MCP-09's no-schema first-increment wording and ADR 0001's separately gated durable consent/UI boundary if the selected AS requires new auth-owned state or interaction. [ADR 0009](./0009-mcp-as-state-boundary.md) subsequently permitted AS-owned shared state and selected a database-backed atomic-commit authority and Zova-presented AS-browser design direction only. Selecting the physical store or schema, Zova site/flavor/SSR/admission and concrete AS identity/session/CSRF implementation, choosing `vonaModule.fileVersion` before a schema edit, and approving AS source execution remain later, distinct decisions.

The recorded 2026-10-09 design acceptance and 2026-10-10 route/state-planning dispositions are explicit but bounded; do **not** infer implementation, configuration, evidence or any other decision's acceptance from this ADR or a planning audit. Before configuring/activating a real endpoint, separately approve and validate the selected authorization-server owner and escalation path, public endpoint/instance/resource registration, proxy and local-mapping owners, client-grant and scope semantics, token-store/lookup and no-refresh behavior, library and security parameter choices, and safe failure behavior against DEC-MCP-04/06/07/08. Retain these as `TODO(confirm)` while unknown; a design-only decision is not authorization to choose their values. A separately approved bounded execution dossier must own dependencies, configuration and fixtures; synthetic tests for wrong issuer/resource, inactive/expired/revoked opaque state, lookup outage, no-refresh AS behavior, scopes, query-token and refresh-credential rejection at the resource endpoint, unmapped/disabled subjects and no-controller dispatch, together with metadata, host isolation and real HTTP ATP, are **implementation/verification gates**, not prerequisites to design-only acceptance. If a JWT/JWKS alternative is selected later, add its key-rotation and required-refresh-failure branch separately.

No runtime evidence exists. Planning audits/charts and source inspection cannot accept this ADR or prove token validation.
