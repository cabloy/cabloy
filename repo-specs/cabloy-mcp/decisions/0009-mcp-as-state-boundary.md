# ADR 0009: MCP Authorization-Server State Boundary

## Status

**Accepted for bounded design only — no physical schema, source, or execution approval.** On 2026-10-10, `zhennann` selected the integrated `a-auth` AS route and a revision of the first-increment no-schema boundary to permit planning for **AS-owned shared authorization state**. `zhennann` accepted AS implementation and operational responsibility. In a separate 2026-10-10 design disposition, `zhennann` selected a **single AS-owned transactional database as the logical authoritative-store direction** and an **AS-owned browser interaction for explicit approval/denial per authorization request**. In a subsequent bounded design clarification, `zhennann` requested a database-neutral state contract rather than a PostgreSQL, MySQL or SQLite product choice and initially selected AS-owned backend-rendered HTML. On 2026-10-11, `zhennann` revised that bounded direction: an MVP need not presume an explicit multi-statement database transaction, but **authorization-code consumption and resulting token activation must still share one atomic commit**; Zova will present the per-request authorization interaction while the AS retains server-side decision and issuance authority. These selections amend `DEC-MCP-09`'s design direction; they do not establish cross-dialect conditional-write/transaction portability or select a concrete database, state representation, owning module/service, table, field, migration, `fileVersion`, TTL, retention, operational topology, Zova site/flavor, browser route, identity/session bridge, CSRF mechanism, live issuer, endpoint, or credential.

`WBS-MCP-20-04` remains blocked. This decision is distinct from approval of its [execution dossier](../wbs-mcp-20-04-execution-dossier.md), AS source, runtime operation, or `ATP-MCP-AUTH-03`.

## Context

[ADR 0001](./0001-mcp-suite-boundaries.md) accepts no new **MCP resource-module-owned** registry, consent, or audit persistence and a no-schema first-increment scaffold. [ADR 0003](./0003-mcp-oauth-resource-server.md) accepts a distinct AS and resource-server design: Authorization Code + PKCE S256, pre-registered public/confidential clients, MCP-only opaque access tokens with current authoritative lookup, and no refresh issuance. The [AS design review](../wbs-mcp-20-04-as-design-review.md) found that existing login/provider, JWT, and Redis session primitives do not provide the required AS transaction, grant, or opaque-token lookup state. Putting new records under `a-auth` would still change the original no-schema scope; a Redis/external shared store is still authorization state even without a relational migration.

The 2026-10-10 decision selects an integrated `a-auth` logical AS for the first profile and separately identifies `zhennann` as both implementation and operational owner. The first profile cannot be executed as real issuance with only the existing session marker or a process-local token map.

## Decision and exact boundary

1. **Ownership:** `a-auth` is the selected logical AS capability owner. `zhennann` is responsible for AS implementation and operations, including issuer/client registration, authorization interaction, state availability and revocation, secret custody, incident response, and retention policy. The `cabloy-mcp` resource server remains a separate owner; it does not issue credentials, retain grants, store consent, or run an independent token registry. This is responsibility assignment, not permission to set live configuration.
2. **First-increment scope revision:** `DEC-MCP-09` permits a separately designed and approved **AS-owned shared authorization state** capability needed for MCP client registration, short-lived authorization request/code/PKCE transactions, grant/resource/scope binding during access-token lifetime, and opaque access-token active/revocation lookup. The originally accepted no-MCP-resource-module persistence boundary and no-schema initial `cabloy-mcp` scaffold remain intact. The blanket statement that the entire first increment can have no new schema is superseded only for a future, separately approved AS-owned store.
3. **Selected logical state direction:** One AS-owned database-backed authority will govern the authorization-request/code/grant linkage and current MCP opaque-access-token active/revocation state. **Code consumption and resulting token activation must share one atomic commit**; approval/denial/cancellation/expiry of a pending authorization must be a separate single-use transition. Multi-worker lookups, absolute expiry and revocation must fail closed when current authoritative state cannot be confirmed. The MVP does not select a database product or require an explicit multi-statement transaction by default: a single authoritative aggregate and conditional mutation may satisfy the contract only if the actual dialect, affected-row result, uniqueness, concurrency, cache bypass and failure behavior prove the same atomic outcome. If the physical representation needs multiple writes, retain the atomic-commit requirement and use an appropriate transaction or return for an explicit authority revision; consuming a code before a separate token activation is not an equivalent shortcut. This is a database-neutral state/transition contract, not a portability claim for one SQL, locking, isolation or migration implementation across SQLite, PostgreSQL and MySQL. The deployed dialect and topology require concurrency and migration proof before execution. No concrete instance, `a-auth` module/service, table/field, index, migration, client registry form, isolation policy, digest, lifetime or operational configuration is selected. Redis-only and SQL-plus-Redis split authority are not selected for this first profile; a later alternative requires a new decision.
4. **Selected logical interaction and presentation direction:** Zova will present the integrated AS browser authorization flow with an explicit approve/deny decision on **every authorization request**; the AS alone retains authenticated decision, code issuance, token activation and final redirect authority. This supersedes the backend-rendered HTML selection, not the AS/RS ownership boundary. The Zova page is a narrowly scoped per-request AS interaction, not a general management UI, a new MCP resource-module page, or approval of a particular Web/Admin/new site, flavor, route, layout or SSR implementation. An existing login session establishes identity only, not approval; the existing client-managed frontend cookie does not by itself authenticate AS requests. The server-held pending authorization request binds a registered client and redirect, requested canonical resource/instance relation, narrow scopes, PKCE S256 and AS/browser correlation; client OAuth `state`, upstream-login state and decision CSRF remain distinct. No remembered-consent record, silent approval, refresh token or refresh family is approved. The intended authorizing population and site admission; AS-side pre-instance admission across authorization, continuation, decision, token and discovery routes; server-verifiable identity/session or reviewed login bridge; request-bound CSRF; protected summary/decision APIs; SSR/hydration privacy; response and clickjacking protections; login continuation, final redirect and terminal-state mechanics still require concrete review. The proposed ADR 0004 `/mcp` ingress hook does not establish AS-route instance admission. The existing disabled CSRF assertion and development mock form are not production controls.
5. **Separate implementation decision:** Before changing source or registering storage, record the exact owning module and runtime service, physical database and client-registration representation, proof of atomic commit for code consumption/token activation, TTL/retention/deletion, digest/custody, issuer/resource/instance registration, concurrency/replay/revocation policy, multi-worker topology, outage recovery, Zova site/admission and browser/session/CSRF behavior, data classification and redaction. Before **any** persisted field/schema edit, ask and record whether the owning `vonaModule.fileVersion` will increment; this decision intentionally does not answer that question. Any `meta.version.ts` edit requires `npm run test` after separately approved implementation. A future Redis/external alternative would need a new direction decision and explicit namespace, lifetime, consistency, custody and failure policy.

The decision is not an exception for a new `cabloy-mcp` schema, an AS inside the resource module, a general consent ledger, new OAuth provider configuration, or a production authorization endpoint. A separately operated AS remains a later alternative only through a new route decision and equivalent contract proof.

## Consequences and readiness

- The AS implementation path has a responsible logical owner, accountable operator, selected database-neutral atomic-commit authority contract and Zova presentation direction, but no deployed dialect, physical store, site/admission contract, interaction implementation or runtime configuration. The existing auth tables and Redis session marker are not accepted as an opaque-token/grant store.
- [WBS-MCP-20-04](../pdp-wbs.md) cannot proceed to implementation until its exact physical storage/interaction contract, applicable migration/file-version choice, configuration ownership, bounded execution approval and safe verification path are separately settled. Planning predecessors and design-direction acceptance do not change its `blocked` status.
- `WBS-MCP-20-02` remains blocked on actual AS contract/proof, transport and trusted endpoint binding; the AS design does not grant any local Passport, RBAC, data scope, or tenant authority to a token.
- No source, schema, state service, dependency, issuer, provider, credential, deployment, OAuth/HTTP test, or ATP evidence follows from this ADR.
