# ADR 0009: MCP Authorization-Server State Boundary

## Status

**Accepted for bounded design only — including the finite physical storage contract below, not executable DDL, source, or execution approval.** On 2026-10-10, `zhennann` selected the integrated `a-auth` AS route and a revision of the first-increment no-schema boundary to permit planning for **AS-owned shared authorization state**. `zhennann` accepted AS implementation and operational responsibility. In a separate 2026-10-10 design disposition, `zhennann` selected a **single AS-owned transactional database as the logical authoritative-store direction** and an **AS-owned browser interaction for explicit approval/denial per authorization request**. In a subsequent bounded design clarification, `zhennann` requested a database-neutral state contract rather than a PostgreSQL, MySQL or SQLite product choice and initially selected AS-owned backend-rendered HTML. On 2026-10-11, `zhennann` revised that bounded direction: an MVP need not presume an explicit multi-statement database transaction, but **authorization-code consumption and resulting token activation must still share one atomic commit**; Zova will present the per-request authorization interaction while the AS retains server-side decision and issuance authority. On 2026-10-14, separate design dispositions accepted the browser package's bounded direction and the physical state package's bounded direction: evaluate the observed Cabloy Basic Web site for a narrow authorization page, with an AS-verifiable short-lived HttpOnly browser-session bridge, fixed internal continuation, independent request-bound CSRF, synchronous per-path early instance admission, and an AS-built final redirect; use a single, trusted-instance-scoped AS authorization aggregate with non-authoritative locator plus high-entropy-secret opaque credentials, complete conditional approval and redemption transitions, same-commit code consumption/token activation, and fresh authoritative fail-closed lookup. On 2026-10-15, `zhennann` selected **SQLite via `better-sqlite3` as the first AS implementation target, using Vona's existing primary datasource**. In a further 2026-10-15 disposition, `zhennann` selected **multiple Vona workers on the same host sharing persistent SQLite through that existing primary datasource** as the first implementation and verification topology. If AS persistence resides in the existing `a-auth` module, **keep `vonaModule.fileVersion: 1` and fold the AS schema into its version-1 creation path**, with no new version-2 migration. Databases already recorded at version 1 do not automatically upgrade. A subsequent 2026-10-15 disposition accepts the fresh-only installation scope/exclusions and secret-free deployment-confirmation requirements detailed below; actual eligibility, deployment observations, implementation and any treatment outside that scope remain separately gated. These are bounded design inputs, not an observation of actual deployment, approval of a schema edit, or proof of SQLite atomicity. They select neither cross-host SQLite nor replica support. A further 2026-10-15 disposition accepts the existing-`a-auth` physical owner/service boundary, logical aggregate/lifecycle, layered read-only activation responsibilities/timing and verifiable approved-fresh-install continuity detailed below. Those earlier selections amend `DEC-MCP-09`'s design direction; at that stage they did not establish cross-dialect conditional-write/transaction portability or select a state table, exact new source target, field, migration/check/provenance implementation, TTL, retention, worker count/connection policy, credential wire format/digest/custody, creation uniqueness strategy, final site/role admission, browser route, bridge/session lifecycle, cookie policy, SSR/hydration implementation, CSRF mechanism, live issuer, endpoint, or credential.

`WBS-MCP-20-04` remains blocked. This decision is distinct from approval of its [execution dossier](../wbs-mcp-20-04-execution-dossier.md), AS source, runtime operation, or `ATP-MCP-AUTH-03`.

## Context

[ADR 0001](./0001-mcp-suite-boundaries.md) accepts no new **MCP resource-module-owned** registry, consent, or audit persistence and a no-schema first-increment scaffold. [ADR 0003](./0003-mcp-oauth-resource-server.md) accepts a distinct AS and resource-server design: Authorization Code + PKCE S256, pre-registered public/confidential clients, MCP-only opaque access tokens with current authoritative lookup, and no refresh issuance. The [AS design review](../wbs-mcp-20-04-as-design-review.md) found that existing login/provider, JWT, and Redis session primitives do not provide the required AS transaction, grant, or opaque-token lookup state. Putting new records under `a-auth` would still change the original no-schema scope; a Redis/external shared store is still authorization state even without a relational migration.

The 2026-10-10 decision selects an integrated `a-auth` logical AS for the first profile and separately identifies `zhennann` as both implementation and operational owner. The first profile cannot be executed as real issuance with only the existing session marker or a process-local token map.

## Decision and exact boundary

1. **Ownership:** `a-auth` is the selected logical AS capability owner. `zhennann` is responsible for AS implementation and operations, including issuer/client registration, authorization interaction, state availability and revocation, secret custody, incident response, and retention policy. The `cabloy-mcp` resource server remains a separate owner; it does not issue credentials, retain grants, store consent, or run an independent token registry. This is responsibility assignment, not permission to set live configuration.
2. **First-increment scope revision:** `DEC-MCP-09` permits a separately designed and approved **AS-owned shared authorization state** capability needed for MCP client registration, short-lived authorization request/code/PKCE transactions, grant/resource/scope binding during access-token lifetime, and opaque access-token active/revocation lookup. The originally accepted no-MCP-resource-module persistence boundary and no-schema initial `cabloy-mcp` scaffold remain intact. The blanket statement that the entire first increment can have no new schema is superseded only for a future, separately approved AS-owned store.
3. **Selected logical state direction:** One AS-owned database-backed authority will govern the authorization-request/code/grant linkage and current MCP opaque-access-token active/revocation state. The accepted bounded physical direction is one trusted-instance-scoped authorization aggregate per request, addressed by a non-authoritative locator plus an independent high-entropy-secret opaque credential format; code consumption and resulting token activation must share one atomic commit, while approval/denial/cancellation/expiry of a pending authorization is a separate single-use transition. The aggregate/credential shape remains a logical design direction, not DDL or a wire-format selection. Multi-worker lookups, absolute expiry and revocation must fail closed when current authoritative state cannot be confirmed. The first AS implementation and verification target is multiple Vona workers on one host sharing persistent SQLite via `better-sqlite3` on Vona's existing primary datasource; this does not establish the actual deployment's configuration. Cross-worker approval/redemption contention, acknowledged-revocation visibility and connection/failure behavior require explicit prospective proof; single-process contexts alone are insufficient. Cross-host SQLite and replica support are not selected. The MVP does not require an explicit multi-statement transaction by default: a single authoritative aggregate and conditional mutation may satisfy the contract only if SQLite's actual driver, affected-row result, uniqueness, concurrency, cache bypass and failure behavior prove the same atomic outcome. If the physical representation needs multiple writes, retain the atomic-commit requirement and use an appropriate transaction or return for an explicit authority revision; consuming a code before a separate token activation is not an equivalent shortcut. This is a database-neutral state/transition contract, not a portability claim for one SQL, locking, isolation or migration implementation across SQLite, PostgreSQL and MySQL. The selected SQLite target and primary-datasource integration require deployment confirmation and dialect-specific concurrency, revocation-freshness and migration proof before execution; PostgreSQL/MySQL AS support is not selected or proven. The owner refinement below initially selects existing-`a-auth` physical ownership and dedicated service-scene responsibilities only; the later independent aggregate/marker disposition selects finite physical fields/indexes and creation/conditional-transition requirements to its bounded extent. No concrete instance, exact new source target, emitted DDL/migration/check implementation, client registry form, exact reservation/isolation API, credential encoding/digest/custody, lifetime or operational configuration is selected. Redis-only and SQL-plus-Redis split authority are not selected for this first profile; a later alternative requires a new decision.
4. **Selected logical interaction and presentation direction:** Zova will present the integrated AS browser authorization flow with an explicit approve/deny decision on **every authorization request**; the AS alone retains authenticated decision, code issuance, token activation and final redirect authority. This supersedes the backend-rendered HTML selection, not the AS/RS ownership boundary. The bounded browser package is accepted for design direction: evaluate the observed Cabloy Basic Web site for a narrow per-request AS page, an AS-verifiable short-lived HttpOnly browser-session bridge, fixed internal continuation, independent request-bound CSRF, synchronous per-path early instance admission and an AS-built final redirect. This acceptance does not select the final site/role admission, flavor, route, layout, session/bridge lifecycle, cookie policy, SSR/hydration implementation or source. The Zova page is a narrowly scoped per-request AS interaction, not a general management UI, a new MCP resource-module page, or approval of an Admin/new site. An existing login session establishes identity only, not approval; the existing client-managed frontend cookie does not by itself authenticate AS requests. The server-held pending authorization request binds a registered client and redirect, requested canonical resource/instance relation, narrow scopes, PKCE S256 and AS/browser correlation; client OAuth `state`, upstream-login state and decision CSRF remain distinct. No remembered-consent record, silent approval, refresh token or refresh family is approved. The intended authorizing population and site admission; AS-side pre-instance admission across authorization, continuation, decision, token and discovery routes; server-verifiable bridge details; request-bound CSRF; protected summary/decision APIs; SSR/hydration privacy; response and clickjacking protections; login continuation, final redirect and terminal-state mechanics still require concrete review. The proposed ADR 0004 `/mcp` ingress hook does not establish AS-route instance admission. The existing disabled CSRF assertion and development mock form are not production controls.
5. **Separate implementation decision:** Before changing source or registering storage, retain the accepted existing-`a-auth` physical owner and dedicated service-scene boundaries below, separately approve exact source targets/dependencies and implementation, confirm the selected SQLite/`better-sqlite3` primary-datasource target against the actual deployment, implement and verify the bounded physical storage contract after separate emitted-DDL approval, select the client-registration representation, prove atomic commit for code consumption/token activation, TTL/retention/deletion, digest/custody, issuer/resource/instance registration, concurrency/replay/revocation policy, worker count/connection ownership and failure behavior within the selected same-host shared-SQLite topology, outage recovery, Zova site/admission and browser/session/CSRF behavior, data classification and redaction. If persistence resides in existing `a-auth`, the recorded strategy is to keep `vonaModule.fileVersion: 1` and fold the AS schema into version 1's creation path, not add version 2. This does not upgrade databases already recorded at v1; apply the accepted fresh-only installation scope/exclusions below, confirm actual eligibility, and separately approve migration implementation and any treatment outside that scope before persisted edits, without implying reset/recreation approval. Do not ask the settled conditional version question again unless the owning-module premise changes; a different owner needs its own explicit version disposition. Any `meta.version.ts` edit requires `npm run test` after separately approved implementation. A future Redis/external alternative would need a new direction decision and explicit namespace, lifetime, consistency, custody and failure policy.

The decision is not an exception for a new `cabloy-mcp` schema, an AS inside the resource module, a general consent ledger, new OAuth provider configuration, or a production authorization endpoint. A separately operated AS remains a later alternative only through a new route decision and equivalent contract proof.
