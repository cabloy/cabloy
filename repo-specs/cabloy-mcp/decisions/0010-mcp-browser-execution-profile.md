# ADR 0010: Bounded MCP Browser Authorization Execution Profile

## Status and precedence

**Accepted for the user-approved bounded implementation on 2026-10-23; not runtime evidence or release qualification.** This records the corrected connected flow contributing to `WBS-MCP-20-04` and `WBS-MCP-20-02`. It supersedes incompatible, unimplemented directions in [ADR 0003](./0003-mcp-oauth-resource-server.md), [ADR 0009](./0009-mcp-as-state-boundary.md) and their legacy SRS/WBS/ATP/dossier references **only for this increment**. Former preparation handoffs and superseded mechanism gates are historical, not instructions to restart planning. Compatible OAuth, tenant, authorization, privacy, lifecycle and acceptance requirements remain in force; no WBS/ATP completion or production exposure is implied.

## Decision

- **Owners:** backend `cabloy-mcp/modules/mcp-auth` owns AS state, DCR client records, decisions, issuance and current lookup/revocation; backend `cabloy-mcp` consumes it one-way as RS. Dev/test-only `mcp-test` retains `/mcp` and existing read-only tools. Zova `cabloy-mcp/modules/cabloy-mcp` owns consent presentation. Existing identity/login owners remain unchanged. The user-approved `mcp-auth` strategy keeps `fileVersion: 1`, with both authorization and client tables in its version-1 creation path, separate from `a-auth`; no version-2 migration, automatic replay against existing v1 databases, `a-auth` schema/version change or reset approval follows. Existing v1 databases missing the client table require separate approved treatment.
- **Navigation:** `/mcp/auth` validates trusted instance, client, exact registered redirect, resource, scope and S256 before any client-directed error redirect. Copy enabled SSR Sites for the current instance/host; choose minimum `publicPath.length`, preserving order for ties. Do not change specificity-first routing, inspect page availability or add a capability check. Use the Site helper for fixed `/cabloy/mcp/consent?request=<opaque-reference>`; include the shared route in selectable Basic/Commerce Web/Admin flavors without bypassing Site-role admission.
- **Existing identity only:** reuse protected-page admission, SSR/browser Passport cookie, normal login and exact internal `returnTo`, never the OAuth callback as login continuation. Reuse the existing `home-passport` cookie → generated API Authorization header → backend `GuardPassport` chain, including integrated-SSR header handoff and account/activation checks. The locator is not identity or approval. Add **no extra cookie, holder, identity bridge, session system, CSRF bootstrap, resume endpoint or callback-state store**.
- **Explicit decision:** authenticated approve/deny POST uses existing `bean.security.checkOriginExact(...)` with trusted configured origin input and a winning pending transition. Its dev/loopback exceptions are not strict production origin proof; stock CSRF-token enforcement is disabled and must not be claimed. OAuth `state` is callback correlation, not authentication. Denial issues no code; only the mutation returns the AS-built registered callback for immediate browser navigation.
- **Authority/configuration (approved simplification, 2026-10-24):** remove authored `mcp-auth.issuer`/`resources`. Issuer **and** resource are the exact `${origin}/mcp`, including the path, derived from root backend `server.serve.protocol`/`host`. Nonproduction may use the existing requestless `AppUtil` fallback `http://localhost:<SERVER_LISTEN_PORT>`; production requires the public serve pair. Do not derive authority from request Host/proxy input. Validate Host against canonical authority, reject client instance selectors and resolve the instance through existing automatic routing in a fresh selector-free context; no MCP resource/instance registry. Missing/invalid/inconsistent authority fails closed; no cross-origin federation. `allowLoopbackHttp` defaults to `true`, supports explicit `false`, and permits HTTP only for exact `localhost`, `127.0.0.1` or `[::1]`, never arbitrary HTTP. Existing origin-only issuer grants/codes/tokens fail exact comparison and require new authorization, not persisted-state rewriting or reset. Schema and `fileVersion: 1` are unchanged.
- **Protocol:** `/mcp/auth`, `/mcp/token`, RFC 7591 `POST /mcp/register`, canonical RFC 8414 discovery at `/.well-known/oauth-authorization-server/mcp` and unchanged PRM at `/.well-known/oauth-protected-resource/mcp`; DCR-only public/confidential `none`/`client_secret_basic` registrations, with no static-client configuration or compatibility, code + PKCE S256 and exact redirects. The approved dual-scope amendment supports `mcp:all` and `mcp:read`: new DCR without `scope` defaults to `mcp:all`, either explicit scope is supported, and valid space-separated lists in either order (`mcp:all mcp:read` / `mcp:read mcp:all`) canonicalize to `mcp:all`. Explicit authorization scope uses the same supported values and list canonicalization; omitted authorization scope inherits the registered ceiling; `mcp:all` registrations permit narrowed `mcp:read`, while `mcp:read` registrations cannot authorize `mcp:all`. Existing read-only registrations, grants and tokens are not promoted; broader access needs a new registration and fresh explicit authorization, not rewritten bindings. Remove `registration.enabled`: DCR and its metadata advertisement are always available when existing AS/MCP ingress is available, retaining body/redirect and rate limits. All flows remain subject to current validity checks. Registration creates only an OAuth client identity and stores only confidential-secret digests; it does not authenticate users, grant local roles/tenant access, issue tokens, or bypass consent/PKCE. Token exchange requires the exact original `redirect_uri`. Reject malformed/duplicate parameters and bind client/redirect/resource/scope through redemption. The delivered refresh-enabled profile supersedes the initial code-only/no-refresh behavior: metadata/registration and token responses reflect supported refresh grants and AS-only rotating MCP JWT pairs; code-only and legacy opaque grants are not upgraded. See [current refresh guidance](../../../repo-docs/mcp/mcp-browser-authorization.md#5-refresh-without-a-new-browser-authorization) and the [existing refresh record](../evidence/business-ai-client.md#user-provided-real-client-mcp-refresh-runtime-evidence-2026-11-01). No `offline_access`, CIMD, remembered consent, general management UI, public registration update/delete endpoints or ordinary Cabloy JWT acceptance. Dynamic scope support is limited to the personal custom-scope disposition below. No scope configuration is needed for the new-registration default; Codex's optional top-level `scopes = ["mcp:read"]` in its server table requests narrower authorization, not an HTTP header.
- **One authority:** a tenant-scoped aggregate transitions `pending → codeReady → tokenActive`, with terminal denial/revocation, immutable bindings, approving user/auth identities and credential digests only. Original defaults: pending **600s**, code **60s**, token **900s**; the delivered refresh profile's current access/refresh lifetimes and generation/nonce-digest state supersede that initial token representation/default (see current guidance). TTLs use seconds, `expiresAt` epoch milliseconds. Ordinary indexes, no authority caches, finite expired-row cleanup. Complete scoped `builderSelect().where(...).update(...)` predicates require numeric affected count **1**; cached `Model.update()` is not winner proof. Consume code/install token digest in one conditional UPDATE; reject ambient transactions or own and await commit before release. No automatic issuance retry, lost-response recovery or terminal revival.
- **Protected resource:** accept exactly one raw-header Bearer credential, never query/cookie/proxy credentials; SSR cookies remain supported. Fresh current lookup checks expiry/revocation/configuration/account validity in the trusted instance. Reload user/auth/roles and validate association/activity/activation in a fresh ordinary executor context; install server-owned Passport. Retain `performAction(..., { innerAccess: false })`, local RBAC, ownership and data scope under both scopes; neither grants administrator or cross-tenant authority. The existing three catalog tools remain read-only and accept either scope. This amendment adds no mutation or dispatch registry. Before exposing future actual mutations, enforce their required scope at dispatch so `mcp:read` cannot execute them; no existing mutation-dispatch enforcement is claimed. Missing/invalid bearer is 401 with applicable challenge; insufficient scope is 403; lookup/configuration failure denies before SDK/business dispatch. Standalone local fixture remains anonymous and credential-rejecting.
- **SSR/privacy:** static unnamed consent route, `requiresAuth: true`, `ssrProfile: 'session'`, empty layout. Model-owned summary state keyed by request disables persistence/dehydration; defer private client queries behind hydration/admission and preserve neutral initial HTML. Generate consumers from backend DTO truth. No raw credential, callback response or Authorization/cookie value in query persistence, SSR or logs. Protocol JSON is bounded, direct and `no-store`.

## Accepted personal custom-scope disposition (2026-11-04)

**Accepted only for the user-approved personal custom MCP scopes increment, `WBS-MCP-20-05`.** This narrows earlier blanket dynamic-scope/management-UI exclusions, not whole Proposed ADRs or unrelated parent/release gates. Existing delivered refresh behavior supersedes historical no-refresh references; the [retained refresh record](../evidence/business-ai-client.md#user-provided-real-client-mcp-refresh-runtime-evidence-2026-11-01), including final managed 63/63, is not custom-scope proof.

- `mcp-auth` owns personal active-instance presets and exact stable tool identities/names, plus their authorization linkage. The approved name-derived alignment (2026-11-05) trims the supplied name and requires 1–100 ASCII `[A-Za-z0-9_-]` characters, preserving case; the identifier is exactly `mcp:custom:<name>` (`test` → `mcp:custom:test`), not a random suffix. Names are unique within owner + active instance; different users may safely share a name/identifier. Authenticated canonical definition resolution binds owner/instance and rejects old random/noncanonical identifiers whose stored identifier differs from the name-derived value; prelogin validation remains syntax-only. No compatibility, identifier migration or reset. Existing Zova `cabloy-mcp` owns personal CRUD and consent presentation through existing login/site/API state owners; no new site or identity/role/shared/nested scope/policy engine.
- Keep requested scope distinct from effective scope. Consent selects exactly one all/read/custom value, only attenuating request and current registered client ceiling; token responses expose actual effective scope. The resource server applies the same exact restriction to list and direct known-name call, intersected with current tool eligibility, Passport/RBAC, ownership and instance scope.
- Refresh inherits or narrows the original effective tool grant, never gaining tools from edited presets. Rename changes the identifier; rename, tool-set edit or deletion revokes all codes/access/refresh credentials linked through either the old effective scope or the old requested scope, including grants narrowed from that request. Description-only edits do not revoke. Preset changes and consent/code/token/refresh linkage must serialize or conditionally fence revisions with atomic revocation so a concurrent operation cannot escape invalidation or release a stale valid grant.
- Keep `mcp-auth` `fileVersion: 1` and fold approved persistence into its v1 path; no v2 migration, automatic replay/adoption or reset. Reuse the existing PRD/SRS contracts and six bounded ATP subsets specified by `WBS-MCP-20-05`; no runtime, status or release proof is created by this decision.
