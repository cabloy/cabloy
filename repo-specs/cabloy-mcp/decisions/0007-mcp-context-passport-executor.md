# ADR 0007: Proposed MCP Request Context, Passport, and Executor Boundary

## Status

Proposed — design draft for `DEC-MCP-07`, accountable decision owner `zhennann`. This record does not itself accept the separately decided DEC-MCP-02/03 designs or DEC-MCP-04 through DEC-MCP-07, create a context factory, authorize source or provider work, run an ATP, or approve a callable tool. The exact instance/transaction-store isolation mechanism, local identity-mapping adapter, protected headers, deadline propagation, per-operation idempotency contract, and SDK cancellation behavior remain `TODO(confirm)`. The endpoint and enabled tool set remain unavailable pending the separate gates.

This proposal refines [ADR 0001](./0001-mcp-suite-boundaries.md)'s accepted fresh-context and guarded fixed-dispatch boundary. [ADR 0003](./0003-mcp-oauth-resource-server.md) accepts the bounded OAuth design (not its implementation) for validation and local subject mapping; [ADR 0004](./0004-mcp-host-instance-binding.md) proposes early endpoint-to-instance selection; [ADR 0005](./0005-mcp-tool-catalog-registry.md) and [ADR 0006](./0006-mcp-tool-eligibility-risk-results.md) propose the fixed registry, eligibility, output, and risk policy. DEC-MCP-02 owns transport/SDK lifecycle and DEC-MCP-08 owns numeric limits and protected audit/telemetry. This ADR accepts none of the referenced decisions; DEC-MCP-02/03 were separately accepted for bounded design only, and ADR 0009 separately amends DEC-MCP-09 to select one AS-owned database-backed authority with an atomic code-consumption/token-activation commit and Zova presentation of the narrow AS per-request approval flow for bounded design only, without assuming a default explicit multi-statement transaction or approving physical storage, Zova site/admission/SSR, identity/session/CSRF or interaction implementation. DEC-MCP-04 through DEC-MCP-06 and DEC-MCP-08 remain proposed. Neither AS design acceptance nor responsibility assignment approves this context implementation.

## Observed Cabloy Basic source and limitations

- `a-executor/src/bean/bean.executor.ts` creates a new Koa context for `newCtx`, but a nested call without explicit `instanceName` may delegate the **same** `state` and request-headers objects from its caller; when delegated, supplied `extraData` does not replace them. `innerAccess` defaults to true on **each** call. `newCtxIsolate()` fills an explicit instance name, and `mockCtx()` sets a database level and explicit instance name; neither is evidence that a production HTTP call has a fresh Passport **and** an independent transaction store. Fetching an instance or asking `newCtx` to check its readiness is not equivalent to the normal HTTP `initInstance()` check for a missing/disabled instance. `newCtx` starts an adapter-level transaction only when explicitly asked and invokes context completion callbacks after success. The `runInBackground` helper is not a durable or cancellable job.
- `a-executor/src/service/executor.ts` calls `newCtx` again, sets `req.method`, URL, merged request headers, body and optional `onions`, then invokes `SymbolRouterMiddleware` directly. `authToken` inserts another Bearer credential; `extraData` can influence nested state. The result accepts only status `200` and unwraps Cabloy `{ code: 0, data }`; it is not a full external HTTP request or a JSON round trip. Route/body parsing does not reapply HTTP raw-body size limits to the executor's already populated body, and route exceptions are not the full HTTP error path. Router middleware runs the route's guards/interceptors/pipes and controller, but bypasses **system middleware**, including real HTTP ingress/instance setup. A test of `performAction()` cannot prove OAuth/Host/Origin admission, early instance binding, or system-level limits.
- `a-user/src/bean/bean.passport.ts` stores the current Passport in `ctx.state.passport`. `guard.passport.ts` checks the local auth token only when `current` is absent, allows anonymous identity on a public route, and short-circuits **later authorization guards** when `ctx.innerAccess` is true; router interceptors/pipes/controller can still run. `bean.passport.setCurrent()` calls the configured Passport adapter; it does not validate an external OAuth token. Ordinary `signin()` also mints a Cabloy JWT and emits a signin event, so it is not a neutral external-token projection API. RBAC uses the current route/Passport and sets a context-owned decision rather than sharing the delegated `state` reference; that decision must be recomputed in the action context. Row ownership still belongs to the domain model/controller.
- `a-orm/src/service/transaction_.ts` defaults to `REQUIRED`: an existing datasource transaction is joined without upgrading isolation; the owning transaction commits or rolls back, then invokes success or compensation callbacks. A success callback may fail **after** commit. `ctx.commit()` is a context-completion callback and is distinct from a database transaction commit. The retryable AOP replays only its downstream suffix for explicitly allowlisted string error codes; it is not a general retry or deadline policy. `switchDb` can reuse an existing datasource and transaction async-local store when the level/client already match. Separate nested Koa contexts alone therefore do not prove competing operations own independent transactions.
- The inspected incoming HTTP lifecycle has request/response close telemetry, but no observed executor `AbortSignal`, deadline, cancellation-to-transaction rollback, or durable job/call-result record. A detached `Promise.race` or a closed response does not establish that the underlying mutation stopped. These are source observations, not an MCP implementation or measured cancellation behavior.

## Proposed decision

### Admission and fresh identity projection

Only a transport request already bound to an approved endpoint/instance under DEC-MCP-04 and independently validated as an OAuth protected-resource request under DEC-MCP-03 may enter tool discovery or dispatch. Treat the external HTTP context as an ingress carrier, **not** a parent whose headers, Passport, RBAC decision, `state`, transaction, or `req`/`res` are silently inherited by a business call. Validate that the endpoint-bound instance, resource, local-subject mapping and current tool/role policy agree on every call. Fail closed before tool dispatch on any mismatch or identity lookup outage; do not look up another instance to diagnose an absent identity or row.

Propose one dedicated per-call isolated Vona context with an **explicit** approved instance name (including the intentional empty default name), request-owned minimal/synthetic request inputs, a fresh `state` and header map, and a verified datasource/transaction ownership boundary. Initialize the local Passport from the approved, active instance-local mapping inside that context using the existing Passport API/adapter; load current local user, auth and roles from their authoritative owners and check account activation. Explicitly admit only an existing, enabled, ready instance—`newCtx`'s instance lookup/readiness does not by itself perform HTTP `initInstance()` admission—and reject the `null` no-instance/system context; an intentionally configured empty-string default instance is distinct. Do not copy OAuth roles into local roles, pass the external bearer token to `authToken`, invoke local `signin()` just to establish identity, or use `extraData.state.passport` as an unreviewed shortcut. Prove how the selected `newCtx`/`newCtxIsolate` or other context factory initializes instance/config/database/transaction scopes under both live HTTP and tests before choosing one. A new context with a matching datasource level may still share an ambient transaction store; concurrent production calls must not borrow an unrelated transaction or caller callback queue.

An inner `performAction()` call may deliberately delegate `state` to that **same** authenticated per-call context so the existing guard sees the mapped Passport; it must not delegate from an earlier external HTTP request or another call. Check at dispatch that the inner context resolves to the same bound instance, has `innerAccess === false`, and sees exactly the intended local Passport and scoped audit identity; the route's authorization guards must create and validate their own action-context decision rather than inheriting an outer RBAC decision. `guard.passport`'s skip-on-current behavior is safe only if the trusted projection was installed in the fresh context by the MCP boundary. A public/anonymous controller route does not authorize anonymous MCP access. Clear request-owned references at completion; never cache a mutable Passport, context, RBAC decision, or handler closure in the process-level registry.

### Fixed executor invocation and guard scope

Resolve a current, unique, deployment-enabled registry entry to one reviewed method/path/controller action and DTO mapping. Validate the tool arguments **before** invocation and construct path params, query and JSON body only from declared fields. Supply a new server-built options object, with literal `innerAccess: false` **on the inner action call** regardless of the outer context, exact method/path and trusted minimal headers. Never spread caller arguments or protocol headers into `IPerformActionOptions` or `INewCtxOptions`; in particular do not forward `Authorization`, cookies, `Host`, forwarding, instance selector, `authToken`, `onions`, `extraData`, state, request/response objects, trace override, or arbitrary route/URL/method controls. Reject caller-controlled query token keys: the ordinary local JWT extractor checks query credentials before Authorization, and a current Passport may skip token re-verification altogether. Review existing action and JWT debug logging before enabling any entry; transport-layer redaction alone does not establish that downstream AOP logging suppresses sensitive arguments, results or credentials. Refuse calls for which the route, guard chain, status, result projection, or required system-only controls cannot be proven to survive router-only dispatch. No caller-provided value may select or replace the already bound instance.

Controller-level route guards/AOP, local RBAC and domain row/data-scope checks remain mandatory, but router-only execution does not replay the public HTTP system middleware. MCP explicitly owns the corresponding OAuth, trusted ingress/instance, limits, policy and redacted audit admission at its boundary; do not claim they ran simply because `performAction` ran. Capture and verify the effective registered route and guard/AOP behavior, including authorization denial and role/row revocation between listing and calling. Runtime results then pass the independently reviewed DEC-MCP-06 JSON output projection; no raw executor value or exception is an external fallback.

### Operation lifetime, commit, failure and retry

The domain controller/service retains transaction, locking, idempotency and external-side-effect ownership; MCP adds **no default wrapper transaction** and does not upgrade isolation or use `REQUIRES_NEW` to hide an ambient transaction. If a candidate needs atomicity, it must document and verify the owning `@Core.transaction(...)`/domain policy. Database commit, transaction success callbacks, context-completion callbacks, external effects, MCP result filtering, audit, and client delivery are distinct boundaries. A failure of any later step cannot prove an earlier commit or external call was undone. Record protected outcome classes such as rejected-before-dispatch, rejected-in-operation, completed-and-delivered, and execution-started/outcome-uncertain; the latter must not be falsely reported as rolled back or successfully delivered. The exact client error taxonomy and protected telemetry belong to DEC-MCP-02/06/08.

Transport disconnect, client cancellation or deadline expiry stops **admission of new work** and prevents further response writes where possible; it is not a blanket rollback or proof that already dispatched work has stopped. Propagate cooperative cancellation only to operations whose domain and adapter semantics have been explicitly reviewed, and keep a bounded, observed execution/accounting lifecycle until work settles or a separately designed durable recovery owner takes over. Do not implement timeout as a fire-and-forget `Promise.race`, or use `runInBackground`/in-memory callbacks as proof that work will survive disconnect/process loss. The exact abort signaling, deadline values, resource cleanup and safe response behavior require real transport/SDK verification with DEC-MCP-02/08 before enabling calls; if no bounded and truthful behavior can be demonstrated, leave the affected tool disabled.

The adapter never automatically retries a failed or uncertain tool call. In particular it must not replay on transport timeout, disconnect, response-filter failure, post-commit callback failure, or uncertain external effect. Existing domain `@Core.retryable(...)` may retry only a **documented replay-safe downstream suffix** with an explicit transient-error allowlist and appropriate transaction ownership, and only after checking that it cannot replay a committed effect. A low-risk mutation that might be submitted twice by a client requires its owning domain's reviewed idempotency/reconciliation contract; no generic executor idempotency key, exactly-once guarantee, or MCP-owned persistence is assumed. Until duplicate submissions and uncertain outcomes are safe for that operation under its declared risk policy, do not enable it.

### Concurrency and proof boundary

Prove both subject and instance separation, including simultaneous authentication and authorization, route guard and row-scope evaluation, transaction ownership, callback/audit classification and response delivery. Unit/integration tests with scoped state must own `app.bean.executor.mockCtx(...)`; each intentionally competing operation uses a separate **top-level** `mockCtx(...)` after setup, not nested contexts sharing an ambient transaction. Use explicit barriers/interleaving, then assert the combined durable outcome and cleanup in `finally` with precise test-owned identities. Do not infer business contention from test-runner parallelism, `TEST_CONCURRENCY=false`, or a new Koa context alone. Real HTTP tests separately prove trusted host binding, OAuth admission, native transport lifetime and disconnect behavior; executor-only tests cannot stand in for those checks.

## Alternatives rejected or deferred

- **Nested `newCtx` or `authToken` alone as identity isolation:** rejected; delegated state/headers and skip-on-current Passport behavior may retain an unrelated caller identity, while the generic token path is not the MCP OAuth validator.
- **Copy the validated external bearer token into a local JWT/`signin()` flow:** rejected; external resource-token validation and current local Passport projection are separate authorities, and local signin has issuance/events not required for a tool call.
- **Trust `innerAccess: false` as a full HTTP security boundary:** rejected; it restores applicable route guards but does not invoke system middleware or prove instance/transport/OAuth enforcement.
- **Treat timeout, disconnect, cancellation, or error response as a rolled-back mutation:** rejected; commit callbacks, output filtering and delivery can fail after durable effects.
- **Retry every failed call or promise-race into detached background work:** rejected; the executor provides no generic exactly-once, cancellation, or durable completion facility. Per-domain replay-safe recovery may be proposed separately.
- **Add MCP resource-module-owned idempotency/consent/job persistence:** deferred; the initial `cabloy-mcp` scaffold has no schema. ADR 0009 selects an AS-owned database-backed atomic-commit authority and Zova presentation of the AS-owned per-request browser flow for design only; it does not approve these MCP stores, a physical AS store/schema or a Zova site/admission implementation. Any new persisted field needs separate approval and the owning module's `vonaModule.fileVersion` decision before schema work.

## Acceptance and execution gates

Before accepting `DEC-MCP-07`, `zhennann` must separately review and record:

1. the concrete context/instance/datasource/transaction-store isolation mechanism and request-owned `req`/`res`/state/header lifecycle for real HTTP and router-only invocation; prove enabled-instance admission equivalent to the skipped system middleware and verify how inner executor delegation is limited to the same call;
2. the approved DEC-MCP-03 local identity adapter and active user/auth/role loading, Passport `setCurrent`/guard behavior, and cross-subject/cross-instance denial without raw bearer or local JWT impersonation;
3. exact server-owned `performAction` options, enabled route and guard/AOP coverage, required system-only controls implemented at MCP admission, safe status/result/error handling and correspondence with DEC-MCP-05/06;
4. timeout and cancellation semantics with the selected DEC-MCP-02 SDK, bounded execution/cleanup under DEC-MCP-08 limits, commit/callback/external-effect outcome classification, per-domain replay/idempotency constraints, and what stays disabled when these cannot be proven;
5. explicit different-subject/instance competing contexts and durable outcome tests for `ATP-MCP-CALL-02/03`, plus `ATP-MCP-AUTH-02` and **real HTTP** `ATP-MCP-INSTANCE-01`/`ATP-MCP-TRANSPORT-01` for system-middleware and disconnect boundaries; record revision, fixture, interleaving and redacted evidence only after a separately approved execution dossier.

This is a proposed planning contract, not runtime proof. No MCP controller, authentication provider, context factory, enabled tool, or ATP result is created by writing it.
