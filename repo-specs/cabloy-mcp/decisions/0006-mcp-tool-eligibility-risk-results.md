# ADR 0006: Proposed MCP Tool Eligibility, Risk, and Result Policy

## Status

Proposed — design draft for `DEC-MCP-06`, accountable owner `zhennann`. This record does not accept a first tool, a risk exception, a confirmation mechanism, `DEC-MCP-02` through `DEC-MCP-05`, or implementation/ATP execution. The first allowlist, each domain owner's side-effect and field review, and the exact adapter and deployment policy remain `TODO(confirm)`. Until they are reviewed, the enabled tool set is empty.

This proposal refines [ADR 0001](./0001-mcp-suite-boundaries.md)'s accepted JSON-only and guarded-executor boundary. [ADR 0005](./0005-mcp-tool-catalog-registry.md) owns candidate identity, metadata, route correlation, and registry freshness; this decision owns **which candidate shapes and effects may be enabled**, how visibility and call policy apply, and what may be returned to an external client. `DEC-MCP-07` owns request-context/Passport isolation, executor mechanics, timeout, retry, and commit boundaries; no ADR for that gate is accepted yet. `DEC-MCP-08` owns numerical limits, audit sinks/retention, and operational redaction. References to other proposed decisions do not accept them.

## Observed and normative inputs

- Existing Vona/OpenAPI contracts are candidate inputs, not evidence that a route is safe to invoke or that its emitted schema matches every runtime result. `a-openapi/src/service/openapi.ts` emits a 200 JSON response schema (normally wrapped), while `a-executor/src/service/executor.ts` directly invokes router middleware, accepts only status 200 as success, unwraps `code: 0` to `data`, and does not perform a JSON serialization round-trip. `a-serialization/src/bean/bean.serializer.ts` patches selected fields but preserves undeclared object properties; neither the DTO nor the serializer is an MCP field allowlist. Pre-populated executor bodies also bypass ordinary raw-body parser checks. The fixed executor design requires explicit `innerAccess: false`; the MCP adapter must separately validate inputs and results and preserve downstream controller guards and business ownership checks. Source inspection alone cannot prove a specific business operation has no side effects or safe output fields.
- The MCP [2026-07-28 tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) supports an object-root input schema and optional output schema; `structuredContent` may carry **any JSON value**, and a server defining `outputSchema` **MUST** return matching structured content. A tool result also contains a `content` array; a JSON text block is recommended for backward compatibility, not an independent unreviewed result. Tool execution failures use `isError: true`; malformed requests and unknown tools use protocol/JSON-RPC errors. The final wire/error mapping must be rechecked with the SDK chosen by `DEC-MCP-02`.
- MCP [tool annotations](https://modelcontextprotocol.io/specification/2026-07-28/schema#toolannotations) are untrusted hints, not safety proof or an authorization grant. In this revision, omitted hints default conservatively (`readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: false`, `openWorldHint: true`); these defaults do not replace a server-owned classification. The specification recommends client-facing human review/confirmation for sensitive calls, but does **not** mandate that every MCP tool call has a human confirmation. A server-verifiable confirmation requirement below is an application safety policy, not a claim about automatic MCP consent.

## Proposed decision

### Admission and reviewed risk classes

A candidate can enter the deployed registry only when its domain owner and MCP operator review a named controller action, its enabled route and OpenAPI/DTO projection, effective guard/data scope, input/output fields and runtime shape, side effects, external interactions, and specific policy owner. Maintain a review record/fingerprint alongside the authored allowlist without adding MCP-owned persistence. Missing classification, review, schema, mapping, or deployment enablement means **not enabled**, even if the route is otherwise public. A metadata annotation alone cannot self-certify a tool.

| Risk class                                                                           | Proposed first-increment treatment                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Read-oriented, no business-visible or external side effects                          | Eligible after shape/field review and explicit allowlist; GET alone is insufficient. Routine internal telemetry does not by itself imply a business mutation, but a write to business state, notification, or external call does.                                                                                                         |
| Bounded reversible mutation with known effect and authorized owner                   | Eligible only after individual domain/operator approval, a narrow deployment policy and OAuth scope, current local authorization, and an audited result/side-effect contract. A generic `write` or admin scope alone is insufficient. If domain policy requires confirmation, apply the gate below rather than silently downgrading risk. |
| Destructive, externally irreversible, open-world/callback, or unclassified operation | Disabled in the first increment. An explicit exception requires a separate reviewed decision covering domain effect, trusted confirmation, data disclosure, idempotency/recovery, and applicable ATP; a metadata hint or HTTP method cannot create the exception.                                                                         |

Classification records must distinguish business mutation from read, reversible from irreversible, idempotent from non-idempotent, sensitive from ordinary results, and whether a call reaches external systems. Review side-effecting GETs as mutations; reject unclassified or misleading `readOnlyHint` declarations rather than advertising them as safe. Publish only truthful, reviewed presentation hints consistent with the server's policy. Hints never relax list or call checks. A future effect/shape change invalidates the prior risk review and the registry entry until reapproved.

Visibility is the current **intersection** of deployment enablement, validated resource-bound token and scope/client grant, bound instance, active local subject, local RBAC/guard policy, applicable data-scope visibility, and risk/confirmation policy. A tool with only argument-specific row scope may be listed when the subject is allowed to attempt it, but listing never promises a particular row is accessible. `tools/call` repeats the effective gates against validated arguments immediately before fixed dispatch; the domain operation still enforces resource ownership. Do not probe across instances or reveal whether an unrelated resource exists. If revocation or policy refresh cannot be established, fail closed rather than trusting a cached list or a caller's assertion.

### Confirmation boundary

A `confirm: true` argument, a tool description/annotation, a client-side approval screenshot, or a prior `tools/list` response is **not** a server-verifiable grant. For any operation whose domain/deployment policy requires per-call confirmation, enable it only after separately approving a trusted confirmer, verified subject/client/instance/tool/argument binding, one-use or otherwise replay-safe consumption, expiry, concurrency behavior, cancellation, and protected audit/evidence. No such channel or persisted consent store is selected here; without that approval the confirmation-required operation stays disabled. Reversible mutations explicitly reviewed as **not** requiring per-call confirmation still require narrow scope, deployment opt-in, local authorization, and auditing. The absence of an MCP-owned UI or consent database is not permission to invent a confirmation flag.

MCP 2026-07-28 offers optional multi-round-trip `input_required` / `elicitation/create` when the client advertises support; it is **not automatically a trusted confirmation mechanism**, nor an unconditional part of the first increment. Adding it requires an explicit transport/client capability, requester identity, state-binding, cancel/decline, result-verification, and security review. URL elicitation consent covers opening a URL, not proof an external action completed. A client that cannot support the approved confirmation channel cannot call confirmation-required tools. No deferred Zova consent UI or MCP-owned durable consent is introduced by this ADR.

### Input/representation eligibility

Require a reviewed JSON object-root `inputSchema` derived from DTO/OpenAPI, with resolved references and a deterministic mapping of allowed path, query, and body fields. Verify effective request content types and runtime validation/serialization; reject undeclared, ambiguous, prototype-control, method/route/URL/host/header/cookie/authorization/instance/onion/state override fields before business dispatch. A business identifier may be an ordinary declared DTO value but never an instance selector or an authority grant. If a field legitimately contains an external URL, callback, resource-fetch target, or user-controlled destination, treat the operation as open-world/high-risk and disable it pending an independently reviewed outbound policy; do not treat string shape as SSRF protection.

Admit only bounded ordinary JSON requests and responses with known status, envelope, and shape. With the inspected executor, that means review and test a **200-status** action and its actual unwrapped return value; 201/202/204 are not assumed to work or mean no effect. By default exclude multipart/form-data, raw bodies, binary/files, redirects, streaming/SSE business responses, non-JSON payloads, arbitrary headers/status handling, unsupported framework response envelopes, and async job/notification workflows. A separately reviewed adapter may make a compatible shape eligible only if it preserves the DTO contract, fixed dispatch, security invariants, and explicit ATP proof; it cannot silently convert a download, redirect, or callback into a first-increment tool. The raw-body parser is not rerun when the executor supplies a body, so MCP-owned limits and validation are required before dispatch; exact byte/depth/time/concurrency/rate bounds belong to `DEC-MCP-02/08` and must be approved before exposure.

### Output and failure contract

For each approved entry, require an explicit reviewed output projection/schema and a runtime check after executor adaptation. Retain the existing domain row/ownership checks; independently allowlist the result fields and nested relationships that the external client may receive. Do not pass through arbitrary model attributes, headers, framework envelopes, diagnostics, tokens, credentials, authorization records, usable secret links, or cross-resource data. Decide whether an approved empty, `null`, object, array, string, number, or boolean response is meaningful for that operation; every emitted result must be JSON-compatible, finite where numeric, within approved bounds, and consistent with any published `outputSchema`. A runtime mismatch fails the tool safely rather than returning raw output or modifying a committed domain effect.

Propose `structuredContent` for the approved JSON value and a `content` JSON text representation only when both can be generated from **the same filtered value** and both meet the disclosure/size policy. The text block must not bypass output filtering or independently serialize the unfiltered Vona response. Do not claim the optional output schema or compatibility text is a protocol-wide MUST; making a reviewed output contract mandatory for enabled entries is a local policy. The exact per-operation null/scalar/schema and SDK conversion behavior remain `TODO(confirm)`.

Distinguish (1) HTTP OAuth/host/transport failures, (2) malformed protocol, unknown tool, or invalid call envelope, and (3) a valid tool call whose business execution/validation fails. Map these to bounded protocol/JSON-RPC errors or `isError: true` tool results according to the chosen revision; do not turn failed work into apparent success or leak downstream stack traces, SQL, unrelated existence, or raw arguments. An authorization failure cannot fall back to inner access or another route. A status, serialization, or output-filter error may happen **after** the domain effect or commit; never infer rollback from an error response or simulate a pre-execution preview by invoking the action. A timeout/disconnect after a domain commit does not prove rollback or permit an automatic non-idempotent retry; `DEC-MCP-07` must define the final outcome/recovery semantics and `DEC-MCP-08` the protected telemetry for uncertain outcomes.

## Alternatives rejected or deferred

- **Allow all guarded/GET/OpenAPI routes:** rejected; guards do not prove row scope, content safety, or absence of business effects.
- **Make protocol annotations or a client confirmation flag enforce risk:** rejected; both are untrusted caller-visible hints without a verifiable grant.
- **Enable destructive tools by default because a client can present a prompt:** rejected; there is no approved, server-verifiable consent channel or idempotency/recovery policy in the first increment.
- **Return the executor result verbatim or rely on a text block to hide schema drift:** rejected; both can disclose unapproved fields and turn runtime mismatch into apparent contract success.
- **Use an MCP-owned consent/audit database to unblock confirmation:** deferred; it contradicts the accepted no-new-persistence increment and would reopen `DEC-MCP-09` and the `vonaModule.fileVersion` gate.

## Acceptance and execution gates

Before accepting `DEC-MCP-06`, `zhennann` must separately review and record:

1. the first candidate/tool allowlist with each domain owner, route, DTO/schema/field projection, effective authorization/data scope, truthfully classified effects, and explicit deployment policy/scope; leaving the list empty is acceptable for planning but does not meet a launch outcome;
2. which reversible mutations, if any, are eligible without per-call confirmation; the destructive/irreversible/open-world default-deny rule, exception process, and risk-hint truthfulness;
3. whether any call requires confirmation and, if so, an independently approved trusted verifier, subject/client/instance/tool/argument binding, replay/expiry/cancel behavior, capability fallback, and audit ownership; otherwise those calls stay disabled;
4. exact input mapping, framework response-envelope/status support, optional output-schema/structured-content and compatibility-text handling, field minimization, JSON scalar/null and limit behavior for the selected SDK/protocol;
5. current role/policy/data-scope visibility and call-time recheck, plus nondiagnostic protocol/tool-failure mapping coordinated with `DEC-MCP-02/03/05/07/08`;
6. negative/positive `ATP-MCP-CONTRACT-03`, `ATP-MCP-AUTH-02`, `ATP-MCP-CALL-01/03`, and `ATP-MCP-OPS-01` scenarios, with revision-bound runtime proof only after a bounded source-execution dossier.

This is planning, not a runtime risk assessment of actual enabled operations; no controller, provider, tool, schema, or confirmation channel has been created or approved.
