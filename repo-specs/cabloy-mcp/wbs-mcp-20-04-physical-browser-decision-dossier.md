# WBS-MCP-20-04 Physical State and Zova Browser Decision Dossier

## Disposition and authority

**Design record with bounded dispositions; no concrete physical or browser implementation is accepted by this dossier.** Prepared on 2026-10-14 for the Cabloy Basic worktree. [ADR 0009](./decisions/0009-mcp-as-state-boundary.md) accepts the _logical_ integrated `a-auth` AS, one AS-owned database-backed authority with code consumption and token activation in the **same atomic commit**, and Zova presentation of an AS-controlled explicit approve/deny interaction for **every** request. On 2026-10-14, the bounded directions in packages A and B were separately accepted: package A's trusted-instance-scoped aggregate/opaque-credential state direction and package B's Basic Web/AS bridge/browser-flow direction. A separate 2026-10-15 target choice selects SQLite via `better-sqlite3` on Vona's existing primary datasource for the first AS implementation, without establishing actual deployment configuration or atomicity. This record still does not select a schema, site/role policy, server-session implementation, migration or execution.

The [earlier candidate analysis](./wbs-mcp-20-04-physical-browser-proposal.md) explains the source observations and protocol pitfalls; the [execution dossier](./wbs-mcp-20-04-execution-dossier.md) remains a blocked planning draft. The initial `cabloy-mcp` resource-server scaffold stays schema-free, no remembered consent or refresh token is added, and `WBS-MCP-20-04` and dependent `WBS-MCP-20-02` remain `blocked`. There is no AS source, runtime evidence or `ATP-MCP-AUTH-03` result.

## Decision package A — one authoritative AS state

**Accepted bounded design direction:** one `a-auth`-owned, trusted-instance-scoped authorization aggregate per browser authorization request, addressed by non-authoritative locator plus independent high-entropy-secret opaque credentials, and two independent conditional transitions: pending → approved/code-ready (or terminal denial) and approved/code-ready → consumed/token-active. Each transition must commit its complete effect once. This is not selected DDL, an ORM method, a cross-dialect SQL recipe, a table name or a mandate to avoid a transaction when one is needed. A multi-record AS-owned representation with a verified single atomic redemption commit remains a viable implementation alternative if the aggregate cannot satisfy actual client/retention requirements; any alternative requires reconciling with this bounded direction before execution.

| Logical field group (candidate, not DDL) | Binding and lifecycle                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Instance and identity                    | Database-generated aggregate locator/row identity scoped to the **trusted** Vona instance, issuer/profile identifier and transition revision. The locator cannot choose an instance or authenticate a client.                                                                                                                 |
| Request truth                            | Registered client/profile, exact validated authorization-time redirect, canonical registered resource and its enabled-instance relation, requested narrow scopes, explicit S256 challenge, creation and absolute pending expiry. Immutable once created; client OAuth `state` is correlation for the validated redirect only. |
| Browser/decision                         | A separately reviewed browser/session binding, per-request decision CSRF binding, terminal decision and decision time, server-verified subject and approved scope subset. Neither possession of a pending reference nor a frontend flag is authorization.                                                                     |
| Authorization code                       | Code digest, issue/absolute expiry and consumption time, assigned **only on a winning approval**. The authorization-time redirect binding remains on the aggregate even if the selected token protocol branch omits a token-request redirect field.                                                                           |
| Access token                             | MCP-only opaque-token digest, issue/absolute expiry and token/grant revocation marker. The digest becomes active only in the **same committed conditional mutation** that consumes its one-time code; no refresh family or separate SQL/Redis token authority.                                                                |

**Credential lookup choice for review:** an opaque code/token carries a non-authoritative aggregate locator and independent high-entropy secret. The AS/RS establishes the trusted issuer/resource/instance first, selects the exact instance-scoped row and credential kind, then compares the protected secret digest and current complete authorization state. A primary database row identity provides addressing, not business uniqueness for a caller-selected client/resource or authorization. This variant needs explicit wire-format version/kind separation, lossless database-ID encoding/limits, entropy, digest/domain-separation, key custody/rotation, enumeration/privacy, backup/restore/row-reuse behavior and RS lookup approval. A digest-only credential is a second option, but requires a proven creation-time **instance-aware** uniqueness/ambiguity strategy. Random generation plus an absent-key check, or CAS on an existing row, does not serialize creation; `table.unique(...)` cannot be used as the tenant-business-uniqueness shortcut.

**Candidate transition contract:**

1. Admit a trusted instance before generic Vona instance resolution; validate issuer, registered client, exact redirect, canonical resource/instance registration, scope and explicit PKCE S256, then create one pending row. If a separate client or browser registration needs two durable writes or creation-key serialization, use a proven atomic boundary rather than claiming the later redemption CAS covers it.
2. At approval, re-check current account, registration, resource, browser binding, CSRF, expiry and site admission. Generate a code in request memory; a scoped condition on aggregate identity, current revision, pending status, absolute expiry and no revocation sets the approved subject/scopes and code digest in **one winning commit**. Deny/cancel/expiry compete for the same pending state and assign no code. Only after the winning approval **commit is confirmed** may the AS construct an OAuth response with that raw code to its previously validated redirect. Losing workers discard their candidate material; a lost redirect cannot reconstruct or reissue a code from its digest.
3. At redemption, independently authenticate the client and verify code secret, original binding, S256 verifier, canonical token-request resource, scope, expiry, revocation and the selected redirect compatibility branch. Generate a token in request memory; **one scoped conditional mutation** sets code consumption, token digest/issue/expiry, token-active status and revision together. Exactly one _committed_ affected row wins; zero/unknown cannot return a credential. The raw token is returned only after the owning commit is confirmed. Never infer commit from a returned object, a successful preliminary read or an update inside an ambient uncommitted transaction. Commit-acknowledgement uncertainty and a committed-but-lost HTTP response are not permission to replay issuance.
4. Revocation is monotonic and competes correctly with redemption. Every protected lookup uses fresh authoritative state, including issuer/profile, client, subject, grant, canonical resource, trusted instance, narrow scope, absolute expiry and revocation; it denies on ambiguous/missing/stale/unavailable state. In particular, a lookup **begun after acknowledged revocation** must not inherit an older ambient snapshot transaction and accept a stale grant. A lookup already admitted before revocation is a separate RS/domain in-flight policy, not retroactively cancelled by this AS promise. No positive token cache, stale read replica, Redis marker or ordinary JWT fallback can establish current validity. Cleanup is not validity enforcement.

**Source-specific obstacle:** cached Vona `model.update()` may reduce the predicate to selected IDs, while the underlying mutation does not expose a reliable affected-row success contract. `getForUpdate()` needs a transaction and returns only one match. A narrow, carefully scoped database adapter may be evaluated, but raw builders need explicit instance/deleted filters, conversion, timestamp, secret-safe SQL/error/binding logging and cache behavior; parameterization alone is not redaction. Its connection can join ambient transactions, and `REQUIRED` does not upgrade isolation. Affected-row `>1` discovered **after** an autocommitted broad update is damage, not a recoverable conflict: address exactly one trusted aggregate row and enforce the full state predicate before mutation. No exact method, query, isolation level or SQL statement is approved here; verify the actual deployed driver/dialect and whether AS issuance **and current lookup** reject ambient transactions or otherwise guarantee the owning commit and freshest revocation state. If multiple writes are chosen, use an appropriate atomic transaction or seek an explicit authority revision—never consume the code in one commit and activate the token in another.

**Migration and deployment gate:** `a-auth` currently has `fileVersion: 1`; editing only its version-1 `meta.version.ts` cannot upgrade existing installs. A future AS schema requires a separately selected owning module and migration/check implementation within the accepted fresh-only installation scope/exclusions, actual-target classification and exact deployed dialect/driver/topology, **tenant-aware client-registration business uniqueness**, client registry/secret custody, lifetime/retention/deletion, clock and outage policy. The first implementation now targets SQLite via `better-sqlite3` on Vona's existing primary datasource; actual deployment configuration and SQLite-specific transition/migration proof remain open, and tests on this dialect do not certify PostgreSQL/MySQL AS support. The further 2026-10-15 inputs select same-host multiple Vona workers sharing persistent SQLite through that primary datasource and, if persistence resides in existing `a-auth`, keeping `vonaModule.fileVersion: 1` and folding schema into version 1's creation path. No version-2 migration or automatic upgrade of already-recorded v1 databases is selected. Supported fresh-only installation scope/exclusions are accepted; exact owner/schema, actual-target classification and migration/check implementation remain open before persisted edits. Existing-v1 upgrade/adoption and missing-history/partial/unknown-state treatment are excluded or blocked pending separate disposition; a different owner requires its own version disposition. Cross-host SQLite and replica support are not selected. Mandatory prospective proof includes cross-worker approval/redemption contention, acknowledged-revocation visibility and connection/failure behavior, not just single-process contexts. These choices are not deployment attestation or execution approval. After an approved `meta.version.ts` edit, root `npm run test` is mandatory. Do not run reset/init to force migrations during planning.

## Decision package B — AS-owned browser contract with Zova presentation

**Accepted bounded design direction; concrete browser implementation remains gated:** evaluate the observed Cabloy Basic Web site with a narrowly scoped authorization page, not an Admin management page or an independent MCP site. This is conditional: protected Web _and_ Admin routes require authentication plus role `siteIds` admission, and built-in registered-user and system-admin roles both currently allow `*`. Confirm the actual authorizing population and assigned-role/site policy; do not broaden roles merely to admit a page. A distinct site/flavor is an alternative only after its additional tuple, build, admission and privacy cost is expressly approved. The MCP resource-server endpoint still owns no Zova page; general management UI remains deferred. The 2026-10-14 disposition accepts the package's bounded direction—Basic Web evaluation, AS-verifiable short-lived HttpOnly bridge, fixed internal continuation, independent request-bound CSRF, synchronous per-path early instance admission and AS-built final redirect—not a concrete site, route, bridge lifecycle, schema, source or execution.

**Accepted direction with proposed browser flow (not an approved identity implementation):**

1. **Entry and instance:** separately classify AS authorization, page/resume/login bridge, summary/decision, token and discovery paths **before** Vona instance initialization. A registered resource may be _looked up_ to choose an enabled instance, but caller-controlled resource, pending reference, Host, query or header is not by itself a trusted instance selector. State exactly how issuer-global endpoints differ from instance-bound endpoints, and how a resumed browser request locates its bound instance before ordinary Vona context setup. The current `getInstanceName(ctx)` hook is synchronous and invoked during context setup, before middleware; it cannot wait for a POST body or asynchronous database lookup. Review a deployment-owned, synchronously resolvable per-path ingress map, including login/callback/resume, or a separately justified earlier admission mechanism. ADR 0004's proposed `/mcp` hook does not cover this route family.
2. **Pending and login:** the AS validates pre-registered client, exact redirect, canonical `resource`, scopes and explicit S256 before storing pending truth. It binds a short-lived opaque pending/browser reference separately from OAuth client `state`, upstream-login state, decision CSRF and PKCE. If login is needed, return through a **fixed internal** continuation bound to that pending request; do not feed the OAuth client redirect or arbitrary `returnTo` into the existing navigation helpers. Recheck instance/account/expiry after login or account switching.
3. **Identity bridge and summary:** the Zova-managed token cookie and `$passport.isAuthenticated` are not a server-verifiable AS browser session; frontend API interception adds bearer headers but a native form POST will not. A bounded candidate is a same-origin bearer-authenticated AS bootstrap that explicitly verifies the existing access token and its server-side session marker, checks account **activation** and trusted instance/site admission, then binds the pending request, verified user/auth identity and browser to a new short-lived AS-owned HttpOnly session. The AS decision POST would validate that session through its own adapter, not by enabling global JWT cookie extraction. This is **not** selected or proven: the existing passport token check enforces active account and, where configured, a Redis marker, but activation is a separate guard; its serialized local identity contains user/auth IDs, not an instance claim. Existing sign-in may refresh/reuse a marker, so account switching is not automatic AS-session invalidation; a native POST cannot see the frontend's current bearer. Approve the narrow bridge, account-switch/logout/revocation linkage and fresh identity/account checks before a native POST, together with an independently checked Origin and per-pending CSRF proof. Do not repurpose reusable OAuth-code/temp-token JWT helpers or call `signin()` merely to establish the bridge. AS protected summary returns only an escaped, minimal client/account/resource/scope display projection, never authoritative hidden fields for Zova to decide. Define cookie scope, SameSite, session lifetime/rotation, cross-tab and replay behavior; an AS HttpOnly session is a candidate, not an observed facility or selected mechanism. The existing JWT sign/verify debug log interpolates raw tokens, so any bootstrap reuse needs a verified logging/redaction disposition before tests or operation.
4. **SSR and decision:** for a cookie-backed protected page, review an explicit `ssrProfile: 'session'`, a neutral server/hydration shell, and a post-hydration/admission model-owned minimal-summary query that neither persists nor dehydrates sensitive data. `private, no-store` alone does not suppress hydration payloads. The existing protected Zova router guard may redirect before this page renders; a neutral shell and AS cookie alone do not supply its Passport/site admission or reconcile the server and hydration guards. Review the exact route-guard/admission behavior without bypassing AS-side identity checks. A browser-native **same-origin decision POST** is a candidate only after the identity bridge and independent request-bound CSRF exist. The AS revalidates current user, instance/site/registration/redirect/resource/scope/pending state and commits one approve or deny outcome; Zova renders choices but cannot issue a code or supply a redirect URI. An AS-owned top-level response goes only to the previously validated bound callback on redirectable outcomes; invalid client/redirect failures terminate locally. Existing `ctx.redirect()` admits only 301/302 and applies a generic external-origin check; any different OAuth callback response status or origin allowance requires a separately reviewed response mechanism and must never replace exact registered-redirect validation. An AJAX redirect by itself does not navigate the top-level browser. Decide cancellation, local errors, duplicate submissions, origin/referrer/framing/no-store protections and explicit user-facing recovery.
5. **Token and metadata:** enforce the same canonical `resource` at authorization and token exchange as the selected stricter local profile, PKCE S256 even when `code_challenge_method` is omitted (reject omission because RFC 7636 otherwise defaults to `plain`), and the reviewed public/confidential-client authentication policy. Decide OAuth 2.1 draft-13 versus any OAuth 2.0 compatibility branch for the token-request `redirect_uri`: the former does not universally require it, while the latter requires the identical value when supplied at authorization. If RFC 9207 `iss` is selected, advertise and emit it on **all redirectable success and error** responses matching issuer metadata. Unregistered/invalid redirects never become redirect targets. Publish truthful no-refresh, registration and metadata behavior.

**Unresolved dependency, not a claim of feasibility:** the listener creates Vona context before ordinary middleware; `a-instance` can select query/header/subdomain. A protected Zova route and a controller guard run too late to undo a wrong instance. Some browser and token requests do not yet carry a _trusted_ resource-to-instance binding before synchronous context setup. The concrete admission/bootstrap strategy and its first-HTTP validation must be approved for **each path**, including login and callback, or this Web/native-form candidate must remain blocked. No code or path/parameter name is chosen here to conceal that gap.

## Future verification, not observed evidence

After separate design and execution approval, [ATP-MCP-AUTH-03](./test-plan.md#atp-mcp-auth-03-authorization-server-issuance-grant-and-token-lifecycle-prospective-no-runtime-proof) must include the confirmed same-host multi-worker shared-persistent-SQLite/`better-sqlite3` primary-datasource and two-instance fixture, approved keep-v1 fresh creation, existing-v1 non-replay/denied activation and missing-history/partial/unknown-state rejection within the accepted exclusions (upgrade/adoption or recovery treatment requires separate disposition), forced locator/digest collision and ambiguous lookup, cache bypass and no replica fallback, competing approval/denial/revocation/redemption across **separate worker processes and Vona contexts**, connection contention/failure, failure before versus after commit, lost redirect/token response and uncertain commit acknowledgment. Prove fresh lookup begun on one worker after another acknowledges revocation; single-process contexts alone cannot close the selected topology's proof. Assert the _combined durable state_ (at most one code and one current token per authorization), not runner scheduling or a successful method return. Exercise store outage, multi-worker revocation, account/client/resource disablement, no-refresh and redacted output.

Real-HTTP browser proof additionally covers early AS instance selection across every route, Web/site admission for intended users, login continuation/account switch, native form authentication, CSRF/origin/cross-tab conflicts, escaped summary, no-store/referrer/frame and SSR/hydration disclosure, and redirectable success/error versus invalid redirect. Never retain raw codes, tokens, cookies, client secrets, complete claims or signed state in evidence. `ATP-MCP-AUTH-01` remains distinct RS proof; a planning audit or chart freshness result is not either ATP.
