# A-MCP Threat Model and Policy Matrix (Draft)

## Status and authority

This is a **proposed security design** for `WBS-MCP-10-02`, which received its separate named-reviewer documentary `planning-complete` closure after the required task-local `Completion mode: planning-only.` declaration was added. That closure does not accept the open security mechanisms, authorize implementation, prove an ATP, or approve production exposure. It applies to the first-increment `cabloy-mcp` remote tools boundary in [ADR 0001](./decisions/0001-mcp-suite-boundaries.md), [PRD](./prd.md), and [SRS](./srs.md). `WBS-MCP-10-01` is `planning-complete` under its separate named-reviewer closure. DEC-MCP-02's transport profile, SDK versions, and integration design were subsequently accepted on 2026-10-07 (design only). DEC-MCP-03's bounded OAuth design was subsequently accepted on 2026-10-09 (design only); ADR 0009's 2026-10-10 design-only amendment selects the integrated `a-auth` logical AS and `zhennann` for implementation/operations, one AS-owned transactional-database authority and an AS-owned per-request browser grant flow. Physical storage and browser/session/CSRF implementation, host/proxy, context, operations and other integration choices remain gated under DEC-MCP-03/04–08 and DEC-MCP-09; application limits and runtime transport behavior also remain unverified. No MCP suite/module source or runtime evidence exists.

The policy below expresses the already specified **fail-closed requirements** and the tests needed to assess them. A row marked `TODO(confirm)` must not be implemented by guessing a permissive default. In particular, a design sketch is not an approved OAuth issuer, endpoint resource identifier, host mapping, registry, confirmation mechanism, or audit sink.

## Assets, actors, and trust boundaries

Protected assets: access tokens and credentials; instance identity; local Passport and RBAC state; business records and ownership/data scopes; controller side effects; the server-owned tool registry, DTO/OpenAPI schemas, and deployment policy; redacted audit and operational evidence.

- **External AI client / tool arguments / protocol headers:** untrusted, even after obtaining a valid token. A tool description, result, or schema field may contain untrusted content; it is not a policy instruction.
- **Endpoint and reverse proxy:** the proxy/host configuration is a trust input only after an approved deployment model; a caller-supplied `Host`, forwarded header, query selector, or instance header is not independent tenant authority.
- **OAuth authorization server to MCP protected resource:** token validation and resource binding precede protected tool discovery/calls. Public protected-resource metadata is discovery information, not an authenticated tool listing or permission grant. The accepted bounded design selects an integrated `a-auth` logical AS with MCP-only opaque access tokens, current token lookup/introspection, pre-registered public/confidential clients and no refresh issuance in the first profile. ADR 0009 selects a single AS-owned transactional-database authority and per-request browser grant-flow direction without selecting an issuer, physical store/schema, resource identifier, scope vocabulary, or concrete registration/session/CSRF implementation.
- **MCP policy to Vona execution:** registry entries are server-owned and immutable for dispatch. A validated client still cannot choose method, route, executor options, authentication, or tenant. The MCP layer must create an isolated request identity; normal controller guards/AOP and domain ownership remain authoritative.
- **Vona business operation to MCP result and telemetry:** DTO/response compatibility does not authorize every field's release. External clients and log/audit sinks are separate disclosure boundaries. Downstream transactions and irreversible effects remain owned by the domain operation.

The active Vona instance is the tenant boundary; this proposal introduces no alternate user, tenant, or MCP resource-module-owned consent, registry, or audit persistence. ADR 0009 amends DEC-MCP-09 for design only to select a single AS-owned transactional-database authority and AS-owned per-request browser grant flow; a physical store/schema, concrete browser implementation or remembered consent remains unapproved. Current Vona generic instance selection and executor context delegation are **hazards to constrain**, not MCP security controls already proven effective.

## Fail-closed policy matrix

Each gate below is **necessary, not sufficient**. Effective visibility/call authority is the intersection of approved transport and host, validated resource-bound token, bound instance, active mapped local subject, deployment enablement, eligible/approved registry entry, scope, local RBAC, domain data scope, and risk policy. An authenticated client cannot turn a failed gate into a grant by changing its tool name, arguments, or protocol state.

## Source checks and version caution

The linked [2026-07-28 Streamable HTTP profile](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [request metadata](https://modelcontextprotocol.io/specification/2026-07-28/basic/index#_meta), [server discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover), and [tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) describe POST request/response exchanges, per-request `_meta` and matching headers, `server/discover` as a protocol request, and `tools/list` / `tools/call`. They do not justify importing older `initialize`/GET/DELETE/session behavior into this profile. DEC-MCP-02 subsequently selected the 2026-07-28 revision and SDK versions for the design, while wire/SDK compatibility still requires execution proof; the [v2 SDK HTTP guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/http.md) warns that default compatibility may admit older traffic unless explicitly rejected. These links informed the subsequent ADR 0002 design acceptance; this threat-model record itself is not a library or endpoint implementation authority.

Source-only Vona inspection locates the generic selector path in `vona/src/suite-vendor/a-vona/modules/a-instance/src/main.ts`, executor context delegation in `vona/src/suite-vendor/a-vona/modules/a-executor/src/bean/bean.executor.ts`, and controller response/body interceptors in `vona/src/suite-vendor/a-vona/modules/a-body/src/bean/interceptor.bodyRes.ts` and `interceptor.bodyReq.ts`. A future native Node transport route must explicitly control parser ownership, response envelopes, error formatting and context lifetime; ordinary `performAction` tests cannot prove real HTTP wire behavior. These are source observations, not implemented MCP controls.

## Open design gates and closure

1. `DEC-MCP-02` (accepted design only): use the selected 2026-07-28 profile, v2 server/Node adapter, modern-only `/mcp` methods, negotiation, framing, and unsupported-feature behavior; prove the installed SDK and real HTTP behavior under `ATP-MCP-TRANSPORT-01`. Do not import initialization, GET/SSE, or protocol-session assumptions from another version. Transport identifiers never grant authorization.
2. `DEC-MCP-03` (accepted bounded design) and `DEC-MCP-09` (ADR 0009 design-only amendment): the integrated `a-auth` logical AS is selected with `zhennann` responsible for implementation and operations; pre-registered public/confidential clients, authorization code + PKCE S256, MCP-only opaque tokens with current lookup, and **no refresh issuance** define the first profile. Exact issuer/resource identity, physical shared-state representation, browser/session/CSRF mechanics, scopes/local subject mapping, consistency and outage behavior remain implementation gates. Blocked AS `WBS-MCP-20-04` / prospective `ATP-MCP-AUTH-03` precede blocked RS `WBS-MCP-20-02` / `ATP-MCP-AUTH-01`; neither task nor ATP is executed. ADR 0009 selects a single AS-owned transactional-database authority with atomic code consumption/token activation and an AS-owned browser approve/deny flow for each request, but no physical store/schema, concrete browser/session/CSRF implementation or remembered consent; approve those concrete details separately and ask about the owning module's `fileVersion` before a schema edit. Current-state lookup fails closed; the JWKS-refresh rule applies only to a separately selected JWT/JWKS alternative. Existing `auth-oauth` login and ordinary temporary tokens are not proof.
3. `DEC-MCP-04`: confirm canonical host/instance/resource mapping, proxy trust, selector-conflict disposition and same-subject cross-instance behavior; do not trust a raw host or forwarded header by default.
4. `DEC-MCP-05`: confirm metadata syntax and ownership, catalog generation/freshness, uniqueness and fixed registry lifecycle without new MCP persistence.
5. `DEC-MCP-06`: confirm eligibility, business side-effect classification, list visibility vs call policy, field minimization and a server-verifiable confirmation model; no implicit destructive enablement.
6. `DEC-MCP-07`: confirm context/Passport factory, executor adaptation, timeout/cancellation, domain commit and retry boundaries with separate-context concurrency proof.
7. `DEC-MCP-08`: review [ADR 0008 (proposed)](./decisions/0008-mcp-limits-audit-telemetry-redaction.md) and confirm numeric limits/keys/windows, worker/outage/deadline behavior, protected audit and telemetry sink/operator/retention, downstream redaction and evidence map. Accountable decision owner `zhennann` does not itself identify an OAuth operator, proxy administrator, or audit-sink maintainer.

The resulting `planning-complete` status is documentary only: it did not accept DEC-MCP-02 through DEC-MCP-08 at that revision's closure. Subsequent independent design-only acceptance of DEC-MCP-02 on 2026-10-07, DEC-MCP-03 on 2026-10-09, and ADR 0009's DEC-MCP-09 amendment on 2026-10-10 does not select a concrete store/schema, issuer/proxy/sink/limit/tool, provide ATP/security proof, or authorize source execution; remaining `TODO(confirm)` items remain downstream gates. Source execution still requires its own bounded dossier.
