This `repo-specs/cabloy-mcp/` directory retains the existing `MCP` requirement, WBS, and ATP IDs for the planned `cabloy-mcp` normal Vona suite. It is maintainer-facing planning material, not end-user documentation, source implementation, or execution authorization. ADR 0001 accepts the overall first-increment boundary and DEC-MCP-01's initial structural/configuration design; ADR 0002 accepts DEC-MCP-02's transport design only; ADR 0003 accepts the bounded DEC-MCP-03 OAuth design only. ADR 0009 accepts a bounded design-only DEC-MCP-09 amendment selecting AS-owned shared authorization state, a database-neutral single AS-owned authority with code consumption/token activation in the same atomic commit, an accepted bounded physical aggregate/opaque-credential direction, and a Zova-presented, AS-controlled per-request grant-flow direction with an accepted bounded browser presentation direction; the first AS implementation now targets SQLite via `better-sqlite3` on Vona's existing primary datasource, without proving actual deployment configuration or atomicity; those initial directions approved no schema, Zova site/admission, browser session/CSRF implementation or consent record. The later bounded physical storage selection below is not executable-DDL or source approval. Initial scaffold/configuration and application integration now exist under separately approved bounded increments recorded in the [phase-20 index](./evidence/phase-20/index.md). The user-directed 2026-10-17 bounded supersession in ADR 0001 sets module-owned `enabled: app.meta.env.CABLOY_MCP_ENABLED !== 'false'`: default enabled, only literal `false` disables, with no standard application MCP `enabled` environment mapping. Generic framework application overrides still merge after module defaults. This supersedes only default-off/literal-`true` application opt-in, not OAuth/host/registry/policy fail-closed readiness; further source execution, endpoint exposure, ATP and release proof remain gated. A proposed, blocked AS delivery task `WBS-MCP-20-04` now precedes the blocked resource-server task `WBS-MCP-20-02`; its ordering and ATP declaration do not authorize implementation.

The later fresh-only installation scope/exclusions and confirmation-requirements disposition below does not resolve actual eligibility, deployment attestation, exact schema/browser contracts or separate execution approval; cross-host SQLite and replica support are not selected. ## Current or Intended Topology

Existing normal Vona suites include `cabloy-basic`. The absence of a `cabloy-mcp` suite/module or naming collision at the originally inspected revisions was a historical pre-scaffold observation. Initial scaffold/configuration and application integration now exist under separately approved bounded increments in the [phase-20 index](./evidence/phase-20/index.md), within the normal-suite workspace/discovery layout:

```text
vona/src/suite/cabloy-mcp/
└── modules/cabloy-mcp/
```

The suite generator defaults to `src/suite`, matching this target. Its not-yet-run status was a pre-scaffold observation; the phase-20 index records subsequent approved initial source/configuration and application integration. DEC-MCP-01 fixes the initial `5.0.0` manifests: the suite composes `vona-module-cabloy-mcp` via `workspace:^`; the module starts with empty library `dependencies`, `vonaModule.dependencies` containing only `a-vona: 5.0.0`, and no `fileVersion` or `meta.version.ts`. The CLI-generated project references, metadata, module registration, and application dependency are not handwritten. Under ADR 0001's 2026-10-17 bounded supersession, module `src/config/config.ts` owns typed `enabled: app.meta.env.CABLOY_MCP_ENABLED !== 'false'` configuration: default enabled, only literal `false` disables. Application `vona/src/backend/config/config/config.ts` has no standard MCP `enabled` environment mapping; generic framework application overrides remain supported after defaults. Initial source does not establish OAuth/host/registry/policy readiness, endpoint exposure or ATP proof. The MCP SDK versions and transport integration design are selected by DEC-MCP-02; installation/transport runtime proof and OAuth libraries and the remaining protocol/controller/bean/service layout details retain their respective DEC-MCP-03 through DEC-MCP-08 or bounded execution-dossier gates, not assumed runnable paths. The module must not create a new tenant, Passport, RBAC, or business-resource authority. It owns MCP transport adaptation, discovery projection, policy enforcement, dispatch isolation, and protocol-facing errors; existing domain modules retain business authorization and persistence ownership.
