# A-MCP Internal Planning

This `repo-specs/cabloy-mcp/` directory retains the existing `MCP` requirement, WBS, and ATP IDs for the planned `cabloy-mcp` normal Vona suite. It is maintainer-facing planning material, not end-user documentation, source implementation, or execution authorization. ADR 0001 accepts the overall first-increment boundary and DEC-MCP-01's initial structural/configuration design; ADR 0002 accepts DEC-MCP-02's transport design only; ADR 0003 accepts the bounded DEC-MCP-03 OAuth design only. ADR 0009 accepts a bounded design-only DEC-MCP-09 amendment selecting AS-owned shared authorization state, a database-neutral single AS-owned authority with code consumption/token activation in the same atomic commit, an accepted bounded physical aggregate/opaque-credential direction, and a Zova-presented, AS-controlled per-request grant-flow direction with an accepted bounded browser presentation direction; the first AS implementation now targets SQLite via `better-sqlite3` on Vona's existing primary datasource, without proving actual deployment configuration or atomicity; it approves no schema, Zova site/admission, browser session/CSRF implementation or consent record. Concrete configuration, source execution, and runtime proof remain gated. A proposed, blocked AS delivery task `WBS-MCP-20-04` now precedes the blocked resource-server task `WBS-MCP-20-02`; its ordering and ATP declaration do not authorize implementation.

The 2026-10-15 bounded inputs additionally select **same-host multiple Vona workers sharing persistent SQLite** through that primary datasource and, **if persistence resides in existing `a-auth`, keeping `vonaModule.fileVersion: 1` and folding the schema into its version-1 creation path**. This adds no version-2 migration and does not automatically upgrade databases already recorded at v1. The later fresh-only installation scope/exclusions and confirmation-requirements disposition below does not resolve actual eligibility, deployment attestation, exact schema/browser contracts or separate execution approval; cross-host SQLite and replica support are not selected. Cross-worker contention, revocation visibility and connection/failure behavior require later runtime proof.

On 2026-10-15, the [installation scope and deployment-confirmation requirements](./wbs-mcp-20-04-as-contract-dossier.md#92-installation-applicability-accepted-bounded-design-only) were separately accepted for bounded design only: fresh physical-database/v1 creation only, with existing-v1, inconsistent, partial and unknown installations excluded or blocked pending separate treatment. The operations-owned, secret-free confirmation requirements are accepted, but the template remains entirely unfilled and no actual installation is classified as eligible. This disposition does not attest deployment, select remaining schema/connection/browser contracts, or authorize execution.

The subsequently prepared [owner/representation/activation-check refinement, sections 9.5–9.8](./wbs-mcp-20-04-as-contract-dossier.md#95-owner-and-runtime-boundary-bounded-design-accepted), was separately accepted for bounded design only on 2026-10-15: existing-`a-auth` physical ownership and dedicated service-scene responsibilities, one logical aggregate/lifecycle, layered read-only activation responsibilities/timing, and only verifiable continuity of the same approved fresh-v1 installation across restart. This satisfies the existing conditional keep-v1 owner premise, without admitting arbitrary existing-v1 targets. At that disposition, exact source targets, schema/DDL, check/provenance/coherence mechanisms, credentials and connection settings remained unapproved; the later paragraph below records only bounded mechanism acceptance; all deployment observations stay unconfirmed. Delivery remains blocked, ATP prospective, and execution is not authorized.

## Current or Intended Topology

Existing normal Vona suites include `cabloy-basic`. No `cabloy-mcp` suite/module or package-name collision was observed at the inspected revisions. The accepted new-source target fits the existing normal-suite workspace/discovery layout:

```text
vona/src/suite/cabloy-mcp/
└── modules/cabloy-mcp/
```

The suite generator defaults to `src/suite`, matching this target, but has not been run. DEC-MCP-01 fixes the initial `5.0.0` manifests: the suite composes `vona-module-cabloy-mcp` via `workspace:^`; the module starts with empty library `dependencies`, `vonaModule.dependencies` containing only `a-vona: 5.0.0`, and no `fileVersion` or `meta.version.ts`. The CLI-generated project references, metadata, module registration, and application dependency are not handwritten. Module `src/config/config.ts` owns typed default-off configuration; application `vona/src/backend/config/config/config.ts` owns explicit environment overrides. Generator output and activation behavior must be inspected only in a separately approved scaffold execution. The MCP SDK versions and transport integration design are selected by DEC-MCP-02, but the packages are not installed; OAuth libraries and the remaining protocol/controller/bean/service layout details remain under DEC-MCP-03 through DEC-MCP-08 or an approved execution dossier, not current runnable paths. The module must not create a new tenant, Passport, RBAC, or business-resource authority. It owns MCP transport adaptation, discovery projection, policy enforcement, dispatch isolation, and protocol-facing errors; existing domain modules retain business authorization and persistence ownership.

## Document Authority

- The PRD owns external-AI product outcomes, scope, user journeys, and product acceptance.
- The SRS owns MCP/OAuth/instance/API/tool/dispatch/security/privacy/operational contracts and technical acceptance.
- The PDP/WBS owns delivery order, dependencies, implementation tasks, and completion checks.
- The test plan owns executable acceptance scenarios, evidence format, and release proof.
- ADR 0001 owns the accepted overall suite boundary, naming, no-new-persistence choice, DEC-MCP-01 structural/configuration design, and first-increment trade-offs. ADR 0002 accepts DEC-MCP-02's transport design only; ADR 0003 accepts DEC-MCP-03's bounded OAuth design only; ADR 0009 accepts DEC-MCP-09's AS-owned shared-state/same-commit atomicity and Zova-presented AS browser-flow **directions** for design only. DEC-MCP-04 through DEC-MCP-08 remain unaccepted integration designs.
- Progress is derived status only and cannot upgrade a proposed decision or claim evidence.

When records disagree, update the document that owns the fact first, then update downstream traceability and derived views. A static audit or generated chart does not close ADR 0001's remaining design gates, create source, or prove a security control.

## Traceability Chain and Status Rules

```text
PRD requirement -> SRS contract -> PDP/WBS task -> ATP scenario -> observed evidence
```

Exact declaration-level links use `PRD-MCP-*`, `SRS-MCP-*`, `WBS-MCP-*`, and `ATP-MCP-*` identifiers. Ranges and wildcard summaries do not define records. New delivery rows start as `not-started`, `deferred`, or `blocked`; no implementation or ATP evidence is claimed in this baseline.
